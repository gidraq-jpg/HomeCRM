# Серверный контракт офлайн R1c.8

Сессия, Origin, обязательный TOTP, эталон доступа и RLS действуют как в сетевых маршрутах.
Оболочка и локальная очередь принадлежат задаче 8b; серверный контракт реализован здесь.
Shared-схемы: `packages/shared/src/offline.ts`, `notes.ts`, `tasks.ts`, `meters.ts`.

## Согласованное чтение

`GET` с `?offline=true` возвращает `{accountId, data: <прежний ответ>, versions: [{id, version}]}`.
accountId — текущая авторитетная учётная запись; клиент сверяет её с владельцем запроса и
поколением сессии до записи в IndexedDB. Поздний ответ другого аккаунта нельзя подписывать
меткой прежнего кэша даже при смене общей cookie в другой вкладке.
Содержимое и точные UTC ISO-версии PostgreSQL читаются одной транзакцией REPEATABLE READ.
Поддержаны `/api/tasks`, `/api/tasks/:id`, `/api/tasks/today`, `/api/tasks/plan`,
`/api/notes`, `/api/notes/:id`, `/api/objects/:id`, `/api/objects/:id/meters`,
`/api/meters/:id`, `/api/meters/:id/readings`, `/api/readings/:id`.
`versions` относится к основному виду ответа: дела, заметки, объект, счётчики или показания.
Для чтения без права офлайн-правки wrapper с авторитетным accountId и пустыми versions
поддерживает `/api/deadlines` (радар с прежними filters), `/api/shopping`, `/api/shopping/:id`,
`/api/objects`, `/api/documents`, `/api/documents/:id`, `/api/documents/:id/versions`,
`/api/contacts`, `/api/contacts/:id`, `/api/contacts/:id/interactions`, `/api/accounts`,
`/api/accounts/:id`, `/api/objects/:id/accounts`. Прежние параметры фильтров сохраняются.
Документ остаётся замаскированным штатным API; wrapper не раскрывает его номера.
PDF/байты/preview файлов, unmask, auth/session/security/settings/export и остальные пути
не входят в allowlist кэша и не получают такой snapshot. Нельзя кэшировать ответ вне allowlist
лишь потому, что предварительная `/api/me` была успешна. Обычные GET без флага прежние.
Версия заметки включает изменения её пунктов, в том числе авторские/личные и корзину пункта.
Чек-лист дела находится в самой строке дела.

Без флага ответ прежний. Нельзя присоединять отдельно полученную свежую версию к старому
содержимому или автоматически править старый кэш без точной версии. Нужен свежий снимок
или явное разрешение конфликта пользователем. UUID последнего отсчёта берётся из
`previousReading` в снимке счётчиков либо последнего элемента ряда показаний.

## Реализованная очередь

JSON-запросы очереди содержат `offline:true`, обязательный UUID `ownerAccountId`, стабильный UUID `idempotencyKey`, необязательный
`clientActedAt` (UTC ISO). Неизвестные поля отвергаются. Для каждой новой операции новый ключ.

| Метод и путь | Shared-схема / поля | Наблюдавшаяся база | Зависимость |
|---|---|---|---|
| POST `/api/tasks` | OfflineTaskCreate: TaskFields, placement?, householdId?, objectId?, links? | Нет | Существующие доступные ссылки |
| PATCH `/api/tasks/:id` | OfflineTaskPatch: title/description/planOn/planTime/dueOn/dueTime/checklist | expectedUpdatedAt точного снимка | UUID и версия create/предыдущей правки |
| POST `/api/tasks/:id/status` | OfflineTaskStatus: status=done | expectedUpdatedAt | UUID и версия последней зависимой операции |
| POST `/api/notes` | OfflineNoteCreate: title/body/pinned/checklist/placement?/object? | Нет | Доступный контекст |
| PATCH `/api/notes/:id` | OfflineNotePatch: title/body/pinned/checklist | expectedUpdatedAt | UUID/версия заметки и UUID пунктов |
| POST `/api/objects/:id/files` | Один multipart-файл, прежние лимиты/обработка | заголовок X-Expected-Updated-At | Подтверждённый объект |
| POST `/api/meters/:id/readings` | OfflineReadingCreate: прежний ReadingInput | expectedUpdatedAt счётчика; expectedLatestReadingId UUID или null | Подтверждённые photoIds |
| POST `/api/objects/:id/readings` | OfflineReadingsCreate: readings из 1–100 различных счётчиков | Оба базовых поля у каждого элемента | Все photoIds подтверждены |

Для multipart обязательны `X-Offline: true`, `X-Owner-Account-Id: <UUID владельца намерения>`, `Idempotency-Key: <UUID>`,
`X-Expected-Updated-At: <точная версия объекта>`. Хэш связывает аккаунт, вид/родителя,
безопасное имя, точную базовую версию и исходные байты до перекодирования. Повтор не пишет
новые блоки. Показание принимает только живое изображение того же объекта; шифрование,
подготовка, пределы и сверка неизвестного COMMIT — штатный lifecycle файлов.

Сетевой клиент без `offline:true` сохраняет прежнюю семантику миллисекундного `updatedAt`.
Один `idempotencyKey` не обозначает офлайн. Финансы, перенос, расширяющее назначение,
аудитория, настройки и безопасность не входят в allowlist. Повторы/назначения существующей
серии меняются обычным сетевым API; создание дела с прежним repeatRule разрешено.
Покупки поддерживают безопасные сетевые повторы, но не офлайн-запись.

## Квитанция и продолжение

Успех очереди содержит `receipt` со стабильными `ownerAccountId`, `key`, `operation`, `confirmedAt`,
`results:[{id,updatedAt}]`. В `updatedAt` — точная версия строки результата перед COMMIT,
сохранённая той же транзакцией, с шестью знаками дробных секунд. В повторе обычная карточка
может быть новее, но версия квитанции не меняется. Для следующих зависимых правок используется
версия квитанции; новая чужая правка даст конфликт. `confirmedAt` — серверная метка подготовки
квитанции в транзакции; ответ отправляется после подтверждения COMMIT. `clientActedAt` только
описывает время намерения и не заменяет аудит базы, дату выполнения, права или версию.

Квитанция заметки содержит `checklist:[{id,position,clientId?}]`. У нового локального пункта
передают `clientId`, а не вымышленный серверный `id`; после подтверждения клиент переписывает
зависимые ссылки на полученный UUID. У существующего пункта передают его настоящий `id`.
Пропущенные пункты уходят в корзину по прежнему контракту.

Квитанция дела сохраняет `completionEventId` и `nextTaskId`; повтор выполнения не создаёт
ещё историю, преемника или уведомление. В квитанции показаний `warningIds` содержит UUID
отсчётов с прежним предупреждением, без значений или текстов; повтор возвращает то же
предупреждение. Ответ batch остаётся массивом, каждый элемент содержит одну общую квитанцию
всей атомарной операции. Нельзя превращать неизвестный исход batch в новые одиночные ключи.

Ключи ограничены аккаунтом; вид/маршрут/UUID и проверенное содержимое входят в хэш.
Владелец намерения должен совпадать с текущим аккаунтом: иначе 403 ACCOUNT_MISMATCH до записи
и создания квитанции. В batch владелец один на весь envelope. Клиент дополнительно сверяет
owner/key/operation полученной квитанции перед переписыванием зависимостей. Нельзя менять
offline/owner/key после неизвестного исхода старого запроса.
Одинаковые конкурентные запросы сериализуются перед блокировками записей. Повтор проверяет
текущие права, живой источник и вложение. `409 IDEMPOTENCY_CONFLICT`, `STALE_VERSION`,
`STALE_READING_BASE` — конфликт, не успех. Прежние причины отказа чтения/изменения и
проверки порядка/точности показаний сохраняются. Устаревшая база не меняет данные.

При сетевой ошибке после отправки состояние — «исход неизвестен»: сохранить запрос/ключ,
байты фото и зависимости, повторить исходное проверенное содержимое. Авторизация обновляется
перед replay. Ошибка прав не разрешает перейти к другому аккаунту. Конфликт блокирует только
зависимую цепочку; независимые операции продолжаются. Неподтверждённое локальное намерение
можно убрать до отправки; после неизвестного исхода сначала требуется квитанция.

Старые строки api_operations сохраняют UUID и хэш без новой квитанции; повтор работает,
но точную базовую версию из него выдумывать нельзя. История ключей не очищается этой задачей.
Отмена выполнения остаётся `/api/tasks/:id/undo` с исходным eventId и серверным окном 7 секунд.
Офлайн-намерение и clientActedAt не продлевают окно; `UNDO_EXPIRED`, `COMPLETION_CHANGED`,
`NEXT_TASK_CHANGED` остаются отказами. Если подтверждение пришло позже — обновить карточку.
