# D23a — первый вход и производительность

TPL-5, SRCH-5; 23 октября 2026. База сравнения: origin/main 88a54b3.

## Первый вход

Личная серверная отметка `notification_settings.first_entry_shown` по существующей RLS.
Новый участник получает false; экран автоматически открывается перед «Сегодня» и сразу
записывает true, поэтому переход по ссылке и закрытие страницы не вызывают повтор.
При ошибке записи есть сообщение и повтор. Кнопка «Понятно» ведёт на «Сегодня».
PATCH принимает только true. Экран доступен повторно через «Ещё».
Оговорка PRD 7.5 сохранена; PRD не задаёт отдельного текста для ребёнка.

Миграция 0066 отмечает всех прежних участников, включая тех, у кого не было строки настроек.
Для backfill владелец в одной транзакции временно снимает FORCE RLS с accounts и
notification_settings и сразу восстанавливает его; политики и права остальных колонок не меняются.
Старые настройки сохраняются. Поле включено в личный экспорт.
Регрессия обновления реальной базы с 0065 проверяет backfill; отдельный тест проверяет нового участника,
повторный вход, независимость отметок и запрет сброса через API.

## Набор и метод

`apps/server/src/testing/family-perf.ts`, seed=23: 1000 дел (треть с ежедневным повтором),
2000 заметок, по 1000 контактов, документов, объектов, покупок, ручных сроков и начислений.
Всего 10 000 первичных записей; служебный лицевой счёт, производные сроки и наступления — сверх этого числа.
Общие и личные записи взрослого/ребёнка распределены 50/30/20, общая аудитория включает взрослых;
5% записей основных списков — в корзине. Начисления — общие.
Содержимое и распределение определяются seed; даты отсчитываются от текущей даты дома,
UUID создаёт одноразовая база. Генератор принимает только тестовый World с именем homecrm_test_*.
Один лицевой счёт — упрощение нагрузки; это не модель бухгалтерии семьи.

PostgreSQL 18 в отдельном compose homecrm-test-feat-tpl-5-first-entry-perf-perf, Fastify inject,
Windows/Node 24, один worker, без параллельного прогона тестов.
По каждому URL: 5 запросов разогрева, 30 измерений, ближайший ранг p95.
Сравниваются исходные server-файлы main и изменения на одном генераторе.

## Разбор SQL

Полные `EXPLAIN (ANALYZE, BUFFERS)` под ролью homecrm_app и контекстом участника:
[до](D23a-before-explain.txt), [после](D23a-after-explain.txt).
Планы относятся к SELECT карточек Today и вызываемому из Today радару с верхней датой завтра,
а не ко всему HTTP-ответу или широкому диапазону радара.

SELECT карточек: 3.875 → 3.840 мс; радар Today: 18.741 → 15.322 мс.
Убран общий jsonb_agg радара: PostgreSQL возвращает строки напрямую, метаданные вычисляет один раз.
LEFT JOIN сохраняет метаданные пустого ответа; явный ORDER BY сохраняет порядок.
Убраны три повторных чтения tasks в summaries: UUID ссылок берутся из уже загруженных строк,
а контакты, участники и наступления по-прежнему читаются под RLS.
Новые индексы не потребовались, политики доступа не ослаблены.

Первоначальный диагностический генератор ошибочно назначал все 2800 видимых сроков на один день:
Today ~692 мс, радар ~646 мс. Эти цифры не сравниваются с итоговым набором.
На том диагностическом наборе EXPLAIN радара сократился с 261 до 140 мс;
итоговый генератор распределяет сроки по календарю.
