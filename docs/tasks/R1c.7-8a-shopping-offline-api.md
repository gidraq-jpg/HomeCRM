## 1. Покупки

1. API чтения общего («Вся семья») и личного списков, выбор текущего дома при нескольких членствах, CRUD позиции, «куплено»/отмена, корзина/восстановление. Личные записи недоступны даже администратору; ребёнок добавляет и меняет доступные общие покупки по действующему эталону.
2. Позиция: название, количество (текст, например «2 упаковки»), заметка, магазин/категория, связь с настоящим делом или объектом. Уточнить существующие поля `data` и механизм связей, валидировать zod. Не вводить самостоятельную сущность списков, если личное/общее уже выражается пространством; не добавлять произвольные именованные списки сверх SHOP.
3. Быстрое добавление — одно название/строка без обязательного мастера; непонятные части остаются текстом, не придумывать новый языковой парсер. Полные поля редактируются обычным API.
4. Отмена «куплено» сбрасывает отметку. Купленное группируется отдельно. Через семь суток от актуальной `bought_at` оно убирается из активного списка через корзину, без физического удаления мимо существующей политики. Повтор задания безопасен; отмена покупки одновременно с очисткой не теряется. Восстановление не должно немедленно повторять автоматическое удаление; закрепить поведение в контракте и тесте.
5. Добавить настоящий поиск покупок, сохранить экспорт, историю/вклад, доступные связи и обычные подтверждения изменения доступа. Для совместимости со старым строгим клиентом новый тип включается параметром `includeShopping=true`; по умолчанию исключается до лимита и счётчиков. Проверить оба режима под RLS, описать параметр для задачи 8b. Не утекать скрытыми названиями через связи/справочники. Если требуется узкая функция уборки worker — только необходимые права и матрица, без доступа к текстам или обхода RLS в приложении.

## 2. Контракт безопасных повторов для офлайн

Сначала составить точную таблицу поддерживаемых операций в `docs/api-offline.md`: метод/маршрут, схема, ключ, версия, зависимости, успешная квитанция, конфликты и доступ. Это готовый контракт для исполнителя 8b, а не обещание будущего API.

Для обязательного чтения без сети согласовать явную allowlist «Сегодня», радара, покупок и последних карточек. Каждый кэшируемый ответ помечается авторитетным `accountId` текущего запроса; отдельно прочитанный `me` не связывает ответ с владельцем при смене общей cookie. Для разрешённых к изменению записей содержимое и точная версия получаются одним согласованным снимком. У read-only карточек точная версия не разрешает запись вне allowlist; не выдавать PDF, раскрытые секретные номера и ответы управления доступом в качестве офлайн-снимков. Обычные GET остаются совместимыми.

Обязательная ограниченная очередь: создание/правка дел и их чек-листов, выполнение; создание/правка заметок и их чек-листов; внесение показаний с фото, включая существующий атомарный `POST /api/objects/:id/readings` («Сохранить всё»). После потери ответа уже отправленную пачку нельзя без подтверждения разбивать на новые операции. Для показаний фиксируется наблюдавшаяся версия счётчика и последний отсчёт, сравнение под родительскими блокировками. Согласовать точный охват с текущими маршрутами. Доступ, перенос/назначение с расширением аудитории, финансы, настройки и операции безопасности остаются с существующим подтверждением и не исполняются автоматически офлайн. Покупки имеют безопасные сетевые повторы; офлайн-запись покупок не добавлять сверх нынешнего перечня PRD.

1. Ключ стабилен для одной попытки операции, ограничен аккаунтом, типом/маршрутом и проверенным содержимым. Офлайн-намерение обязательно несёт владельца очереди, который сравнивается с текущим аккаунтом до записи; у фото эквивалентный заголовок. Иначе намерение A без placement могло бы создать личную запись B после смены cookie. Офлайн-snapshot и квитанция также помечаются авторитетным аккаунтом ответа, не токеном; legacy онлайн-контракт не меняется. Потеря ответа после COMMIT и повтор не создают второй элемент, файл, историю, выполнение, преемника серии или уведомление. Одновременные одинаковые отправки дают один эффект. Иной запрос под тем же ключом — явный 409, не успешная квитанция.
2. Изменения существующей записи проверяют её наблюдавшуюся версию. Не допускать тихой перезаписи между двумя устройствами, после переноса/удаления или изменения прав. Повтор уже подтверждённой операции отличать от новой правки; квитанцию читать с текущей проверкой доступа.
3. Для цепочки локальных правок определить безопасную передачу UUID и **версии результата на момент COMMIT**. Текущая версия позднее изменённой записи не является такой квитанцией и не позволяет автоматически затереть чужую правку. Квитанции не содержат секретов/файлов/текстов источников; новые метаданные и права фиксируются в ADR/матрице.
4. Сохранять порядок зависимых операций и возможность продолжить независимые. Полного общего bulk-движка не требуется: расширить действующие маршруты/помощник узко, с единой shared-схемой и документированной allowlist. Не делать отдельный путь с ослабленными правами.
5. Фото: безопасный повтор multipart-загрузки с тем же ключом и проверкой байтов/родителя; затем показание связывается с подтверждённым UUID файла. Использовать существующие шифрование, подготовку, лимиты и жизненный цикл. Потерянный ответ/неизвестный исход COMMIT не оставляют дубли или необратимую потерю файла; запрет подстановки чужого вложения проверен. Отдельная загрузка и запись показания имеют документированное возобновление.
6. Даты показаний, точные десятичные значения, часовой пояс дома, предупреждения и авторство сохраняются. В контракте явно описать время клиентского действия и серверного подтверждения: клиентская метка не заменяет проверку версии/прав и не подделывает аудит. Семантику повторов/выполнения не менять молча.
7. Отмена выполнения сохраняет действующее окно 7 секунд. До подтверждения очередь может отменить своё локальное намерение; это не основание расширять серверное окно или обходить причины отказа отмены. Описать состояния неизвестного исхода для исполнителя клиента.

## Готово, когда

- Работает сквозной API SHOP-1…3, личное/общее/ребёнок/второй дом/скрытые связи, куплено/отмена/семь суток/корзина/восстановление и гонка очистки.
- Точная allowlist очереди реализована, контракты и shared-схемы доступны клиенту; нет пунктов «сделает следующий агент на сервере».
- Регрессии реального COMMIT с потерянным ответом, параллельного повтора, другого payload/аккаунта/версии, ухода из дома, удаления и изменения доступа; цепочка create → edit/complete, заметка/чек-лист, фото → показание, повтор выполнения серии не дублирует преемника/push.
- Обновление с 0063 сохраняет прежние строки/историю/квитанции/файлы; только новые миграции после последней. RLS/точные гранты/матрица, настоящий ZIP, поиск и корзина проверены. Прежние perf-пороги и тайм-ауты отдельных тестов не менялись; общий бюджет задания CI меняется только по B3 ниже.
- Обновлены `docs/api-shopping.md`, `docs/api-offline.md`, отчёт `docs/shopping-offline-api.md`, необходимые ADR/схемы. Новая зависимость обоснована; клиентских экранов/IndexedDB здесь нет.
- Во время работы целевые тесты, затем обычный push со штатным `pnpm check`; дождаться зелёного CI конкретного HEAD. Отчёт до 15 строк в PR и ведущему. Один PR прикреплён к чату.
