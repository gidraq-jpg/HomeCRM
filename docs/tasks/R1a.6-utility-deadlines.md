# Бриф R1a.6. Сроки коммуналки в радаре и уведомления о них

- **Задача:** R1a.6 из [плана](../03-dev-plan.md), серверная часть — **первой, к окну показаний 20–25 ноября**: окна показаний, сроки оплаты и поверка попадают в радар и в push. Экранные правки радара и карточка окна на «Сегодня» — отдельной задачей на готовом API.
- **Требования:** UTIL-13, DEAD-1, DEAD-2, DEAD-4, DEAD-5, DEAD-6, NOTIF-2, NOTIF-3; приложение Б (значения по умолчанию); [ADR-0028](../adr/0028-deadline-engine.md), [ADR-0029](../adr/0029-notification-dispatcher.md), [ADR-0031](../adr/0031-property-accounts.md), [ADR-0032](../adr/0032-meters-readings.md).
- **Ветка:** `feat/util-13-utility-deadlines`, в своём worktree от свежего `main`.

## Сделать

0. **Сначала — замечания ревью** (отдельными коммитами), строки бэклога PR #35 и #36:
   - для экранов: признак `supplierHidden` у лицевого счёта; id личного пространства в `/me`; общий `GET /api/accounts?trash=true` (все счета в корзине, видимые участнику); `scope` у `GET /api/contacts`;
   - `meters.utility_account_id` — `ON DELETE SET NULL` (миграция безопасна для рабочей базы);
   - PATCH счётчика не возвращает статус «заменён» в «работает»;
   - восстановление показания, чей предыдущий сосед в корзине: расход пересчитывается от предыдущего живого показания;
   - `meter_readings.occurred_on` без умолчания `CURRENT_DATE`.
1. **Источники сроков** (DEAD-2) — через движок R0.8, без второго движка: окно показаний и день оплаты лицевого счёта (правила DEAD-1 уже в счёте), дата следующей поверки счётчика. Правка счёта или счётчика, корзина, восстановление, перенос и смена аудитории пересчитывают сроки; права и видимость — как у источника (ребёнок не видит сроки объекта «Взрослые»).
2. **Закрытие** (DEAD-5): окно показаний закрывается, когда у всех активных счётчиков счёта есть показание в окне и оно отмечено переданным; при способе «автоматически» или «не требуется» окно в радар не выводится. Поверка закрывается новой датой поверки. Оплата — пока только «отмечено вручную» (начисления — R1a.8).
3. **Пункт радара** (DEAD-4): основное действие по типу — «Внести показания» (ведёт на экран показаний объекта), «Отметить оплату», «Поверка проведена»; `GET /api/deadlines` отдаёт вид источника, объект с названием и статусом, лицевой счёт — чтобы клиент обошёлся одним запросом.
4. **Уведомления** (NOTIF-3): «Открылось окно показаний», «Окно закрывается завтра», «Оплата через 3 дня», «Оплата сегодня», «Подходит срок поверки» — через диспетчер R0.7, с тихими часами, бюджетом и «скрывать текст». Получатель — ответственный за объект (правило 7.3.9). Значения предупреждений — по приложению Б.
5. **Окно в часовом поясе дома** (DEAD-6), окна через границу месяца («с 28 по 5»), короткие месяцы (окно «с 29 по 31» в феврале).

## Готово, когда

- Тесты: окно открывается и закрывается в поясе дома, через границу месяца и в феврале; закрытие по DEAD-5 при двух счётчиках (один передан — окно открыто); «автоматически» не попадает в радар; поверка через год; пересчёт после правки, корзины и восстановления; push по каждому виду NOTIF-3 у ответственного, ребёнку — ничего по «Взрослые».
- Матрица доступа без расхождений; `GET /api/deadlines` по-прежнему один запрос и в пределах замера G4.
- Миграции безопасны для рабочей базы; `pnpm check` и CI проходят; ADR, если решения выходят за ADR-0028 и ADR-0032.

`apps/web` (параллельно идут экраны показаний), рабочее окружение: compose-проект `homecrm`, порты 8300, 8301 и 8309, `E:\HomeCRM-data`. Начисления и оплаты — R1a.8.
