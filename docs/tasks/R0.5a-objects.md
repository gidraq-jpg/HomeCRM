# Бриф R0.5a. Объекты, связи, свои поля и лента: база и API

- **Задача:** первая половина R0.5 из [плана](../03-dev-plan.md) — основа объектов на сервере, без экранов и без файлов. Файлы с шифрованием и превью — R0.5b ([ADR-0010](../adr/0010-files-encryption.md)); экраны — после проверки прототипа 0.5.
- **Требования:** OBJ-1…3, OBJ-5, OBJ-6, SPACE-4, SPACE-6; PRD, раздел 7.3. Эталон правил — `packages/shared/src/access.ts`.
- **Ветка:** `feat/obj-1-objects`, в своём worktree от свежего `main`. Схему и `access.ts` в это время меняет только этот исполнитель.

## Сделать

1. **Объект (OBJ-1).** Рабочая таблица объектов на образце заметок: название (единственное обязательное поле), тип из закрытого списка (на первое время — «недвижимость», «машина», «техника», «другое»; список — массив `as const`, расширяется следующими модулями UTIL, DOC и R1), свои поля «название — значение» (порядок, до 50 полей, длины ограничены схемой zod), автор, ответственный, пространство, аудитория, корзина. Подключение — `attach_record_table`. Поля типа (адрес, площадь…) — не здесь: место под них, чтобы UTIL-1 добавил их без переделки.
2. **Связи (OBJ-2).** Любая запись связывается с любой видимой записью (объекты, заметки, дела, покупки — все таблицы, подключённые `attach_record_table`) с подписью роли. Связь видна и выдаётся только тем, кто видит обе записи — в RLS и в `access.ts`, строки матрицы на все пары «кто видит одну, а другую — нет». Создать связь может тот, кто видит обе и может писать хотя бы в одну (уточнить по PRD 7.3 и записать в ADR). Связь не раскрывает существование чужой записи: ни в ответе, ни в коде ошибки, ни в счётчике.
3. **Лента (OBJ-3).** Ручные события: дата, текст, сумма (копейки), контакт — пока как ссылка на запись, оценка; файлы — место под них для R0.5b. Автоматические: создание и изменение ключевых полей — из истории (OBJ-6), с тем же правилом видимости «с момента, когда запись стала видна»; показания, начисления, продление документа, выполненные дела — точки расширения для будущих модулей, без них самих. Лента выдаётся одним запросом с постраничностью по времени.
4. **Дочерние записи (OBJ-5).** События ленты и свои поля лежат в пространстве объекта и не видны шире него.
5. **API** в `apps/server`: объекты — список, карточка, создание, правка, свои поля, смена аудитории, перенос по правилам 7.3 (как у заметок), корзина и восстановление; связи — создать, подписать, удалить, связи записи; лента — список, ручное событие (создать, править, удалить). Проверка доступа — на сервере и в RLS одновременно, без служебных обходов. Границы — схемы zod. Описание API — `docs/objects-api.md`.
6. **Пункты бэклога «К R0.5»**, которые касаются этой задачи:
   - отказ отложенного внешнего ключа дочерней записи (23503) не выдаёт существование чужой записи — тест под ребёнком;
   - `record_guard` для всех таблиц, кроме заметок, считает вкладом любое поле — привести к PRD 7.3.6 (вклад — заголовок или текст, добавление, правка или отметка пунктов и дочерних записей; закрепление, аудитория, корзина и восстановление вкладом не считаются) для объектов, дел и покупок.
   Закрытые пункты вычеркнуть.
7. **Решения для каждой новой сущности (AGENTS.md):** поиск — колонка или индекс под R0.6 (название, свои поля, текст событий), без самого поиска; экспорт — что попадёт в личный и общий экспорт R0.10; корзина — у связи и события ленты (вместе с записью или отдельно). Записать в новый ADR (следующий свободный номер — проверить `docs/adr`, 0023 или дальше).
8. **Журналы:** ни названий, ни значений своих полей, ни текстов событий (PRD, раздел 13).

## Готово, когда

- Матрица доступа охватывает объекты, связи (все пары видимости), ленту и перенос; расхождений нет; ослабленная политика роняет тест.
- Интеграционные тесты API на вымышленной семье: взрослый, второй взрослый, ребёнок, администратор не видит чужое личное; связь с невидимой записью не раскрывает её; лента ребёнку — только с момента, когда объект стал виден «Всей семье».
- Миграция безопасна для существующих данных (тест обновления базы, как `household-upgrade.test.ts`).
- `pnpm check` и CI проходят.

## Блокеры ревью PR #16 (Opus, 6 октября) — исправить в той же ветке

1. **Событие ленты не пропадает из-за контакта.** Сейчас политика `object_events_select` (0010_objects.sql:182, то же в 0014) и `timeline.ts:161` прячут всё событие, если его контакт удалён очисткой корзины или стал невидим (например, автор сделал заметку-контакт личной) — событие теряют все, включая автора, оно не попадает в корзину и экспорт. Нужно: видимость события — только по объекту; невидимый контакт скрывается **как поле** (в ответе — без контакта, без его названия и без признака, что он был); при окончательной очистке записи ссылки на неё как на контакт обнуляются (по образцу `purge_record_link_tree`). Тесты: очистка контакта, контакт стал личным, ребёнок не видит контакт «Взрослые», но видит событие. Поправить ADR-0023.
2. **Восстановление родителя возвращает всё, что ушло в корзину вместе с ним.** Сейчас (0014:33, `cascade_trash` в 0005:346) при восстановлении объекта автором-не-администратором чужие поля и события остаются в корзине, их не видно в API, через 30 дней они стираются. Нужно: восстановление родителя восстанавливает дочерние записи, удалённые его каскадом (достаточно права восстановить родителя); дочерние записи, удалённые отдельно до этого, остаются в корзине. То же для пунктов заметок. Тесты: мама (взрослый, не администратор) удаляет и восстанавливает свой объект — поля и события папы вернулись; то же для заметки с чужими пунктами.

Остальные замечания ревью — в бэклоге, в этой ветке их не делать.
