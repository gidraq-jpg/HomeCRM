## Новые клиентские блокеры PR #51

### B1. Сбросить состояние интерфейса на границе пользователя · P1

**Место:** `apps/web/src/tasks/TaskForm.tsx:73–78`, `Quickline.tsx:56–60`, подключение экранов в `App.tsx:77–81`. Контекст: `auth/AuthRoot.tsx:183`, `auth/session-cache.ts:18`.

**Сценарий:** участник A вводит личный текст в «Новое дело»; участник B входит в соседней вкладке. После обновления `/me` исходная вкладка получает B. Очистка query-кэша не размонтирует `App` и `TaskForm`: `useState(initial)` оставляет текст A. Аналогичный локальный state есть у быстрой строки и подтверждений операций. Это раскрытие личного текста B, даже если серверные RLS и списки работают правильно.

**Воспроизведение ведущего:** настоящий `AuthRoot`/`App`/`TaskForm` из HEAD PR, два вымышленных `/me`, обновление query `me` без logout/unmount. После переключения наблюдалось `{account:"…0002",title:"SYNTHETIC_PRIVATE_DRAFT_A"}`. Сам `/me` уже принадлежал B; поле сохраняло маркер A.

**Исправить:** синхронно отделить всё состояние пользовательского интерфейса по `me.id` (например, ключ на границе приложения), а не только query-кэш. Сбрасывать формы, чипы, локальные снимки, диалоги, тосты и сохранённые действия. Поздний результат запроса предыдущей сессии не должен повторно показать текст/тост, открыть прежнюю запись или вызвать действие от имени нового участника. Не сбрасывать черновик при обычном обновлении данных того же пользователя.

**Регрессия:** две страницы одного browser context с общей cookie-сессией: ввод A → вход B на соседней странице → обновление исходной без явного logout. Проверить полную форму и быструю строку, диалог назначения, тост отмены и задержанный ответ старой мутации; ни текста A, ни готового к отправке старого тела в состоянии B. Отдельно — refetch того же A сохраняет черновик. Это должен быть тест перехода `A → B`, а не прежний сценарий `A → logout → B`.

### B2. Не блокировать отмену обновлением кэша · P1

**Место:** `apps/web/src/tasks/operation.tsx:29–40,61–62`, `TaskRows.tsx:18–35`; `ui/Toast.tsx:87–88` закрывает тост сразу после callback. В карточке `TaskScreen.tsx:275–286` отмена также заблокирована `operation.pending`.

**Сценарий:** POST выполнения успешен, появился тост «Отменить», но `await refresh()` ещё ждёт активные GET-запросы. `locked.current` остаётся `true`; callback отмены вызывает `run()`, который молча возвращается. Тост исчезает, `/undo` не отправлен. В карточке медленный refetch съедает окно, оставляя кнопку отмены disabled.

**Воспроизведение ведущего:** неизменённые `TaskRows`, `useTaskOperation`, `ToastProvider/ToastRegion` и активный TanStack Query с задержанным refetch; выполнить дело, нажать появившуюся отмену в пределах окна. Результат `{statusRequests:1,undoRequests:0,refetchStarted:true,toast:null}`. Это воспроизведение клиентской гонки с синтетическими ответами, без правки сервера.

**Исправить:** отделить блокировку мутации от фоновой актуализации кэша так, чтобы подтверждённое выполнение сразу можно было отменить в оставшемся серверном окне. Не терять нажатие, не продлевать серверные семь секунд, сохранить защиту от двойной отправки; устаревший ответ refetch не должен отменять результат `/undo`. Ошибка отмены видна и после перестройки списка; тост не выдаёт пропущенное действие за выполненное.

**Регрессия:** задержать GET после успешного POST, нажать отмену до разрешения GET и проверить ровно один `/undo` по eventId, восстановленный статус и правильного преемника серии. Покрыть ленту и карточку, повторный клик, отказ сервера и перестройку/уход строки из списка. Не обходить ошибку ожиданием полного refetch в тесте.

### B3. Показать теряющих доступ перед сужением · P2

**Место:** `apps/web/src/tasks/TaskScreen.tsx:438–456`. Сейчас показано только «Прежняя аудитория может потерять доступ», а запрос уже содержит `confirmed:true`.

**Сценарий:** взрослый меняет дело «Вся семья» на «Взрослые». Диалог не указывает детей, которые перестанут видеть дело, хотя PRD 7.3.8 требует показать, кто потеряет доступ. То же необходимо для появляющегося в A4 переноса в личное.

**Исправить и проверить:** вычислить/получить актуальный состав теряющих доступ по дому записи, показать понятные имена до подтверждения; отмена диалога не меняет доступ. При недоступных данных не отправлять слепое подтверждение. Для серии пояснить влияние на следующие экземпляры. Проверки: «Вся семья → Взрослые», разрешённое «Общее → Личное», отказ и запрет сужения при ребёнке-исполнителе. Серверные проверки прав сохраняются.

### B4. Брать участников дома самой записи · P2

**Место:** `apps/web/src/tasks/ResponsibleField.tsx:24,35–40` и вызовы из `objects/ObjectOverview.tsx`, `documents/DocumentScreen.tsx`, `deadlines/DeadlinesSection.tsx`.

**Сценарий:** участник состоит в домах H1/H2; открывает видимый общий объект или документ H2 (из списка либо по прямому маршруту). Компонент берёт `HouseholdContext.householdId = me.roles[0]`, то есть H1. Новый ответственный, состоящий только в H2, отсутствует в списке, хотя готовый API `/api/households/H2/members` его отдаёт. У ручного срока есть собственный `householdId`, но он также не передан компоненту. Старый выбранный UUID отображается заглушкой, выбрать другого из H2 нельзя.

**Исправить и проверить:** передавать контекст записи/срока в `ResponsibleField`; для общей записи — её дом, для личной не подставлять произвольный дом как источник новых прав. Сохранять текущего исполнителя при пагинации/ошибке справочника, обновлять выбранное значение при смене записи и подтверждённой сервером ответственности. E2E с двумя домами и непересекающимися участниками: объект, документ, ручной срок H2; назначение члену H2 успешно, участник только H1 не предлагается как допустимый и не получает доступ.

## Серверные пробелы и обязательная интеграция

### A1. Выбор дома у старого личного дела

**Доказательство:** в `apps/server/src/tasks/routes.ts` PATCH-схема не содержит `householdId`, а выбор дома при дате использует `legacyHouse`. У участника в двух домах старое личное дело с `household_id=NULL` получает `400 HOUSE_REQUIRED` при добавлении даты; повтор с выбранным домом — `400 INVALID_INPUT`. В PR #51 это воспроизводит сценарий `API: HOUSE_REQUIRED…`.

**Исправить:** поддержать явную привязку такого дела к выбранному действующему дому в PATCH, с проверкой членства, версии и идемпотентности. Ограничить изменение этой задачей: не превращать поле в неявный перенос общего дела между домами и не переопределять пояс уже привязанной серии. Общее дело сохраняет свой дом, размещение и аудиторию. Недоступный дом не раскрывать. Если статус «жду» требует даты, обеспечить такой же путь через форму без частично сохранённых изменений.

**Клиент и тест:** при `HOUSE_REQUIRED` дать выбрать дом, сохранить черновик и повторить правку. На вымышленном участнике в двух домах проверить дату плана, крайний срок и дату проверки ожидания; правильный пояс производных сроков, повтор запроса, отказ для чужого дома. Удалить заглушку `LEGACY_HOUSE_REQUIRED` из успешного пути.

### A2. Производный срок возвращает EDIT_SOURCE

**Доказательство:** `apps/server/src/tasks/actions.ts:33–35` читает срок с `FOR UPDATE` до проверки `sourceKind`. Политика UPDATE скрывает производный срок документа, и видимый срок возвращает 404 вместо обещанного `409 EDIT_SOURCE`.

**Исправить:** сначала прочитать видимость и вид срока под обычной RLS, вернуть `EDIT_SOURCE` только для видимого живого производного срока. Для ручного срока сохранить проверку прав записи, блокировку и повторную проверку актуальности перед изменением. Не расширять UPDATE-политику производных сроков и не добавлять обход RLS.

**Клиент и тест:** видимый производный срок документа/дела/коммуналки ведёт к доступному источнику; прямой вызов возвращает `409 EDIT_SOURCE`. Чужой личный и удалённый срок остаются 404, читатель без права изменения ручного срока не может сменить ответственного. Заменить e2e-ожидание 404 у видимого производного срока на правильный контракт.

### A3. Точные причины отказа отмены

**Доказательство:** `/undo` уже различает `COMPLETION_CHANGED`, но истёкшее окно и изменённый преемник попадают из триггера в общий `409 CONFLICT` через обработчик PostgreSQL-ошибок. Клиент показывает несколько возможных причин сразу.

**Исправить:** публичные стабильные коды `UNDO_EXPIRED`, `NEXT_TASK_CHANGED` и существующий `COMPLETION_CHANGED`, сохранив атомарную защиту в базе и блокировку серии. Одна предварительная HTTP-проверка не заменяет защиту от гонки в транзакции. Если для точного различения требуется миграция функции, добавить новую миграцию вперёд, не переписывать 0057–0059; использовать технические коды/метаданные ошибки, не раскрывать сырые тексты PostgreSQL. Не менять обработку посторонних `23514` и конфликтов других модулей.

**Клиент и тест:** точное русское сообщение, обновление состояния и сохранение отказа как отказа. Убрать безусловное превращение любого `/undo` 409 в `UNDO_CONFLICT` в `operation.tsx`: сохранять конкретные новые коды, общий текст оставить только для неизвестного конфликта. До границы отмена успешна, после — `UNDO_EXPIRED`; другой eventId — `COMPLETION_CHANGED`; изменённый преемник этого события — `NEXT_TASK_CHANGED`. Повтор успешной отмены идемпотентен. Преемник прежнего выполнения сохраняется при отмене повторного выполнения даже после его правки. Проверить альтернативные пути PATCH/status: запрет нельзя обойти; возобновление после окна сохраняет преемника.

### A4. Разрешённый перенос общего дела в личное

**Доказательство:** `publicRecord` и ответ дела не содержат `hasOtherContributions`; `canMove` по умолчанию получает `true`, и UI не предлагает допустимый перенос даже автору без чужого вклада.

**Исправить:** вернуть из API проверенный признак возможности переноса либо необходимый признак чужого вклада и подключить к существующему `canMove`. Учесть вклад в дочерние записи по PRD 7.3.6, а не только верхнюю строку. Сервер заново проверяет возможность в момент переноса; клиентское поле не является авторизацией. Сохранить поведение файлов, сроков, истории и шаблона повторов при переносе; не раскрывать скрытые записи через диагностические ответы.

**Клиент и тест:** автор без чужого вклада видит «Сделать личной», подтверждает сужение доступа с указанием теряющих доступ участников и успешно переносит дело. После чужого содержательного вклада перенос недоступен, прямой запрос отвергается; появление вклада между чтением и переносом также не обходится. Чужая отметка чек-листа/вклад во вложение учитываются. Закрепление, корзина, восстановление и смена аудитории сами по себе вкладом не становятся. Не подставлять `false` при отсутствии поля. Копирование записей не добавлять в эту задачу: это отдельное расширение API.

### A5. Пояс выбранного дома

**Доказательство:** `apps/server/src/tasks/feeds.ts` вычисляет `zone`, но отдаёт только `today`; `/me` содержит один пояс. Поэтому быстрая строка дополнительного дома в PR #51 отключена. Дату выбранного дома недостаточно использовать вместо его часового пояса.

**Исправить:** отдать проверенные `householdId` и `timeZone` выбранного дома через существующий подходящий контракт (предпочтительно агрегаты today/plan), под проверкой действующего членства. Подключить этот пояс к быстрой строке и всем вычислениям/подписям дат выбранного дома, включая радар на «Сегодня». Ключи query-кэша учитывают участника и дом; при смене дома нельзя использовать старый пояс для сохранения. Для формы вне ленты предусмотреть получение того же контекста без N+1.

**Клиент и тест:** два вымышленных дома с разными поясами, фиксированный момент около полуночи, различный пояс браузера. «Сегодня», «завтра», время и данные радара относятся к выбранному дому; переключение туда и обратно не оставляет старые дату/пояс/черновик назначения. Чужой дом и ушедший участник контекст не получают. Удалить отключение быстрой строки второго дома и связанные сообщения об ограничении.

## Проверки и завершение

- На каждый подтверждённый блокер — регрессионный тест, воспроизводящий ошибку до исправления. API — настоящий сервер и PostgreSQL в отдельной тестовой базе; замокать успешный HTTP-ответ недостаточно.
- Во время работы — затронутые тесты, затем Playwright изменённых сценариев на 360 и 412 px с axe, проверкой целей от 44 px и отсутствия горизонтальной прокрутки. Обновлённые скриншоты — только Linux-контейнер, в `docs/screenshots/R1c.4c/`.
- После русских текстов — `pnpm check:encoding`; перед push — штатный `pnpm check` через hook, затем CI на новом HEAD и матрица доступа. Существующие тесты серий, отмены, экспорта и приватности не ослаблять. Непостоянный deadlock не скрывать отключением тестов или увеличением индивидуальных тайм-аутов.
