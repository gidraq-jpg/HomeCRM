## Проверенные причины и исправления

- У каждого e2e своя случайная база, вымышленная семья, origin и свободный порт. `workers: 2`, `fullyParallel` и `retries: 0` сохранены; общей базы сценариев нет.
- Часы: между чтением Date.now()+10 и pauseAt проходит реальное время. Проба с задержкой 100 мс воспроизвела ошибку; один вызов pauseAt(new Date()) сам устанавливает часы, точно останавливает их и сохраняет runFor(310). Убрано четыре одинаковых окна гонки.
- B2: снятие interception до завершения удержанного callback воспроизвело Route is already handled; завершение callback до unroute прошло. Теперь cleanup сначала дожидается callback, затем снимает interception; ошибки не проглатываются, один undo проверяется как прежде.
- Геометрия и axe: остановка sheet-in на 20 мс воспроизвела serious color-contrast, завершение той же анимации прошло. Общие проверки ждут document.fonts.ready и реальные animation.finished; пороги 44 px, overflow, контраст и расстояния сохранены.
- Радар: настоящий ответ /api/me сохраняется через route.fetch и доставляется браузеру; его тело не зависит от CDP уже отменённого focus-refetch. Статус действия A теперь явно 200; реальный вход B, accountId, пустой радар, отсутствие личного A, active и поздний ответ A проверяются как прежде.
- Очередь: одного ожидания меню в queue оказалось недостаточно. Исходный второй online reload трижды оставлял «Открываем HomeCRM» (29/30, 29/30 при ограничении CPU, 47/48 совместно с B1); owner совпадал, verified=true, outbox=3, Blob=2, потери данных нет. Теперь сразу после reload ожидается H1 сохранённого маршрута, до updateRow и unroute; helper также ждёт меню до смены hash. Это исключает изменение обвязкой IndexedDB/interception во время старта AuthRoot. Конкретный внутренний механизм зависания запроса Chromium не доказан: проба со снятием interception после начала get-session прошла 4/4, дополнительная диагностика IndexedDB — 36/36. Все прежние offline, unknown/confirmed, frozenBody и точный receipt.parent сохранены.
- Смена B1: вспомогательная вкладка выполняет настоящий sign-in B без второго AuthRoot, как в D5. Найден изъян прежней изоляции: активный SW может ответить index.html раньше page.route. Минимальная проба: URL внутри scope — перехват не вызван, приложение запущено; вне scope — перехват вызван, приложение не запущено. Поэтому B1 и радар используют инертный HTML по /e2e-session.html на том же origin вне scope оболочки; дополнительно проверяется отсутствие script. Общие cookies, настоящий вход, refetch и все privacy assertions сохранены. Runtime-гонка stale identity из D5 остаётся отдельной известной задачей бэклога.
- Корзина матрицы: родительский каскад и UPDATE его детей больше не запускаются вместе; в тестовом runMatrix trash/restore разделены по видам, сохраняя общий отчёт и прежние проверки вырожденности. Обычная роль, RLS и все сочетания участников/мест/операций сохранены, повторов транзакций нет.
- Windows baseline со штатным max_locks_per_transaction=64 воспроизвёл 53200 в миграциях: 24 файла не прошли. Только одноразовый compose.test.yaml получает 512; адрес рабочего PostgreSQL не используется.
- Для независимых полных проверок добавлен workflow_dispatch; такие явно запрошенные запуски не отменяют друг друга. Обычный CI по PR/main сохраняет отмену устаревшего запуска.

- Windows native fast-fail: после двух зелёных полных проверок третий прогон потерял worker cookies-csrf с кодом 3221226505 (0xC0000409), без JS-ошибки; в Application за это окно нет записей 1000/1001. Отдельный файл прошёл 12/12. На машине 16 логических CPU, по умолчанию Vitest запускает до 15 forks; только на Windows число ограничено четырьмя (либо меньшим числом CPU). Проверка процессов подтвердила четыре активных дочерних воркера. Это ограничение нагрузки, а не доказательство конкретного нативного дефекта; параметры Argon2 и assertions не менялись. После ограничения пять полных Windows-проверок подряд прошли.
