## B1. Черновик теряет исходную базу

Кандидат: `apps/web/src/notes/NoteForm.tsx:80`, `apps/web/src/tasks/TaskForm.tsx:83` и восстановление в `offline/drafts.ts`.

Триггер: открыть настоящий редактор с согласованным снимком V1, изменить ввод и дождаться autosave; перезагрузить страницу после чужой правки и согласованного GET V2. Восстановленный ввод V1 сейчас отправляется с `expectedUpdatedAt` V2, молча затирая чужую правку.

Сохранять и восстанавливать исходный согласованный снимок/версию вместе с черновиком. Поздний GET не заменяет эту базу. Старый черновик без базы требует явного решения, а не автоматической подстановки новой версии.

Регрессия: заметка и дело, ввод V1 → autosave → чужая V2 → reload → восстановление → сохранение. API получает исходную базу V1 и возвращает честный конфликт; чужая V2 и локальный ввод сохраняются. Проверить старый черновик без базы и продолжение обычного create/autosave.

## B2. Отмена pending гоняется с отправителем

Кандидат: `apps/web/src/offline/queue.ts:773`, `freeze` и `cancelIntent`.

Триггер: поставить done существующего дела с точным снимком, начать `synchronize`, задержать второй `/me`, отменить ещё pending и отпустить ответ. `freeze.put` восстанавливает удалённое намерение и отправляет POST; отмена в интерфейсе оказывается ложной.

В транзакции freeze перечитывать существующее намерение и проверять допустимое состояние. Удалённая/отменённая запись не создаётся заново из ранее прочитанного объекта. Состояния уже отправленного/неизвестного исхода и их исходные ключи сохраняются.

Регрессия: удержать второй `/me`, отменить pending, освободить ответ — намерение отсутствует и POST не был отправлен. Существующие двухвкладочные, lease и lost-ACK сценарии не ослаблять.

## B3. Решение конфликта использует временный ID

Кандидат: `apps/web/src/offline/queue.ts:437`, `resolveConflict`.

Триггер: confirmed create с receipt/серверным UUID → зависимая правка `notes/local:<create>` → 409 → свежий согласованный snapshot серверного UUID → осознанное применение. Поиск версии по исходному local ID завершается `EXACT_VERSION_REQUIRED`, решение невозможно.

Использовать фактически разрешённый `frozenPath`/серверный UUID для версии и нового намерения. Осознанное применение создаёт новый ключ и запрос к настоящей записи; старое отправленное тело/ключ не переиспользуются с новым смыслом. Сохранить сопоставление checklist и зависимости.

Регрессия: пройти эту цепочку через панель конфликта; новый PATCH использует серверный UUID, точную показанную базу и новый ключ. Подтверждение не создаёт дубль заметки и не блокирует независимую цепочку.

## B4. Фоновый отправитель сохраняет прежний доступ

Кандидат: `apps/web/src/offline/queue.ts:490`, `freshMe`/`synchronize` и `offline/identity.ts`.

Триггер: без AuthRoot установить adult identity, сохранить снимок «Взрослые» и общий pending; свежий `/me` возвращает child, запись получает 403. Последующий offline cachedIdentity остаётся adult и snapshotRequest выдаёт прежнее содержимое.

Применять авторитетную идентичность, роли и принадлежность пространству из отправителя окна/SW. При изменении доступа отзывать прежние snapshots/generation во всех контекстах, сохраняя pending, Blob и ввод того же аккаунта для решения. Старый batch/ответ не возвращает отозванный снимок. Смена аккаунта и выход сохраняют отдельные существующие правила удаления; не заменять механизм входа.

Регрессия: самостоятельный synchronize без AuthRoot, adult → fresh child → 403 → offline cachedIdentity/snapshotRequest. Роль обновлена, старый adult-снимок недоступен, pending/черновик/Blob сохранены. Проверить изменившийся доступ между первым и вторым свежим `/me`, а не только при запуске AuthRoot.
