## 1. Фото счётчика → показание

- На экране «Показания» (UTIL-7) у каждого счётчика — кнопка «С фото» (камера телефона через `<input type="file" accept="image/*" capture="environment">`); видна, только если ИИ включён в доме.
- Сервер сжимает фото до 1600 px (JPEG, без EXIF и геометки) и отправляет в разбор с контекстом: ресурс, тарифность (1–3 зоны), разрядность, единица, прошлое значение. Модель возвращает значения по зонам строками, как на табло; число собирает сервер с учётом разрядности (дробная часть — красные цифры/после запятой).
- Результат — черновик в поле ввода счётчика с пометкой неуверенности; дальше обычные проверки UTIL-5 (меньше прошлого, аномалия +40%). Ничего не сохраняется без «Сохранить».
- Фото: по умолчанию **не хранится** (AI-5). Галочка «Приложить фото к показанию» (UTIL-4) — тогда фото сохраняется существующим механизмом фото показаний (`reading_photo` в `apps/server/src/utilities/meters.ts`), с обычными правами.
- Несколько счётчиков на одном фото — не нужно; одно фото — один счётчик.

## 2. Квитанция → начисление

- В форме начисления (UTIL-9) — «Заполнить по квитанции»:
  - **сначала QR без ИИ на телефоне** (PRD R2): платёжный QR по ГОСТ Р 56042 (`ST00012|Name=…|PersonalAcc=…|Sum=…`). Распознавание — `BarcodeDetector`, где он есть; иначе одна небольшая библиотека (обоснование в PR). Из QR: сумма (копейки!), лицевой счёт → подбор лицевого счёта дома по номеру, период/назначение, если есть;
  - **если QR нет или не прочитался** и ИИ включён — фото уходит в разбор: поставщик, лицевой счёт, период, итог, срок оплаты, строки по услугам (необязательно). Деньги модель возвращает строкой как на квитанции, в копейки переводит сервер; лицевой счёт — только из списка лицевых счетов, видимых автору.
- Результат — заполненная форма начисления с отметками неуверенных полей; сохраняет человек. Фото квитанции по галочке прикладывается как файл квитанции (существующее поле `ReceiptField`).
- Квитанция — не документ личности: AI-4 не мешает; номера лицевых счетов и суммы не попадают в журналы.

## 3. Хвосты ИИ из бэклога (PR #78, #80)

1. `ai_daily_usage`: политика FOR ALL позволяет участнику, в том числе ребёнку, сбросить счётчик предела через SQL — расход только функцией с проверкой (SECURITY DEFINER или эквивалент), без прямого UPDATE у ролей приложения; строка матрицы доступа. Дата предела — по часовому поясу дома, как на сервере.
2. Общий срок одного разбора — не больше 120 с на все попытки и схемы (сейчас худший случай ≈ 9 мин).
3. `/api/ai/status` — кэш проверки поставщиков на 30 с; ошибки 403/404/429 — свои понятные сообщения.
4. `createNote` из черновиков — с ключом повтора, как дела и покупки.
5. Контекст объектов — 50 после фильтра доступа, а не до.
6. Ключ версии согласия содержит имя поставщика: смена поставщика сама запрашивает согласие заново. В тексте согласия — что уходят фото (для пп. 1–2).

## Короткие инструкции

Как в D25: на каждый вид (`meter`, `receipt`) — не больше ~600 знаков правил и 0–2 примеров; каждая строка оправдана ростом `ai:eval`. В отчёте — длина в знаках.

## Оценка `pnpm ai:eval`

- Вымышленные образцы в репозитории: 10–15 синтетических изображений счётчиков (сгенерированные табло: ХВС, ГВС, электро 1–3 зоны, с бликом/наклоном) и 6–8 синтетических квитанций (вымышленные поставщики, лицевые счета, суммы; часть с QR, часть без). Настоящие фото — только через `--samples <папка>` вне репозитория.
- Цели на Hermes: счётчики ≥ 90% значений точно, квитанции ≥ 85% полей; QR — 100% на образцах с QR. Сумма в копейках сравнивается точно.
- Запуск против Hermes — как в D25 (служба на `127.0.0.1:8643`, ключ из файла только программой, значение не выводить). В CI — только `fake`. Если Hermes/модель не принимает изображения — остановиться и описать в отчёте, не обходя.

**Готово, когда:** `ai:eval` — цели выше (отчёт без содержимого); модульные тесты: разрядность и дробная часть, деньги строкой → копейки, разбор QR ГОСТ Р 56042 (в т.ч. кодировка и неполный QR), подбор лицевого счёта только из видимых, фото без галочки не сохраняется и не попадает в журнал, политика `ai_daily_usage` (участник не может уменьшить счётчик); матрица доступа для изменённой политики; e2e «фото счётчика → показание» и «квитанция с QR → начисление» на 360 и 412 px с axe (поставщик `fake`); `pnpm check` и CI без внешних служб.

**Общие правила:** вымышленная семья, вымышленные поставщики и номера; секреты не выводить; новая зависимость — только с обоснованием; коммиты `UTIL-4: …`, `UTIL-9: …`, `AI-7: …`; PR открыть, не сливать; отчёт — до 15 строк по шаблону `AGENTS.md`.
