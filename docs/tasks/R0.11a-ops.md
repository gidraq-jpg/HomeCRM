# Бриф R0.11a. Рабочее окружение и резервные копии

- **Задача:** первая половина R0.11 из [плана](../03-dev-plan.md): рабочее окружение на компьютере владельца и резервные копии. Само включение рабочего окружения, изменения на VPS и в DNS — только по команде владельца (AGENTS.md); задача готовит всё, чтобы это было одной командой из runbook.
- **Требования:** DATA-3, DATA-4; PRD, раздел 13 (журналы). Пункты бэклога «К R0.11».
- **Ветка:** `feat/data-3-ops`, в своём worktree от свежего `main`.

## Сделать

1. **Compose рабочего окружения** (`deploy/compose.yaml`, проект `homecrm`; ADR-0015):
   - PostgreSQL 18 с томом данных, три подключения приложения с разными ролями (`homecrm_app`, `homecrm_auth`, `homecrm_worker`) и пароли из файлов в `E:\HomeCRM-data\secrets` (создаются скриптом из `deploy/scripts`, на экран не выводятся);
   - сервер: миграции при запуске, `BETTER_AUTH_SECRET` и `HOME_TIME_ZONE` из файла окружения;
   - статика клиента с возвратом `index.html` для `/invite/…` и `/reset-password` (ADR-0008), рядом с API под одним адресом;
   - туннель `tunnel-ru` смотрит на приложение вместо заглушки; заглушка остаётся отдельным профилем;
   - профиль предпросмотра (`homecrm-preview`, свои порты и база) — для проверки выпуска до переключения.
   Наружу публикуется только 127.0.0.1.
2. **Резервные копии restic (DATA-3):**
   - копия 1 — на этом компьютере, в `E:\HomeCRM-data\backups`, путь — настройка;
   - копия 2 — облачное хранилище, совместимое с S3 (решение владельца 6 октября; по умолчанию Yandex Object Storage, адрес и корзина — настройки). Ключ доступа владелец вводит скриптом в `deploy/scripts` по образцу `save-cloudflare-token.ps1`: скрытый ввод, проверка, запись в `secrets`;
   - в копию входят дамп базы и файлы; пароль репозитория restic — в `secrets` и в инструкции, где хранить его вне компьютера (без него копии бесполезны), вместе с `BETTER_AUTH_SECRET`;
   - ежедневно, хранение 7 ежедневных, 4 недельных, 6 месячных; запуск — планировщик Windows или контейнер с расписанием, выбор объяснить в ADR;
   - проверка восстановления: скрипт поднимает базу из копии в отдельном compose-проекте и сверяет число строк по таблицам; раз в месяц — по расписанию, с отметкой результата.
3. **DATA-4:** копия перед каждой миграцией, меняющей схему; без удачной копии миграция не идёт.
4. **`/health` и сторож:** `/health` проверяет базу; внешний сторож — сценарий для VPS, который раз в минуту проверяет `https://home.gidraq.link:8443/health` и пишет владельцу (канал уведомлений — пока журнал и заготовка под Telegram R2). На VPS не ставить — только скрипт и инструкция.
5. **`docs/runbook.md`:** включение, обновление, откат, восстановление из копии, что делать при потере компьютера. Закрыть пункты бэклога «К R0.11».

## Готово, когда

- Тест (в CI или локально в своём compose-проекте `homecrm-test-<ветка>`): поднять окружение, сделать копию, удалить базу, восстановить, данные на месте.
- Секреты не попадают в журналы, образы, git и вывод скриптов; `.env` и `secrets` исключены из образов.
- `pnpm check` и CI проходят; ADR о копиях добавлен.

## Не трогать

Рабочий compose-проект `homecrm`, его тома и порты 8300, 8301 и 8309 — не запускать и не менять на этом компьютере; VPS и DNS; `packages/db` и `packages/shared/src/access.ts` (параллельно идёт R0.4a, ветка `feat/note-1-notes-api`); `apps/web`.

Отчёт — по шаблону из `AGENTS.md`.
