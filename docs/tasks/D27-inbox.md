# Бриф D27. «Входящие»: захват чего угодно и разбор ИИ

- **Задача:** четвёртая задача R2 «Захват» — часть 4 брифа [D26](D26-photo-capture.md), отложенная в PR #82. Один PR, исполнитель — Codex. **Начинать после слияния PR #82 в `main`** (используются его разборы фото, миграция 0068 и ADR-0044).
- **Требования:** INBOX-1…5 (PRD 16.2), AI-1…AI-8 (PRD 16.1, особенно AI-4 в редакции 24 октября), DOC-1, DOC-2; [ADR-0043](../adr/0043-ai-gateway.md), ADR-0044; PRD 13; AGENTS «Безопасность и данные» и «Личное остаётся личным».
- **Ветка:** `feat/inbox-1-inbox`, worktree `../HomeCRM-d27`, порты `PORT=8385`, `WEB_PORT=5247`.
- **Область:** `packages/db` (одна миграция `inbox_items`), `packages/shared` (схемы, правило в `access.ts` только для новой сущности), `apps/server/src/inbox` (новый), `apps/server/src/ai` (вид `inbox` и `document`), `worker` (разбор и очистка), `apps/web/src/inbox` (новый), главный экран и меню «Ещё», `docs/runbook.md`. **Не трогать:** правила доступа и политики RLS существующих сущностей, `deploy/hermes-ai`, `E:\HomeCRM-data`, рабочее окружение `homecrm`.

## Что сделать

1. **Сущность `inbox_items`** — строго по правилу AGENTS «Новая сущность»:
   - поля доступа: личное пространство автора, видит **только автор** (администратор тоже нет), автор, отметка удаления;
   - политика RLS и строки матрицы доступа, правило в `access.ts`;
   - поиск — не индексируется; экспорт — в личный архив автора; корзина — неразобранное через 30 дней автоматически в корзину (задание `worker`), дальше по общим правилам корзины;
   - содержимое: вид (фото, файл, текст, голос → текст), файлы (несколько страниц) существующим механизмом файлов, статус (новый, разбирается, черновик готов, ошибка, документ личности), черновик разбора — JSON по схеме из `packages/shared`.
2. **Захват (INBOX-1):** кнопка «Во входящие» на главном экране и в меню «Ещё»: камера или галерея (несколько страниц), файл, диктовка (как в D21) или текст. Без сети элемент ждёт в существующей офлайн-очереди клиента и уходит при появлении сети; не больше 10 МБ на элемент.
3. **Разбор (INBOX-2):** если ИИ в доме включён и у участника есть согласие (AI-3) — разбор в `worker` сразу после загрузки, с общим дневным пределом и общим сроком 120 с. Типы: дело, покупка, заметка, показание, начисление, документ объекта (DOC-1 «прочие», ОСАГО/КАСКО/СТС/ПТС/ЕГРН и т. п.), медицинский документ (анализы, заключения, назначения). Повторно используются разборы D25 (текст) и D26 (счётчик, квитанция, проверка документа личности); новый вид `document` — тип DOC-1, название, даты выдачи и окончания, владелец, ключевые поля.
4. **Документы личности (AI-4):** паспорт РФ и загранпаспорт, свидетельства о рождении и о браке, СНИЛС, ИНН, водительское удостоверение, полисы ОМС и ДМС. Перед любым извлечением — проверка D26 «да / нет / не уверен»; «да» или «не уверен» → статус «Документ личности — заполните вручную», ничего не извлекается, кнопка открывает обычную форму документа с приложенным фото. Тест: для таких образцов в ответе модели, черновике и журнале нет серии, номера, ФИО.
5. **Привязка (INBOX-3):** объект или человек — только из видимых автору (как контекст D25). Нет подходящего — карточка «Новый объект» с предложенными полями; создаёт человек обычным API.
6. **Решение (INBOX-4):** у элемента — «Сохранить как предложено», «Изменить» (обычная форма записи с заполненными полями), «Другой тип», «Удалить». Сохранение — только обычными API с обычными проверками; исходные файлы переходят к созданной записи; элемент исчезает из «Входящих». Неуверенные поля отмечены.
7. **Экран «Входящие»:** список новых сверху, статус разбора, счётчик «Входящие · N» на главном экране — только у автора. Без ИИ — элементы ждут ручного разбора («Другой тип» → обычная форма).

## Короткие инструкции и оценка

- Как в D25/D26: инструкция `inbox` (определение типа и привязка) и `document` — не больше ~600 знаков правил и 0–2 примеров каждая; каждая строка оправдана ростом `ai:eval`. В отчёте — длина в знаках.
- Образцы: 15–20 вымышленных элементов разных типов (фразы, синтетические договоры, гарантии, анализы, квитанции, показания) и 5 синтетических документов личности с явно вымышленными данными. Настоящие — только через `--samples <папка>` вне репозитория.
- Цели на Hermes: тип ≥ 90%, объект ≥ 85%, поля документа ≥ 85%; документы личности — 100% «заполните вручную», ни одного извлечённого поля.
- **Бережём подписку** (Hermes и Codex на одном ChatGPT Plus): не больше 5 полных прогонов `ai:eval` против Hermes на всю задачу; подбор инструкций — на подвыборке 10–15 образцов; при HTTP 429 или сообщении о лимите — остановиться и описать в отчёте. В CI — только `fake`.

**Готово, когда:** матрица доступа `inbox_items` (автор видит; второй взрослый, ребёнок и администратор — нет); автоочистка через 30 дней; экспорт; офлайн-захват; модульные тесты статусов, привязки только к видимому и запрета извлечения у документов личности; e2e «во входящие → разбор → сохранить как предложено», «Изменить → обычная форма», «документ личности → ручная форма», «новый объект» и офлайн-захват на 360 и 412 px с axe (поставщик `fake`); `ai:eval` — цели выше; `pnpm check` и CI без внешних служб.

**Общие правила:** вымышленная семья; секреты не выводить; новых зависимостей не нужно; коммиты `INBOX-1: …`; PR открыть, не сливать; отчёт — до 15 строк по шаблону `AGENTS.md`, с длиной инструкций, точностью и числом прогонов против Hermes.
