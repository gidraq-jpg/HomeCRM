# Бриф R0.6. Поиск

- **Задача:** R0.6 из [плана](../03-dev-plan.md) — единый поиск по видимым записям: индекс, API и экран поиска.
- **Требования:** SRCH-1…5, NOTE-3; PRD разделы 7.3 (правило 1: чужое личное не попадает в поиск, даже счётчиком), 13, 14 (поиск в шапке); [ADR-0011](../adr/0011-search-postgresql.md), [ADR-0004](../adr/0004-access-code-and-rls.md); решения о поиске в ADR-0020, 0023, 0024 (что из заметок, объектов, файлов идёт в поиск).
- **Ветка:** `feat/srch-1-search`, в своём worktree от свежего `main`. Параллельно Sonnet делает экраны фото профиля и корзины файлов (R0.5f, `apps/web/src/files`, `household`, корзина) — эти папки не трогать; экран поиска (`apps/web/src/screens/SearchScreen.tsx` и новая папка `apps/web/src/search`) — твой.

## Сделать

1. **Индекс** — таблица поискового индекса по ADR-0011: те же поля доступа, что у записей (пространство, вид, аудитория, владелец), RLS ENABLE + FORCE, политики, строки матрицы доступа; полнотекстовая часть с конфигурацией `russian` и `pg_trgm` для номеров, телефонов и частей слов. Индекс обновляется в той же транзакции, что и запись (триггеры): создание, правка, перенос между пространствами, смена аудитории, корзина, восстановление, очистка.
2. **Что индексируется сейчас:** заметки (заголовок, текст, пункты чек-листа), объекты (название, свои поля), ручные события ленты (текст) — каждое со своей видимостью (событие — по правилам ленты ADR-0023, не шире объекта). Имена файлов — по решению ADR-0024. Будущие модули добавляют свои строки тем же механизмом — описать в ADR (новый, номер 0027 или выше).
3. **API** `GET /api/search?q=…`: результаты сгруппированы по типам (SRCH-3), у каждого — тип, id, заголовок, фрагмент с совпадением, пространство («Общее · Вся семья», «Личное»…); пустой и слишком короткий запрос — понятный ответ; фильтр по переключателю «Всё · Общее · Личное». Чужие личные записи и записи «Взрослые» для ребёнка не влияют ни на результаты, ни на их число, ни на время ответа заметно.
4. **Экран поиска** (`SearchScreen`, поиск в шапке): поле, группы по типам, значок пространства, номер копируется из результата (SRCH-3), переход в карточку, пустое состояние и «ничего не найдено». Запрос не попадает в адрес страницы, localStorage и журналы сервера (PRD 13); история поиска — только в памяти страницы.
5. **Скорость (SRCH-5):** тест на 10 000 вымышленных записей — p95 до 300 мс; план запроса использует индексы (записать в отчёте).
6. **Бэклог:** пункты про поиск в выборе записи для связи (до 100 записей, R0.5c) — перевести выбор на поиск, если это укладывается в задачу; иначе оставить в бэклоге.

## Готово, когда

- Матрица доступа для индекса без расхождений; тесты: словоформы («счётчик» → «счётчика», «счётчики»), часть номера и телефона, перенос в личное убирает запись из поиска остальных, смена аудитории на «Взрослые» убирает её у ребёнка, корзина и восстановление, очистка; чужое личное не находится ни по слову, ни по номеру.
- Playwright на 360 и 412 px с axe для экрана поиска; скриншоты в `docs/screenshots/R0.6/`.
- Миграция безопасна для существующей базы и заполняет индекс по уже имеющимся записям; `pnpm check` и CI проходят.

## Не трогать

`apps/web/src/files`, `apps/web/src/household`, экран корзины (там R0.5f), `apps/server/src/auth`, `deploy`, рабочее окружение: compose-проект `homecrm`, порты 8300, 8301 и 8309, `E:\HomeCRM-data`. Сервер разработки — на своих портах (`PORT=8324`, `WEB_PORT=5187`).

Отчёт — по шаблону из `AGENTS.md`, в описании PR.
