# UI-8. Полная карта анимаций на тестовом стенде — второй проход

Задача владельца: применить согласованную в чате карту из 24 пунктов в текущем тестовом приложении. Это продолжение эксперимента; принятия в рабочую версию ещё нет.

База: локальный коммит 1bdec61, ветка feat/ui-8-motion-template-preview, текущий worktree homecrm-motion-template/HomeCRM.
Стенд сохраняется: WEB 5360, API 8500, PostgreSQL 15500, compose homecrm-test-motion-template, только вымышленная семья. Вход http://localhost:5360/api/demo/enter.

## Что исправляем

Предыдущий проход пропустил главное переключение лент: нажатие вкладки в TaskTabs всё ещё двигает всю карусель как свайп. Пользователь указал на расхождение. Новый проход должен закрыть полный перечень, а не только эту точку.

Сначала уточнить экспериментальные требования PRD UI-8 и ADR-0050; принятый ADR-0049 остаётся основой экранных переходов, листов и жестов. Текущая команда владельца разрешает экспериментально заменить сценарий нажатия вкладок на главной.

## Границы

- Основная область — apps/web/src и её проверки. Бизнес-логика, API, доступ, RLS, миграции и настоящие данные не меняются.
- Не трогать E:/Projects/HomeCRM main, рабочий compose homecrm, E:/HomeCRM-data и чужие стенды. Не перезаполнять текущую демонстрационную БД без необходимости.
- Сохранять текущие демонстрационные данные и оставлять стенд работающим после проверки.
- Push, PR, merge и выпуск не разрешены. Локальный коммит в текущей экспериментальной ветке после проверок.
- Данные, адрес, фокус и доступное состояние обновляются сразу. Уходящие слои inert/aria-hidden, без дублирующихся id. Одинаковое состояние не прерывает и не перезапускает движение.
- Прерывание продолжает видимое состояние, последнее действие побеждает. Старые callbacks не удаляют новый слой и не сбрасывают его высоту/позицию.
- При reduced-motion — только fast160 без сдвига, масштаба и очереди.
- Не складывать два движения на одной области (карусель + ContentMotion + useListMotion).
- Новых зависимостей избегать, большие списки не клонировать на каждом кадре.

## Готово, когда

1. У каждого из 24 пунктов есть статус в инвентаре: применено / подтверждено соответствие / конкретное обоснование неприменимости. Нет молча пропущенных экранов.
2. Главное нажатие вкладки визуально совпадает с назначенным сценарием; свайп продолжает работать за пальцем.
3. Есть кадровые/видео доказательства нажатия вперёд и назад, свайпа, заголовка/индикатора, фильтрации, перестановки и прерывания графика.
4. Проверены быстрые переключения, тот же ключ, частично общие строки, list→empty, отказ API/загрузка, фокус, история и восстановление места.
5. pnpm check:changed и meaningful regression tests зелёные. Linux Playwright 360/412, normal/reduced, axe, 44 px и отсутствие горизонтального переполнения — по изменённым сценариям. Снимки только Linux.
6. Одно независимое ревью изменения от 1bdec61. Исправляются блокеры, затем проверяются только исправления.
7. Обновлены бриф/ADR и ведомость проверок, русский UTF-8/LF проверен. Реальные ограничения указаны без заявления полного успеха по непроверенным сценариям.

### Доказательства и ограничения

- Linux-набор: motion-round2.e2e.ts (normal/reduced × 360/412), прежние motion-template/history/spatial/sheet/whole и целевой motion-polish API failure/undo.
- Сохранён первый каталог apps/web/test-results/motion-template-proof. Новые прогоны имеют собственные каталоги motion-round2-*, результаты и видео не коммитятся.
- Кадры: tab-forward-start.png, tab-rapid-exit.png, tab-back-incoming.png, swipe-follow.png, reorder-existing.png, chart-interrupted.png, submit-pending.png в каталогах соответствующего нового прогона.
- checkScreen проверяет axe serious/critical, 44px и горизонтальное переполнение и сохраняет Linux screens/360 либо screens/412/round2-*.
- Ревью от 1bdec61: исправляются только подтверждённые блокеры, проверка исправлений отдельная. Принятие физической PWA/Android predictive back остаётся за владельцем; выпуска/CI/PR/push нет.
- Поиск/контакты/организации/Inbox/месяц подключены по реальному коду. Сквозные проверки всех вариантов бизнес-данных этих экранов не заявляются: целевые UX-инварианты проверяются на делах/заметках/графике и сохранённых D44 сценариях.

- Проверка отказа формы использует HTTP400. При HTTP500 прежняя durable-очередь сохраняет intent и открывает экран очереди; это сохранённое поведение offline, а не подтверждение успешной записи сервером.
