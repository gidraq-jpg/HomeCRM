# Бриф R0.11b. Восстановление облачных копий и ожидание выпуска

- **Задача:** устранить отказ облачного хранилища, выявленный при выпуске v0.4.0, и сделать подготовку выпуска ограниченной по времени без преждевременной остановки работающего приложения.
- **Требования:** DATA-3/4, ADR-0015, ADR-0021; [runbook](../runbook.md), разделы 7 и 9.
- **Основа:** свежий `origin/main`; установленный код v0.4.0 — `f065fc6`.
- **Ветка:** `fix/data-3-cloud-backup`, собственный worktree. Не пересекаться с миграциями исполнителя R1c.5–6.
- **Область:** `apps/server/src/ops`, `deploy/scripts`, при доказанной необходимости `deploy/Dockerfile`/Compose, операционные тесты и документация. Не менять продуктовые API, RLS, матрицу доступа и данные семьи.

## Подтверждённые факты

1. Владельцем собран образ v0.4.0; `release.ps1` остановился через 300 секунд с `timeout waiting for dependencies`. Контейнер `migrate` продолжал работать.
2. Локальная копия перед миграцией сохранена. Её пробное восстановление с семью миграциями 0054–0060 прошло: 76 таблиц, 9785 строк, 3 файла, расхождений нет.
3. Облачная операция остановилась на `restic cat` примерно через 15 минут. Запуск владельца имел `BACKUP_PRE_MIGRATION_CLOUD=skip`, поэтому миграции применились после отказа облака.
4. Отдельный rclone в том же образе: `about` успешен, свободное место есть; скачивание только служебного `config` даёт `GoneError`. Отключение `--yandex-spoof-ua` не меняет результат. Это ещё не доказательство удаления файла, повреждения всего хранилища или ошибки авторизации.
5. Ведущий запустил готовый образ через `release.ps1 -Version v0.4.0 -NoBuild` с `required` в окружении этого процесса. Приложение, worker и backup работают, публичный `/health` успешен. Файлы секретов и окружения не редактировались.

## Выполнить

- Воспроизвести отказ коротким чтением служебного файла, ограниченным по времени. Выводить только этап, код HTTP/выхода и безопасный класс ошибки; не публиковать токены, подписанные ссылки, содержимое конфигурации, названия пользовательских файлов или полный stderr внешней программы.
- Установить, на каком этапе Яндекс отклоняет запрос. Проверить официальный код установленной версии rclone и актуальную документацию. Сначала подтвердить причину; не обновлять зависимости или менять хранилище наугад.
- Если решение требует входа владельца или восстановления утраченного объекта на стороне Яндекса, подготовить точное действие и остановить только зависимую часть. Не удалять, не инициализировать заново и не перезаписывать существующее облачное хранилище; локальная и облачная restic-конфигурации не взаимозаменяемы.
- Для необходимого изменения кода/скриптов добавить регрессию в подходящем операционном тесте: недоступное облако при `required` запрещает миграцию, зависший дочерний процесс завершается с безопасной ошибкой и не остаётся в фоне.
- Согласовать ожидание копии с ожиданием Compose. Увеличение 300 секунд само по себе не устраняет зависание. Сначала успешно подготовить копию и миграцию, затем пересоздавать приложение/worker/backup; не останавливать прежнее приложение из-за отказа предварительной подготовки.
- Работать с рабочими данными только через `deploy/scripts`, по разрешённому операционному действию. Исполнитель не выпускает исправление самостоятельно. Для реального изменения аккаунта/хранилища нужна команда владельца на конкретное действие.

## Готово, когда

1. Причина `GoneError` подтверждена; короткое чтение `config` и список снимков успешны либо точно описано необходимое внешнее действие владельца.
2. После разрешённого исправления свежая копия успешна в обоих хранилищах, пробное восстановление из облака проходит; неполный результат не объявляется готовым.
3. Отказ подготовки выпуска проверен на отдельном compose-проекте: без миграции и без остановки предыдущего приложения; ожидание ограничено, дочерние процессы очищены.
4. Нет обхода `required`, секретов в выводе и изменений реальных записей. Проверки затронутого кода и штатный `pnpm check` перед push зелёные; один PR и отчёт до 15 строк. Слияние и выпуск — ведущему.

## Промпт исполнителю

Выполни R0.11b по этому брифу. Прочитай `AGENTS.md`, PRD, план, ADR-0015/0021 и runbook. Работай в отдельном worktree от свежего `origin/main`, ветка `fix/data-3-cloud-backup`. Сначала воспроизведи короткую безопасную проверку облака и установи причину. Доведи необходимое исправление до одного PR с регрессией и зелёными проверками. Не пересоздавай хранилище, не обходи резервное копирование, не выпускай и не сливай самостоятельно. Если требуется действие владельца в Яндексе, сообщи точное действие и доказательство необходимости, продолжая независимую работу.
