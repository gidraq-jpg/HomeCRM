# Бриф R1b.4–5. Импорт vCard, дни рождения в радаре и долги API: база и API

- **Задача:** R1b.4 и R1b.5 из [плана](../03-dev-plan.md), серверная часть, одним PR; плюс долги API из [бэклога](../backlog.md), которых ждут экраны. Экраны — отдельной задачей.
- **Требования:** CONT-6, CONT-7; PRD 7.2, разделы 12 и 13; [ADR-0036](../adr/0036-passport-people-api.md), [ADR-0028](../adr/0028-deadline-engine.md), [ADR-0034](../adr/0034-templates-charges.md), [ADR-0035](../adr/0035-month-documents-api.md).
- **Ветка:** `feat/cont-6-vcard-birthdays`, в своём worktree от свежего `main`.

## Сделать

### R1b.4 Импорт vCard

1. **Разбор** (CONT-6): `POST /api/contacts/import` — файл `.vcf` (vCard 3.0 и 4.0, несколько карточек, кодировки UTF-8 и quoted-printable, фото пропускаются), граница и лимиты размера — проверка zod; ФИО, телефоны, e-mail, адрес, день рождения (в том числе без года), организация, заметка.
2. **Предпросмотр и объединение:** сначала ответ-предпросмотр без записи: новые контакты и совпадения по нормализованному телефону с видимыми контактами — с предложением «объединить» или «создать отдельно»; затем применение выбранного одним действием, в одной транзакции, с ключом идемпотентности. Объединение не перетирает непустые поля, а дополняет; история фиксирует импорт.
3. **Место:** по таблице PRD 7.2 (личные контакты — «Только я»), «Кто видит» — параметром; совпадения ищутся только среди видимых импортирующему.

### R1b.5 Дни рождения в радаре

4. **Источник `birthday`** (CONT-7): день рождения участника («Обо мне») и контакта-человека — ежегодный срок в движке сроков, если включено в карточке (флаг в контакте; для участника — в профиле). Предупреждения по умолчанию — за 7 и 1 день; 29 февраля — как в ADR-0036. Дата без года — срок без возраста.
5. **Доступ:** срок виден только тем, кто видит дату рождения (то же условие, что в паспортном правиле, `app.passport_birth_visible` — переиспользовать идею, не копировать); в push — имя только если не включено «Скрывать текст на экране блокировки».

### Долги API из бэклога

6. `complete-payment` возвращает `paymentId` созданной оплаты или `null`; радар отдаёт сумму и остаток начисления; создание начисления и оплаты принимает ключ идемпотентности.
7. `/api/utilities/month` отдаёт место и аудиторию объекта; карточка и список документов — названия объекта и контакта-владельца, файлы документа в карточке.
8. Радар сам ограничивает горизонт: 90 дней для обычных сроков, 365 — для документов и дней рождения с начавшимся предупреждением (клиент сейчас запрашивает 366 дней — оставить совместимость).

### Для каждой новой сущности и поля (AGENTS.md)

9. RLS ENABLE + FORCE, двойник в `access.ts`, строки матрицы, история, корзина, перенос, поиск, экспорт; в журналах нет ФИО, телефонов, дат рождения и содержимого файла; `redactUrl` знает новые маршруты.

## Готово, когда

- Тесты: файл vCard с тремя карточками (одна совпадает по телефону) → предпросмотр, объединение без потери полей, повтор с тем же ключом без дублей; битый файл — понятная ошибка, ничего не создано. День рождения в радаре с предупреждениями, без года, 29 февраля; ребёнок не видит день рождения контакта «Взрослых»; выключенный флаг убирает срок.
- Долги: `paymentId`, остаток в радаре, ключи идемпотентности, место в месяце, названия в документах — тестами API.
- Матрица доступа без расхождений; `GET /api/deadlines` — в пределах замера G4 с запасом (сейчас p95 до 299 мс при пороге 300 — не ухудшать, лучше улучшить).
- Миграции безопасны для рабочей базы (после 0049); ADR (0037 или выше); контракт API в `docs/`; `pnpm check` и CI проходят.
