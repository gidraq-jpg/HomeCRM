# Бриф R0.8. Ядро движка сроков

- **Задача:** R0.8 из [плана](../03-dev-plan.md) — общий движок сроков, на который встанут коммуналка (R1a.6, к окну показаний 20–25 ноября), документы, дела и радар (R1c.5).
- **Требования:** DEAD-1, DEAD-6; заготовка под DEAD-2…5; PRD разделы 7.3 (сроки видит тот, кто видит запись), 13 (даты «5 окт.», журналы); [ADR-0012](../adr/0012-time-and-dates.md), [ADR-0006](../adr/0006-pg-boss.md), [ADR-0004](../adr/0004-access-code-and-rls.md).
- **Ветка:** `feat/dead-1-engine`, в своём worktree от свежего `main`.

## Сделать

1. **Часовой пояс дома** — в таблице домов (название IANA), а не в настройке сервера `HOME_TIME_ZONE` (бэклог «Отчёт R0.3c»); отдаётся в `/api/me` по дому участника; смена — администратором. Значение по умолчанию для существующего дома — текущая настройка сервера.
2. **Правила сроков** (DEAD-1) — один формат для всех источников: дата; окно (с — по, со временем начала, например «20–25 число в 9:00»); повтор (ежемесячно в день N с переносом на последний день короткого месяца, ежегодно, каждые N дней или месяцев); «через N дней или месяцев после события»; предупреждения за N дней. Даты — тип `date`, моменты — `timestamptz`, расчёт — в часовом поясе дома (date-fns и @date-fns/tz). Схема правила — zod в `packages/shared`.
3. **Таблица сроков** — срок принадлежит записи-источнику (пока: объект и заметка; модули R1 добавят свои тем же механизмом) и наследует её место и аудиторию, как дочерняя запись (OBJ-5): поля доступа, RLS ENABLE + FORCE, политики, двойник в `access.ts`, строки матрицы, корзина и перенос вместе с родителем, решение о поиске и экспорте — в ADR (новый, номер 0028 или выше).
4. **Ближайшие наступления:** функция в `packages/shared`, которая по правилу и «сейчас» даёт ближайшие наступления и моменты предупреждений; фоновая задача pg-boss (роль `homecrm_worker`) раз в сутки и при изменении правила раскладывает наступления на 90 дней вперёд в отдельную таблицу с теми же правами. Обработчик — отдельный вход сервера (`worker`), как задумано в плане; в compose — сервис worker (рабочее окружение не включать).
5. **API:** создать, изменить, удалить в корзину срок записи; `GET /api/deadlines?from&to` — наступления видимых сроков с группами радара DEAD-3 («Просрочено», «Сейчас», «7 дней», «30 дней», «90 дней») по времени дома. Действия радара (DEAD-4) и закрытие пунктов (DEAD-5) — в R1c.5, здесь только место под отметку «выполнено» у наступления.
6. **Под уведомления (R0.7):** момент предупреждения создаёт строку «к отправке» (кому — по правилу 7.3.9 ответственному, только если он видит запись); саму отправку делает R0.7.

## Готово, когда

- Тесты расчёта при заданном часовом поясе: конец месяца (31 → 30, 28/29 февраля), високосный год, окно через полночь и через границу месяца, «через N после», смена часового пояса дома, сервер в другом поясе, повтор после выполнения.
- Матрица доступа для сроков и наступлений без расхождений; чужой личный срок не виден ни в списке, ни счётчиком групп; перенос записи в личное убирает её сроки у остальных.
- Миграция безопасна для существующей базы; `pnpm check` и CI проходят.
- В журналах нет названий записей и текстов сроков.

## Не трогать

`apps/web` (экраны сроков и радара — отдельной задачей), `apps/server/src/auth`, рабочее окружение: compose-проект `homecrm`, порты 8300, 8301 и 8309, `E:\HomeCRM-data`. В `deploy` — только сервис worker в compose.

Отчёт — по шаблону из `AGENTS.md`, в описании PR.
