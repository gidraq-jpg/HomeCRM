# Бриф R1a.1–3. Недвижимость, организации, лицевые счета: база и API

- **Задача:** R1a.1–R1a.3 из [плана](../03-dev-plan.md), серверная часть. Первый шаг этапа R1a: к окну показаний 20–25 ноября должны работать объекты, лицевые счета, счётчики, показания и напоминания. Экраны — отдельной задачей на готовом API.
- **Требования:** UTIL-1, UTIL-2, CONT-2, CONT-3, OBJ-5; PRD 7.2 (недвижимость и лицевые счета — общее, «Взрослые»; организации — общее, «Вся семья»), сценарий S1, разделы 12 и 13; [ADR-0023](../adr/0023-objects-links-timeline.md) (объекты, `recordTable`, `type_data`), [ADR-0028](../adr/0028-deadline-engine.md).
- **Ветка:** `feat/util-1-property-accounts`, в своём worktree от свежего `main` — после слияния R0.10.

## Сделать

1. **Недвижимость** — объект типа `property` с полями типа в `type_data`; схема — zod в `packages/shared`: вид (квартира, дом, дача или участок, гараж или машиноместо, нежилое помещение), адрес, площадь (без чисел с плавающей точкой: целые сотые м² или `numeric`), кадастровый номер с проверкой формата, статус («живём», «сдаётся», «пустует»). Собственники — участники дома или контакты; где хранить (связь OBJ-2 с ролью «собственник» или поле) — решить в ADR. API объектов принимает и отдаёт поля типа; поиск находит по адресу и кадастровому номеру.
2. **Организации** (CONT-2) — новая сущность `contacts` с видом «организация» сейчас и местом под «человека» (CONT-1, R1b.3): название, тип (УК или ТСЖ, ресурсоснабжающая, банк, страховая, школа, поликлиника, сервис, магазин, госорган, другое), телефоны с подписью и признаком «аварийный», сайт, адрес, часы работы, заметка. По умолчанию — общее, «Вся семья». Связь с объектом с подписью роли (CONT-3) — через существующие связи OBJ-2; в карточке объекта API отдаёт блок «Люди и организации».
3. **Лицевой счёт** (UTIL-2) — дочерняя запись объекта (OBJ-5, `parent: objects`): поставщик (организация), услуги (закрытый список из приложения А и «другое»), номер, способ передачи показаний (Госуслуги Дом, сайт или приложение поставщика со ссылкой, телефон, автоматически, не требуется), окно передачи (день с — по), день срока оплаты, кто платит (собственник, арендатор, другое), ссылка на личный кабинет, заметки. Окно и оплата хранятся в формате правил DEAD-1, чтобы R1a.6 подключил их к радару без переделки; сами сроки в радар здесь не выводить.
4. **Для каждой новой сущности** (AGENTS.md): поля доступа, RLS ENABLE + FORCE, двойник в `access.ts`, строки матрицы, история изменений, корзина и восстановление вместе с родителем, перенос вместе с объектом, решение о поиске, экспорт в модуле R0.10. Ребёнок не видит лицевые счета «Взрослых»; организация «Вся семья», связанная с объектом «Взрослые», видна ребёнку сама по себе, а связь — только тем, кто видит обе записи (OBJ-2).
5. **API:** создать, изменить, в корзину, восстановить — для организаций и лицевых счетов; список лицевых счетов объекта; список организаций с фильтром по типу. Ответы — без лишних полей для тех, кто не видит запись.

## Готово, когда

- Матрица доступа без расхождений для организаций, лицевых счетов и полей типа недвижимости; сквозные тесты на вымышленной семье: ребёнок, второй взрослый, администратор; перенос объекта уносит его лицевые счета.
- Тесты zod-схем: формат кадастрового номера, площадь без потери точности, окна через границу месяца в правилах DEAD-1.
- Миграции безопасны для рабочей базы с данными (объекты v0.1.0 остаются как были, `type_data` пустых объектов валиден); ADR (номер 0031 или выше; миграция — следующая после 0027) — собственники, контакты, лицевой счёт как дочерняя запись, поиск и экспорт.
- `pnpm check` и CI проходят; сценарий S1 (первая квартира с тремя лицевыми счетами) проходит через API.
