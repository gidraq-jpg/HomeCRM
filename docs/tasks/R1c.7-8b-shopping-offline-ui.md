## 1. Экран покупок

1. Реальный `/more/shopping`, вход из «Ещё» и добавления; общий список «Вся семья»/личный, выбранный дом и переключатель пространства. Быстрая строка, количество, заметка, магазин/категория, доступные связи с делом/объектом; ребёнок добавляет общее по серверным правам.
2. Куплено и отмена работают через API, купленное свёрнуто отдельно; статус очистки/корзины/восстановления соответствует серверу. Нет второго счётчика/локального списка, выдаваемого за серверный.
3. Загрузка, ошибка, пустое состояние, повтор после ошибки, недоступная запись/связь, conflict с сохранением ввода. Отложенный ответ A после смены на B не показывает прежнее личное. Количество, роль, пространство и доступ не определяются одной надписью UI.
4. Настоящий поиск: расширить строгую схему `search/api.ts`, иконку/название и безопасный путь результата в `search/Results.tsx` для `shopping_item`, отправлять `includeShopping=true`. Серверный opt-in нужен для совместимости старого клиента; проверить поиск личной/общей покупки, скрытую запись ребёнка и переход к настоящему экрану.

## 2. Чтение без сети

1. Собственный service worker остаётся `injectManifest`; Cache Storage — оболочка, IndexedDB/Dexie по ADR-0008 — ограниченные owner-scoped snapshots/drafts/outbox/blobs. Постоянная PostgreSQL остаётся истиной. Не кэшировать все GET/POST автоматически.
2. После успешного онлайн-чтения доступны «Сегодня», радар и последние открытые карточки с ранее доступными полями; покупки можно показывать из последнего снимка. Зафиксировать явную allowlist ответов карточек, лимиты по количеству/возрасту/байтам и обновление схемы. Карточка документа не означает загрузку PDF/секретного номера: файлы документов без сети относятся к R2.
   Содержимое и точная версия изменяемой записи должны быть получены согласованно одним снимком по контракту API. Нельзя позже прикрепить отдельно прочитанную новую версию к прежнему тексту. Старый снимок без точной версии пригоден для чтения, но не для автоматического обхода конфликта при записи.
3. Работают повторное открытие приложения/навигация офлайн, плашка «Нет сети», время снимка и понятное состояние отсутствующих данных. Последние сохранённые данные не называются актуальной серверной версией. Ошибка серверного доступа 401/403 не заменяется «успешным» офлайн-ответом.
4. В локальном хранилище нет паролей, токенов сессий/2FA, CSRF-секретов, ответов управления устройствами, ссылок приглашения/сброса или скрытых полей. Кэшированная идентичность — метка локальных данных, не разрешение синхронизации. Старт офлайн и истечение сессии различать в архитектуре явно.
5. Разделение минимум по аккаунту, дому/пространству и параметрам списка; active-account generation и защита поздних результатов. До сохранения snapshot проверить авторитетный accountId ответа против владельца запроса: cookie могла смениться в другой вкладке раньше broadcast. Смена пользователя/выход очищают или блокируют прежние snapshots/очередь/blobs сразу во всех вкладках и SW. Смена дома не переносит записанную операцию в другой дом.

## 3. Очередь изменений

1. Только фактическая allowlist `api-offline.md`: дела/чек-листы/выполнение, заметки/чек-листы, показания с фото. Неподдерживаемые действия имеют понятное требование сети; не расширять перечень автоматически на деньги, права и безопасность.
2. Перед показом «Сохранено на устройстве» операция и Blob атомарно записаны в IndexedDB; у неё стабильные account/id/request key, снимок версии, принадлежность дому, зависимости и состояние. Ошибка/quota IndexedDB не выдаётся за сохранение. Перезапуск, закрытие вкладки и повтор не теряют намерение или фото.
3. Различать «В очереди», «Отправляется», «Подтверждено», «Нужно решение», «Ошибка». Не считать запись серверной до квитанции. Локальное создание имеет устойчивый временный ID и безопасное сопоставление с серверным UUID; зависимые правки не отправляются на выдуманный серверный ID.
4. Повтор начинается только после свежего подтверждения аккаунта/дома/сессии сервером и по обычному безопасному API. Передавать обязательного владельца намерения по контракту; квитанцию проверить по аккаунту, ключу и виду операции. Cookie/CSRF не сохранять в IndexedDB. Новый аккаунт B никогда не отправляет очередь A; офлайн-ярлык старого `me` не годится для этого.
5. Порядок внутри одной записи и её зависимостей сохраняется. Один конфликт не останавливает независимые записи; зависимые приостанавливаются. Версию можно согласовать до первой отправки следующего намерения по точной квитанции предшественника; после неизвестного исхода payload/ключ не менять. Не подставлять текущую чужую версию, чтобы обойти 409.
6. Сеть flapping, потерянный ответ после COMMIT, две вкладки/окно+SW, перезапуск отправителя и повтор доставки имеют один эффект. Использовать согласованную блокировку/lease между отправителями, тайм-ауты и bounded backoff; `navigator.locks` не заменяет восстановление после аварии. Удалять операцию только после валидной подтверждённой квитанции.
7. 409 не успех. Показывать серверную версию/локальный ввод и варианты решения: обновить и осознанно применить новую правку либо отменить намерение. Ранее отправленное тело не переиспользуется с другим смыслом под старым ключом. 403/404 — отдельное понятное решение, 401 — остановка до правильного входа, 429 — Retry-After; локальное не теряется молча.
8. Фото хранится Blob, отправляется до показания по серверному протоколу и сохраняется до подтверждения всей зависимой операции. Следующее фото того же объекта получает точную базу из `receipt.parent.updatedAt` предыдущей загрузки; поздний replay не меняет её на чужую текущую версию. Ошибка прав/файла не приводит к фиктивному успеху показания. Проверить размер/квоту, правильного родителя, повтор multipart и возобновление после загрузки с потерянным ответом; утрата исходного фото/связи перед replay показания — явный отказ. Не писать бинарные файлы/семейные данные в репозиторий.
9. Офлайн-отмена ещё не отправленного выполнения отменяет локальное намерение; уже подтверждённое выполнение имеет существующее серверное окно 7 секунд. При неизвестном исходе сначала выяснить квитанцию, не придумывать успех отмены и не менять бизнес-правила серий.
10. Экран/панель очереди показывает pending/conflicts/errors и позволяет безопасно отменить либо повторить решение. Перед выходом при неотправленных изменениях — предупреждение и явный выбор; после выбранного выхода данные удалены по ADR-0008. Обновление SW/схемы базы не стирает pending или ещё редактируемую форму.

## Готово, когда

- Покупки работают на настоящем слитом API с вымышленной семьёй, личным/общим/ребёнком и двумя домами. Визуально соответствуют исходному прототипу, сохранены реальные действия и текущий каркас.
- Chromium/Service Worker/IndexedDB сквозные сценарии: онлайн → офлайн → reload/навигация → запись → reload → восстановление сети → один серверный эффект; выполнить для дела, заметки и показаний с настоящим фото.
- Проверены потерянный ответ после COMMIT, две вкладки, смена A→B и поздний ответ A, истекшая сессия, изменение прав/удаление, конфликт и независимая операция, цепочки create/edit/complete и photo/reading, отмена/выход с pending, quota и миграция локальной схемы.
- Linux Playwright по затронутым экранам на 360/412 px с axe/44 px/без горизонтального скролла; настольная ширина и длинные тексты. Скриншоты prototype/real + states только Linux, только вымышленная семья. Никаких новых скриншотных эталонов Windows.
- Во время работы — целевые проверки; обычный pre-push `pnpm check`, затем зелёный CI точного HEAD. Существующие сценарии входа/PWA/push/дел/показаний не ослаблены. Фактическую проверку Android/PWA/камеры/сети владельца не заменять Chromium.
- Обновлены `docs/shopping-offline-ui.md` (доказательства/лимиты/allowlist/конфликты), при необходимости ADR-0008 с новым решением, отчёт до 15 строк в одном прикреплённом PR и ведущему. Новый полный аудит не выполняется после исправления блокеров.
