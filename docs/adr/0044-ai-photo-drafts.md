# ADR-0044. Фото в проверяемые черновики

- **Статус:** принято для реализации D26, 25 октября 2026
- **Связано:** AI-2…AI-8, UTIL-4/5/9, ADR-0043

## Решение

Фото проходит JPEG-преобразование до 1600 px без метаданных; содержимое остаётся
в памяти запроса. Перед извлечением выполняется отдельная проверка документа
личности с единственным полем `identity: yes | no | unsure`. Да и сомнение
останавливают извлечение. Обе операции делят срок 120 секунд и один расход
дневного предела разбора. Отказ поставщика не возвращает расход.

Числа на табло модель возвращает строками. Разрядность проверяет сервер существующими
`meterUnits`/`meterDecimal`, не применяя арифметику с плавающей точкой. Несоответствие
становится пустым неуверенным полем. Результат заполняет обычную форму; сохранение,
проверки уменьшения/аномалии и приложение выбранного фото используют прежние API
и офлайн-очередь показаний. Отдельного временного хранилища фото нет.

Согласие общее для текста и фото, с версией, участником, домом и отпечатком поставщика.
Поля контекста зависят от операции: для табло — только параметры счётчика и прошлые
значения, для проверки личности — никаких записей приложения.

## Защита предела при FORCE RLS

Миграция 0068 сохраняет политики существующих пользовательских сущностей.
Приложение не получает UPDATE/DELETE счётчика. INSERT вызывает проверку членства,
включения ИИ и дня в поясе дома с правами вызывающего, затем закрытый триггер
владельца атомарно заменяет дневную строку числом `прежнее + 1` под блокировкой дня.
Это эквивалент защищённой функции расхода: прямой INSERT также проходит проверку
и не может уменьшить число. Доступ владельца к счётчику разрешён только внутри
триггера; доступа к пользовательским таблицам он не получает.

## Последствия

Проверка личности добавляет вызов модели, но исключает извлечение полей при сомнении.
Синтетические табло проверяются через `pnpm ai:eval --kind=meter`, проверка личности —
`--kind=identity`; CI использует только контракт fake. Качество настоящих фото и камера
телефона остаются отдельной проверкой владельца перед включением сценария.

## Квитанции

QR сначала читается на телефоне через BarcodeDetector. Если API отсутствует/ошибается,
используется jsQR 1.4.0: единственная новая зависимость, отдельный чанк 47,5 КБ gzip
в локальной сборке. Он отдаёт исходные байты: это позволяет прочитать Windows-1251
и KOI8-R, а не только UTF-8. [API jsQR](https://github.com/cozmo/jsqr) проверен через Context7.
`Sum` QR уже в копейках; напечатанные рубли модели переводятся сервером через BigInt.
Неполный QR оставляет известные поля, неизвестные заполняет человек. Без прочитанного
QR фото отправляется в ИИ только после включения и согласия.

Список счетов для подбора читает сервер под RLS участника; в модель уходят только
UUID и номера. Чужой UUID отбрасывается, одинаковые номера требуют выбора человека.
Форма явно показывает объект и счёт. Сохранение и загрузка выбранного по галочке
снимка идут через прежние API для выбранного объекта, включая счёт другого объекта.
До сохранения снимок остаётся только в памяти клиента; отдельного временного файла
или записи начисления нет.

## D27: личные входящие (решение владельца 25 октября 2026)

`inbox_items` и дочерние `inbox_files` — только личное пространство автора:
автор, ответственный и владелец пространства совпадают. Администратор не имеет
исключений. Проверки access.ts, RLS и матрица включают оба вида. Поиск их не индексирует;
личный экспорт содержит записи и расшифрованные страницы. Исходный захват до 10 МБ
фиксируется одной транзакцией существующей офлайн-очереди с устойчивой квитанцией.

После подтверждения захвата клиент вызывает `POST /api/inbox/:id/parse`.
Разбор выполняется синхронно в app под RLS автора, вне долгой транзакции базы;
кроме claim/сохранения результата транзакции короткие. При закрытом приложении
новое ждёт следующего открытия «Входящих»; есть кнопка «Разобрать». Повторный
одновременный запрос не расходует предел снова. Согласие проверяется по версии
и поставщику; 120 секунд общие для всех страниц, проверки личности и извлечения.
До первого извлечения каждая страница и текст отдельно проходят барьер D26.
Да/сомнение на любой странице оставляет только статус ручного заполнения.
Для дел/покупок/заметок повторно используется смешанный разбор D25, для показаний
и начислений — D26; новый документ ограничен типами без документов личности.
PDF сохраняется существующим файловым механизмом и заполняется вручную;
для автоматического разбора загружаются изображения страниц. Новых зависимостей нет.

Объект, человек и счётчик берутся из контекста, доступного автору. «Новый объект»
создаётся человеком обычным API. Решение создаёт записи обычными API и формами;
перенос файлов проверяет обычные права записи назначения. Видимость документа
выбирается по существующим правилам и показана до сохранения. Смешанный элемент
сохраняет все предложенные записи; файлы получает первая запись с вложениями.
У покупок вложений нет: до сохранения видно «Фото не сохранится». После успешного
подтверждения исходные страницы удаляются узкой политикой только новой таблицы;
блоки хранилища удаляются после COMMIT. При неизвестном исходе COMMIT сохраняются
для штатной уборки сирот (ADR-0025), чтобы не потерять единственную копию.

Worker выполняет только часовую очистку `inbox-cleanup`: узкий SELECT сроков,
UPDATE `deleted_at` только у неразобранного старше 30 дней, каскад страниц,
ещё 30 дней до удаления по общим правилам корзины. Содержимое, черновики, ключи
файлов и полномочия homecrm_app ему не выдаются; deploy не изменяется.
Восстановление начинает новый срок 30 дней. Политики существующих сущностей
не меняются; в общую защиту регистрируются только имена новых таблиц.
