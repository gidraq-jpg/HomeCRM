# ADR-0027. Производный поисковый индекс и доступ до совпадений

- **Статус:** принято, 7 октября 2026
- **Связано:** SRCH-1…5, NOTE-3, R0.6; ADR-0004, 0011, 0020, 0023, 0024

## Контекст

Поиск должен понимать русские словоформы, части слов, номеров и телефонов. Сужение доступа и корзина должны немедленно менять поиск. Ручное событие нельзя открыть шире его исторической аудитории. Скрытые совпадения не должны заметно менять время ответа.

## Решение

`search_index` — производная таблица без самостоятельного редактирования. Одна строка на заметку, пункт чек-листа, объект, своё поле или ручное событие. Поля доступа копируются из источника, владелец личного — из ответственного; для событий сохраняется также исходное место. В группах заметок и объектов пункты и поля показываются отдельными совпадениями с переходом к родительской карточке. Автоматическая история, файлы, имена файлов, OCR и PDF не индексируются (ADR-0024).

`AFTER INSERT OR UPDATE OR DELETE` обновляет индекс в той же транзакции. Корзина удаляет производную строку, восстановление создаёт её заново; переносы и смена аудитории проходят через существующие каскады. Физическая очистка удаляет индекс вместе с источником. Миграция заполняет индекс через `INSERT SELECT`, без изменения дат, истории и вкладов источников. Временное снятие FORCE с источников и временная политика владельца существуют только внутри транзакции миграции; по завершении FORCE восстановлен на всех таблицах.

Триггер `app.sync_search_entry` — узкий `SECURITY DEFINER`, владелец `homecrm_owner`, фиксированный пустой `search_path`. Он не читает источники, пользователей или файлы: пишет только строку индекса из `NEW/OLD` пяти зарегистрированных таблиц. Владелец получает политику индекса только при глубине триггера больше нуля; вне триггера не видит индекс. Вызов функции отозван у PUBLIC и всех runtime-ролей. Приложению выдан только SELECT, службе входа и обработчику — ничего. Это нужно, чтобы каскад мог обновить уже скрытую строку после сужения доступа, не выдавая приложению права подделать индекс.

RLS ENABLE + FORCE повторяет `canView`; событие дополнительно требует видимого живого объекта и `placement_visible` исходного места (ADR-0023). Сам текстовый предикат входит в ту же политику SELECT: PostgreSQL не использует индекс для не-LEAKPROOF операторов `@@` и `ILIKE`, вынесенных за отдельный барьер RLS. `setSearchQuery` задаёт строку, экранированный LIKE и нормализованный номер через `set_config(...,true)`: контекст ограничен текущей транзакцией. Поиск без этого контекста пуст. `%`, `_` и обратная косая черта — обычные символы запроса.

Проверка живого родителя вынесена в `app.search_parent_visible`, обычную `SECURITY INVOKER` функцию: она выполняет тот же EXISTS под RLS вызывающего. Фиксированный `search_path` предотвращает встраивание вложенных политик объекта в план общей выдачи. На время транзакции поиска отключается JIT: компиляция многочисленных вложенных политик при изменении статистики давала задержку выше полезного времени запроса. Ни правила доступа, ни RLS при этом не отключаются.

Для текста используется `to_tsvector('russian',content)`; `pg_trgm` индексирует текст и нормализованные цифры телефона. Составные GIN через доверенное расширение `btree_gin` содержат ключ места: UUID пространства плюс аудитория (или `personal`). API вычисляет разрешённые ключи из пространств под RLS и `canView` и передаёт их явно в запрос. Это дополнительное ограничение, оно не заменяет RLS. Оно позволяет отбирать места внутри GIN вместе с совпадениями, не сканируя скрытые документы. Приложение повторно проверяет текущую видимость возвращённых строк.

У трёх GIN отключён `fastupdate`: иначе общий pending list после массового добавления чужих записей читается при каждом поиске и сам создаёт задержку. Для семейного объёма более дорогая запись предпочтительнее такого влияния скрытых данных. Проверка скорости не делает VACUUM и не очищает pending list вручную.

`GET /api/search` принимает до 200 символов, ищет от трёх; пустой и короткий запрос возвращают состояния `empty`/`short`. Фильтр `scope` — `all`, `household`, `personal`. Ответ содержит группы, фрагменты, видимость и найденные номера для копирования. Возвращаются первые 150 совпадений; `hasMore` предлагает уточнить запрос, счётчик отражает показанные совпадения. Фрагменты отображаются текстом React, без вставки HTML. Адрес запроса полностью вырезается сериализатором журнала до `/api/search`; ответы API имеют `no-store`. Клиент хранит строку и результаты только в состоянии страницы, без URL, storage и QueryClient, отменяет устаревшие запросы при вводе и смене режима.

## Добавление модулей

Новый модуль добавляет явный тип источника, состав `content`, целевую карточку, закрытый триггер и заполнение существующих строк в миграции. Он обязан расширить матрицу поиска, проверку триггеров и API-группы; для дочерних сущностей — доказать, что доступ не шире родителя. Историческая аудитория добавляется отдельно, если модуль её сохраняет. Нельзя индексировать новый модуль автоматически через весь JSON записи: так в поиск могли бы попасть служебные данные или секреты.

Индекс отдельно не экспортируется: его содержимое уже входит в экспорт источников, а производные векторы и ключи доступа не пользовательские данные. После восстановления базы индекс восстанавливается из дампа вместе с источниками; при изменении алгоритма новая миграция пересобирает производные строки. Дополнительных сервисов и npm-зависимостей нет.

## Проверка и последствия

Матрица сравнивает строки индекса с `access.ts` для вымышленной семьи, двух домов и личных пространств; API проверяет историческую аудиторию событий, изменения доступа и жизненный цикл. Проверка обновления непустой базы сравнивает источники и историю до/после. Нагрузочный тест измеряет p95 полного API на 10 000 записей и разницу после добавления 10 000 чужих личных совпадений; EXPLAIN выполняется от `homecrm_app`, без отключения RLS и без принуждения плана.

Основания: [GIN и btree_gin](https://www.postgresql.org/docs/18/btree-gin.html), [буфер отложенных изменений GIN](https://www.postgresql.org/docs/18/gin.html), [барьеры безопасности и LEAKPROOF](https://www.postgresql.org/docs/18/rules-privileges.html), [pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html). Два доверенных расширения ставятся миграцией от владельца базы; отдельный суперпользователь для этого не нужен. [Результаты локального замера](../screenshots/R0.6/performance.md).
