# ADR-0005. Авторизация на Better Auth

- **Статус:** принято, 5 октября 2026; подтверждено проверкой 0.3 в тот же день
- **Связано:** план, T5; PRD AUTH-1…9, раздел 13; ADR-0004; код — `apps/server/src/auth`, `packages/db`

## Контекст

Сессии, второй фактор и хранение паролей опасно писать с нуля. Но правила дома нестандартные: вход детей без e-mail, администратор сбрасывает пароль только ребёнку, приглашения с ролью.

## Решение

**Берём Better Auth 1.7.7.** Проверка 0.3 прошла: все пункты работают, но шесть из них — только с небольшим своим кодом поверх библиотеки (таблица ниже). Версия закреплена точно; обновление — осознанное и только вместе с зелёным `pnpm check`.

Библиотека подключена так: таблицы — наши, в схеме `packages/db` (адаптер Drizzle); шесть функций и правил — плагин `homecrm`, который живёт в маршрутизаторе библиотеки, поэтому на нём действуют её CSRF, ограничение запросов и проверка сессии; ко всему, что библиотека делает с паролями и сессиями, добавлена четвёртая роль базы.

### Четвёртая роль базы: `homecrm_auth`

Библиотека не может работать под политиками «только своё» из ADR-0004: чтобы войти, надо найти учётную запись по имени и создать сессию, а чья это учётная запись — ещё неизвестно. Поэтому служба входа — отдельная роль:

- **`homecrm_auth`** — Better Auth, приглашения, сброс пароля. Видит таблицы входа (учётные записи, сессии, пароли, секреты второго фактора, приглашения) и состав домов; **ни одной таблицы данных семьи у неё нет**. Политики на таблицах входа — `true`: защищают права. Узкие условия там, где они возможны: приглашение она может лишь отметить принятым, и только живое (политика проверяет срок, отзыв и повтор); сброс пароля записывает только по правилу «администратор — ребёнку своего дома»; права на отдельные колонки не дают менять в строке ничего лишнего.
- **`homecrm_app`** — приложение: паролей, секретов, сессий и счётчиков не видит вовсе (42501). Видит только своё: журнал входов, отметку о сбросе, приглашения своего дома. Приглашает и отзывает администратор — проверяет политика базы, а не только код.
- Все таблицы входа — с `FORCE ROW LEVEL SECURITY`: владелец таблиц, как и везде, не видит ни одной строки.
- Правила `canInvite`, `canResetPassword`, `canViewAccountJournal`, `mustUseSecondFactor` — в `access.ts`, их SQL-двойники — в `access-sql.ts`. **Матрица правил входа** (`identity-matrix.test.ts`): 217 проверок «участник × дом × действие» без расхождений; участников семеро, в том числе Мила — ребёнок в одном доме и взрослая в другом. Семь испорченных политик матрица находит все (`identity-mutations.test.ts`).

Это не обход проверок доступа: роль служебная, данных семьи не касается, а всё, что она делает от имени участника (сброс, приглашение), проверяется и в коде, и политикой.

## Что нашла проверка

Находки тестов; каждая закрыта и закреплена тестом.

- **Login CSRF на входе по имени** — библиотека не защищает (см. выше).
- **Подбор пароля при смене пароля и подтверждении второго фактора** шёл без блокировки по учётной записи: теперь неверный пароль на этих путях считается попыткой.
- **Fastify писал токены в журнал**: на стандартный ответ 404 он пишет `Route GET:/invite/<токен> not found`. Теперь свой обработчик 404 и вырезание токена из адреса в журнале запросов; тест прогоняет все сценарии и ищет в журналах и пароли, и токены, и секрет библиотеки, и секреты TOTP.
- **Список устройств не открывался на сессии старше суток** (требование свежести) — `freshAge: 0`.
- **Адрес клиента библиотека берёт только из заголовка**, а без него все запросы делят одну корзину ограничения. Мост Fastify ставит свой заголовок из `request.ip` и затирает присланный; подмена `X-Forwarded-For` не помогает (тест).
- **Две копии `drizzle-orm`**: Better Auth приводит свою (peer `kysely`), и типы схемы с операторами из другой копии не сходятся. Сервер берёт операторы из `@homecrm/db` и своей зависимости от `drizzle-orm` не имеет; на выполнении копии живут вместе без проблем.
- **Лишние маршруты** (внешние поставщики входа, подтверждение и смена почты, самоудаление, проверка «свободно ли имя», страница ошибок) закрыты `disabledPaths`; маршрут с параметром `/callback/:id` — в мосту.

## Что библиотека не делает

- **Повтор кода TOTP.** В окне 30 секунд один и тот же код принимается дважды (RFC 6238, п. 5.2, требует отказ). Риск низкий: нужен ещё пароль. Тест `two-factor.test.ts` закрепляет это поведение и напомнит обновить запись, если библиотека его исправит.
- **«Доверять устройству».** После входа с кодом и отметкой устройство 30 дней входит без кода (по умолчанию в библиотеке). Для администратора это ослабляет AUTH-3 — решает владелец.
- **Блокировка по учётной записи** сообщает «заблокировано» только для существующих имён: можно перебором узнать, какие имена есть. Имена в семье не секрет; защита — пароль и второй фактор.
- **Сброс пароля администратором** позволяет ему войти как ребёнок, если у ребёнка нет второго фактора: PRD принимает это (отметка при следующем входе). Если у ребёнка включён TOTP, администратор не войдёт даже после сброса (тест).

## Последствия

- Меньше своего кода безопасности: сессии, шифрование секретов, сброс по ссылке, второй фактор, коды восстановления и ограничение запросов — библиотека. Обновления отслеживаются; тесты этого ADR — страховка.
- Новые зависимости — 22 пакета, все MIT (кроме `@opentelemetry/semantic-conventions`, Apache-2.0), без скриптов установки. Телеметрия выключена (`telemetry.enabled`); переменную `BETTER_AUTH_TELEMETRY` в окружении задавать нельзя.
- Секрет библиотеки (`BETTER_AUTH_SECRET`, не короче 32 символов, из файла окружения) шифрует секреты второго фактора и подписывает cookie. **Потеря секрета — потеря второго фактора у всех**: он входит в резервные копии секретов (runbook).
- Приложению нужны три подключения к базе: `homecrm_app`, `homecrm_auth`, `homecrm_worker` (R0.11).
- Cookie с `Secure` работает только по HTTPS или на `localhost` и `127.0.0.1`: на телефоне по `http://192.168.x.x` вход не заработает — нужен адрес с HTTPS (0.2, 0.6).
- За обратным прокси (туннель) Fastify нужен `trustProxy`, иначе адрес клиента — адрес прокси.
- Argon2id занимает ≈90 мс и 64 МиБ на проверку. Ограничение запросов не даёт устроить нагрузку подбором.
- В `main.ts` вход не подключён: нужны конфигурация и базы (R0.1). Первого администратора создаёт `provisionAccount` — для первой настройки нужна команда.
- Хранилища работают без очистки: просроченные сессии, одноразовые значения, счётчики адресов и журнал входов копятся — очистка в обработчике (бэклог).

## Отклонённые варианты

- **Своя реализация с нуля** — запасной вариант, если библиотека перестанет подходить. Готовы и останутся при любом исходе: Argon2id, приглашения, блокировки, журнал, правила и тесты. Пришлось бы дописывать сессии и cookie с продлением и отзывом, TOTP и коды восстановления (на проверенной библиотеке, без своей криптографии), сброс по ссылке, ограничение запросов и CSRF — порядка 500–700 строк (оценка).
- **Внешний поставщик входа** (Google, Яндекс) — зависимость от внешнего сервиса и неудобно для детей.
- **Плагин `organization` для приглашений** — приглашения только по e-mail, регистрация должна быть открыта.
- **Плагин `admin` для сброса пароля** — сбрасывает пароль любому и умеет «войти как пользователь», что нарушает AUTH-5 и «личное остаётся личным».
- **Argon2id из `@node-rs/argon2` или `argon2`** — внешняя сборка или платформенные бинарные пакеты; встроенный `node:crypto` не добавляет зависимостей. Если API встроенного Argon2 изменится, `@node-rs/argon2` подменяет `password.ts` без перехэширования: формат строки тот же (PHC).
- **Сессии в cookie без базы** — отозвать сессию потерянного телефона было бы нельзя.
