# ADR-0005. Авторизация на Better Auth

- **Статус:** предложено, 5 октября 2026; решение — по итогам проверки 0.3
- **Связано:** план, T5; PRD AUTH-1…9

## Контекст

Сессии, второй фактор и хранение паролей опасно писать с нуля. Но правила дома нестандартные: вход детей без e-mail, администратор сбрасывает пароль только ребёнку, приглашения с ролью.

## Решение

Берём Better Auth, если проверка 0.3 подтвердит все пункты:

| Что проверить | Требование |
|---|---|
| Вход по имени пользователя без e-mail | AUTH-1, AUTH-9 |
| Хэш паролей Argon2id. По умолчанию Better Auth использует scrypt, поэтому нужна своя функция хэширования на проверенной библиотеке | AUTH-1 |
| Приглашения с ролью, одноразовые, на 72 часа; открытая регистрация выключена | AUTH-2 |
| TOTP; обязателен для администратора | AUTH-3 |
| 10 одноразовых кодов восстановления | AUTH-4 |
| Сброс пароля: администратор — только ребёнку; ребёнок видит отметку о сбросе | AUTH-5 |
| Сессии до 90 дней с продлением; список устройств; «Выйти на всех устройствах» | AUTH-6 |
| Повторный ввод пароля для смены пароля, второго фактора и экспорта | AUTH-7 |
| Ограничение попыток, временная блокировка, журнал входов | AUTH-8 |
| Таблицы через адаптер Drizzle; cookie `Secure`, `HttpOnly`, `SameSite`; защита от CSRF | PRD, раздел 13 |

Своё поверх библиотеки: приглашения и роли в доме, правило сброса пароля, журнал входов — если библиотека его не даёт.

## Последствия

- При положительной проверке — меньше своего кода безопасности; обновления библиотеки отслеживаются.
- Таблицы Better Auth получают политики RLS по общим правилам (ADR-0004).

## Отклонённые варианты

- **Своя реализация с нуля** — остаётся запасным вариантом, если проверка не пройдёт: только на проверенных библиотеках для Argon2id и TOTP, без своей криптографии.
- **Внешний поставщик входа** (Google, Яндекс) — зависимость от внешнего сервиса и неудобно для детей.
