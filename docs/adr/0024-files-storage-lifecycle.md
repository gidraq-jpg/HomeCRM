# ADR-0024. Файлы записей: жизненный цикл, поиск и экспорт

- **Статус:** принято, R0.5b, 7 октября 2026
- **Связано:** OBJ-4, OBJ-5, SPACE-7, DATA-1, ADR-0010, ADR-0004

## Решение

Файлы заметок и объектов — `note_files` и `object_files`, дочерние таблицы `recordTable` с отложенными FK на место и аудиторию родителя. Аудитория совпадает с родителем. RLS, FORCE, корзина, история, перенос и матрица повторно используют общий механизм. Прямой SQL не может подменить содержимое, родителя, ключи и конверты. Файлы автора и добавление/отдельное удаление другим участником учитываются при переносе в личное; каскад корзины сам по себе вкладом не считается.

Диск содержит только блоки со случайными UUID. Каждый блок и каждый WebP-превью шифруются отдельным AES-256-GCM ключом, обёрнутым главным ключом с номером. AAD связывает блок, конверт и storage key. Имена, размеры, типы и конверты — только в базе; конверты и storage keys исключены из пользовательской истории. Приложение не отдаёт их клиенту. Тестовые ключи создаются только тестами. Главный ключ — отдельный файл секрета, обязательный при запуске; автоматической смены номера пока нет.

Загрузка проверяет сигнатуру через `file-type`, затем декодирует и перекодирует фото через sharp без метаданных. HEIC декодирует `heic-decode`/libheif (штатная поставка sharp не включает HEVC); размеры проверяются до выделения RGBA, предел 40 млн пикселей. Основное изображение HEIC сохраняется JPEG. JPEG, PNG и WebP сохраняют формат. Превью — WebP до 480×480. PDF сохраняется исходным и выдаётся вложением, без превью. Предел входа и сохранённого файла — 25 МиБ. Подмена заголовка/расширения не меняет определённый формат; HTML, SVG и прочие типы отклоняются.

Сервис хранилища имеет операции положить/взять/удалить; итерация старых ключей нужна только обслуживанию. При откате, включая ошибку COMMIT, написанные блоки удаляются компенсирующей операцией. `file_blobs` содержит только UUID действующих блоков; его меняют триггеры файлов, а обработчик читает реестр без пользовательских метаданных. При физическом удалении файла ссылка из реестра исчезает в той же транзакции. Каждый час и при старте worker физически удаляет файлы после 30 дней корзины, затем сверяет блоки старше часа с реестром и удаляет отсутствующие. Advisory lock storage key сериализует очистку с записью блока; общая блокировка GC сериализует очистку со staging копии. Сбой компенсации оставляет блок для этой сверки и возвращает ошибку, а не успех.

Копия родителя получает новые UUID файлов, storage keys и ключи шифрования; независимо восстанавливается и очищается. Список теряющих доступ совпадает с родителем, поскольку файлы строго наследуют его аудиторию. Выдача проверяет файл и родителя в транзакции участника; скрытый и отсутствующий id дают одинаковый 404. Ответы маршрутов файлов, включая ошибки, имеют no-store/nosniff; основной файл — attachment с безопасным именем. Публичных ссылок нет.

`photoFileId` профиля принимает только свой живой файл изображения при живом родителе, через триггер с правами вызывающего. При последующей смене аудитории или очистке ссылка не даёт обхода доступа: выдача снова проверяет родителя. Семейный профиль не расширяет аудиторию приватного изображения: при чтении скрытый или удалённый UUID маскируется `null`, сама ссылка в базе сохраняется.

## Поиск и экспорт R0.10

Имя файла **не включается в общий поиск**: он ищет родительскую карточку по её содержимому; OCR и содержимое PDF не индексируются. Это явное решение для R0; поиск по имени — отдельное продуктовое изменение.

Экспорт R0.10 должен включать манифест метаданных и расшифрованные файлы только для своего личного и общего администрируемых домов, после повторной проверки родителя под RLS. Имена в архиве строятся из UUID файла и безопасного имени, без storage keys и конвертов. Отдельный `exportFiles` готовит такой перечень и читает содержимое тем же сервисом выдачи. В существующий маршрут auth/export бинарный архив не подключается: это область R0.10. Файлы в корзине включаются с отметкой. Главный ключ не экспортируется. Архив содержит открытые данные и создаётся только по явному действию владельца.

## Копии и последствия

Том `/data/files` уже подключён в compose. Добавлено монтирование главного ключа только приложению. Снимок restic версии 2 содержит дамп, манифест и staging `files/`: реестр обязательных блоков читается из того же DB snapshot, затем каждый блок проверяется после staging. Отсутствующий/нечитаемый действующий блок делает копию неуспешной. Снимки версии 1 продолжают восстанавливаться из прежнего расположения. Главный ключ владелец хранит вне компьютера вместе с паролем restic; в restic его нет.

Зависимости: `@fastify/multipart` ограничивает загрузку в потоке, `file-type` определяет бинарный формат, `sharp` удаляет метаданные и строит превью, `heic-decode` даёт переносимую поддержку HEVC/HEIC без установки системного libvips. API сверены с [sharp](https://sharp.pixelplumbing.com/api-output/), [multipart](https://github.com/fastify/fastify-multipart) и [heic-decode](https://github.com/catdad-experiments/heic-decode). HEIC декодируется синхронной частью библиотеки; для большого параллельного потока понадобится отдельный worker-пул. Сейчас пределы входа/пикселей ограничивают обработку семейного приложения.
