# ADR-0031. Недвижимость, организации и дочерние лицевые счета

- **Статус:** принято; 8 октября 2026
- **Связано:** UTIL-1, UTIL-2, CONT-2, CONT-3, OBJ-5, R1a.1–3; ADR-0023, ADR-0028, ADR-0030.

## Решение

Недвижимость остаётся объектом `property`. `PropertyData` проверяет `type_data`: вид, адрес, статус, кадастровый номер и целые сотые квадратного метра `areaHundredths`. Все поля необязательны: существующие `{}` и создание только с названием валидны. PATCH заменяет поля типа целиком; смена типа на другой очищает их. Копия сохраняет поля типа. Содержательная правка типа или его полей другим участником считается вкладом, как правка названия.

Собственники-участники — массив `ownerMemberIds` в полях недвижимости. API принимает только собственную учётную запись и участников доступного дома; для общего объекта — его дома. Уход участника не стирает сведения о собственности, как не стирает авторство. Собственники-контакты — обычные связи OBJ-2 с ролью «собственник». Контактные id не дублируются внутри JSON и истории объекта: скрытый контакт не раскрывается после переноса объекта. Каталог контактов сейчас принимает организации, вид `person` и его поля вводятся отдельной задачей R1b.3.

`contacts` — самостоятельная таблица записей `recordTable`, вид `organization`, название в `title`, остальные поля CONT-2 — в проверяемом `data`. Вид организации и услуги — закрытые списки общих схем. По умолчанию организация создаётся в общем пространстве первого по UUID доступного дома с аудиторией «Вся семья»; без дома — в личном. Для объектов сохраняется прежний контракт: отсутствие `placement` означает личное, в том числе при передаче полей недвижимости. Клиент уже выбирает общее «Взрослые» по таблице 7.2 PRD и передаёт место явно; его выбор «Только я» нельзя превращать в общее. При явно указанном общем месте недвижимости без аудитории API использует «Взрослые». Явная аудитория имеет приоритет. Связи с организациями используют OBJ-2, карточка объекта содержит `peopleAndOrganizations` только с живыми видимыми контактами и связями.

`utility_accounts` — дочерняя таблица `recordTable` с `parent: objects`. Место, аудитория, перенос, корзина и восстановление наследуются от объекта через отложенные составные FK и триггеры. Отдельная корзина сохраняется при восстановлении объекта; счета другого автора, удалённые каскадом, восстанавливаются с объектом. Правки и добавления чужих счетов необратимо отмечают вклад в родителя. Копия объекта включает живые счета с новыми id и автором. Самостоятельный перенос счёта между объектами запрещён. Ответственный при создании — автор по общей модели, при переносе в личное — владелец.

Поставщик — необязательный FK `supplier_id` на организацию. Назначение требует видимой живой организации, в API и в SQL-триггере; разделяемая advisory-блокировка согласуется с очисткой контакта. API выдаёт поставщика только под RLS контакта, иначе `supplier` и `supplierId` равны `null`. История фиксирует смену поставщика признаком `supplier_changed`, без прежнего id. Окончательная очистка организации обнуляет FK, включая счета в корзине, не меняя содержимое и время записи. Узкое исключение в триггерах допускает только такое вложенное обнуление; обхода доступа приложения нет. Копия не сохраняет скрытого поставщика или поставщика в корзине.

Окно показаний и срок оплаты хранятся в `data` как правила DEAD-1. Для ежемесячного повтора добавлен необязательный `repeat.endDay`: при окончании раньше дня начала конец относится к следующему месяцу, иначе — к тому же. В коротком месяце дни ограничиваются последним числом. Так окно 28–5 не зависит от длины месяца и не требует фиксированного количества суток. `endDay` определяет календарную дату окончания вместо `durationDays`; API лицевых счетов требует нулевой `durationDays` при `endDay`. Оплата — ежемесячная дата без окна. Якорь и предупреждения остаются в общем формате. Наступления и сроки в радар не создаются: подключение источников — R1a.6.

## Поиск и экспорт

Поиск объекта индексирует название, адрес и кадастровый номер под его прежним RLS. Обновлён только вычисляемый `search_text` и производный триггер поиска, содержимое и история старых объектов не переписываются. Организации пока находятся через свой список с фильтром типа; отдельные поисковые результаты контактов вводятся вместе с их экранами. Лицевые счета пока находятся через карточку объекта; отдельной выдачи номеров в общем поиске нет. Это исключает переходы к ещё отсутствующим экранам. Поля организаций и номера счетов остаются первичными данными и входят в экспорт.

ZIP версии 1 дополнен `contacts.json`, `utility_accounts.json` и их строками в `history.json`, включая корзину. Новые виды проверяются строгими общими схемами и входят в счётчики манифеста. Поля недвижимости уже входят в `objects.json`. Личное — только своё, общее — администратору выбранного дома, под RLS и историческими снимками. В общем архиве ссылка на личного или другого недоступного поставщика — `null`, его id нет и в истории. Контактные собственники и роли организаций экспортируются видимыми связями OBJ-2. Прежние JSON API не заменяют ZIP и сохраняют свои контракты.

## Миграция и проверки

0028 создаёт только новые таблицы и истории, включает ENABLE/FORCE RLS и стандартные права, расширяет существующие функции жизненного цикла. Пересоздаётся только вычисляемая колонка поиска с возвратом её прав; для пустого `type_data` значение сохраняется. Нет удаления пользовательских данных, переписывания истории или автоматического создания счетов у старых объектов. Обновление с 0027 проверяется на заполненной отдельной базе. Выпуск и применение к рабочей базе выполняются отдельно владельцем.

Новые сущности входят в общую матрицу `access.ts` ↔ SQL, матрицу связей, проверки прав и каталога. Дополнительно проверяются поля недвижимости, приватность поставщика, очистка FK, вклад, перенос, самостоятельная корзина и каскадное восстановление. Сквозной API-тест S1 создаёт квартиру, организацию и три счета с проверками для ребёнка, взрослого и администратора. Временные ZIP используют префикс с id процесса: проверка очистки не захватывает каталоги параллельных прогонов. Регрессионный тест одновременно оставляет чужой каталог и проверяет удаление своего после ошибки дешифрования. Новых зависимостей нет.
