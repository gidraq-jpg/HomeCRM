# ADR-0041. Покупки и точные квитанции ограниченной очереди

- **Статус:** принято для R1c.7–8a, 12 октября 2026
- **Связано:** SHOP-1…3, PRD13, NOTE-1…3, TASK-4/6/8/10, UTIL; ADR-0004/0008/0010/0012/0024/0038/0039

## Решение

Используем shopping_items/record_links и прежний доступ, без новых списков. Новая data хранит
note/store/category, входит во вклад, штатный GIN и ZIP. Поиск покупок включается явно
includeShopping=true: прежний клиент имеет строгий enum групп. Исключение по умолчанию
действует до LIMIT/счётчиков; RLS одинакова.

Расширяем прежнюю api_operations nullable metadata-квитанцией. Ключи/хэши/UUID старых
операций сохранены. Новой сущности пользовательского контента нет; RLS квитанции по аккаунту,
SELECT/INSERT приложения, без UPDATE/DELETE/worker/auth. Квитанции не ищутся, не входят в
пользовательский ZIP/корзину и не содержат текстов, сумм, файлов, конвертов или секретов.
Срок очистки квитанций не вводим. Правила доступа результата повторно проверяются при replay.

Версии результата на момент COMMIT фиксируются точно в PostgreSQL ISO-формате, не Date с
миллисекундами. Доступная текущая карточка — отдельно от неизменной квитанции. Очередь
обозначается offline:true; legacy idempotencyKey не меняет сетевой контракт версий/ответов.
Владелец намерения ownerAccountId обязателен только в очереди и сравнивается с текущим
аккаунтом до записи/ключа; multipart использует X-Owner-Account-Id. Receipt включает owner,
а snapshot — авторитетный accountId для проверки поздних ответов после смены общей cookie.
Снимки GET?offline=true читают данные и версии одной REPEATABLE READ транзакцией и
возвращают wrapper. Старые GET прежние. Любая содержательная правка note_items касается
версии notes под существующей блокировкой; история не получает пустых событий.
Read-only радар/покупки/документы/контакты/счета используют тот же accountId-wrapper без
editable-версий. Список путей закрыт; бинарные файлы, unmask и безопасность исключены.

Фото использует прежний multipart/lifecycle с key в заголовке и hash исходных байтов/родителя.
Неизвестный исход COMMIT оставляет блоки для штатной сверки и повторяется тем же ключом.
Офлайн-квитанция фото сохраняет точный `parent:{id,updatedAt}` после собственного вклада:
несколько зависимых фото используют эту базу, а поздний replay не подставляет чужую свежую
версию. Replay показаний проверяет исходные photoIds, родителя, текущий доступ и живые
reading_photo-связи; удалённое вложение не превращается в успешный ответ с пустым списком.
Показания поддерживают одиночную и прежнюю атомарную пачку с observed meter version и UUID
последнего отсчёта. Значения/даты/предупреждения/авторство не подменяются клиентской меткой.

Worker-уборка покупок — SECURITY INVOKER, отдельные RLS политики только просроченного boughtAt,
SELECT служебного boughtAt и UPDATE deletedAt. Дополнительный guard запрещает иные изменения
при уборке. История пишет системный actor=null. Физическое удаление остаётся спустя 30 дней
корзины. Restore снимает boughtAt после штатного восстановления в той же транзакции.

## Последствия

Клиент 8b должен использовать точные снимки, переписывать локальные UUID пунктов/записей по
receipt и сохранять ключ/байты до известного исхода. Нельзя считать 409 успехом, начинать
новый batch после потерянного ACK или присваивать старому кэшу отдельно полученную версию.
Финансы, права и безопасность остаются online. Семь секунд отмены выполнения не расширены.
Новых зависимостей и второй очереди событий/общего bulk-механизма нет.
