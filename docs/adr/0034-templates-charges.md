# ADR-0034. Шаблоны, начисления и оплаты

- **Статус:** принято для R1a.7–8; 8 октября 2026.
- **Связано:** TPL-1…3, UTIL-9/10, DEAD-2/5; ADR-0031…0033.

## Шаблоны

Каталог трёх шаблонов хранится в `packages/shared/src/templates.ts`. Клиент передаёт только выбранные пункты; пустые массивы означают снятые галочки. Название объекта обязательно, остальные поля необязательны. Для общего объекта аудитория по умолчанию «Взрослые», организации-заготовки — «Вся семья» без выдуманных телефонов. Явное личное место сохраняется. Снятый счёт не создаётся ради выбранного счётчика: прибор остаётся без связи со счётом. Налоговый режим сдаваемой квартиры выбирается явно. Годовой день ТО газа — предложение, его можно заменить правилом из договора. Услуги и ТО можно независимо исключить.

Одна транзакция создаёт объект, выбранное дерево и техническую квитанцию `template_applications`. Advisory-блокировка по участнику и ключу сериализует повторы. Хэш нормализованного запроса выявляет повтор ключа с другим содержимым (409). Квитанция содержит только хэш и UUID объекта, видна только своему участнику под ENABLE/FORCE RLS. При окончательной очистке объекта ссылка становится `null`, квитанция сохраняется: старый ключ не создаст объект повторно. Ответ содержит UUID; актуальное содержимое читается обычным API под RLS.

`GET /api/onboarding` возвращает пустоту общего пространства для действующих администраторов. Чужое личное для определения пустоты не читается. Дом, часовой пояс и приглашения используют существующие API.

Повторы налога, ТО газа, показаний арендатора и НПД/НДФЛ пока создаются обычными сроками объекта с `label`. Налог на имущество: 1 декабря, предупреждения за 30 и 11 дней (1 и 20 ноября), в 09:00 дома. В R1c каждый такой срок станет сроком повторяющегося дела: новая миграция создаст дело, сохранит правило и UUID наступлений/доставок, переключит источник. Повторное применение шаблона для этой миграции не используется. До R1c эти записи показываются в радаре с понятным названием и редактируются API сроков.

## Деньги и доступ

`utility_charges` — дети лицевого счёта, `utility_payments` — дети начисления. Обе таблицы используют `recordTable`, ENABLE/FORCE RLS, историю (в том числе личных денежных записей, чтобы отмена всегда оставляла след) и общую матрицу `access.ts` ↔ SQL. Вложенные FK удерживают место и аудиторию; перенос объекта каскадно переносит всё дерево. Вклад другого участника отмечается также у счёта и объекта. Восстановление возвращает только записи, удалённые каскадом вместе с родителем.

Денежные записи самостоятельно не отправляются в корзину: используются необратимая отмена, причина и история. Корзина и очистка доступны вместе с родителем по общим правилам. Сумма, дата, плательщик и способ оплаты после создания неизменяемы: ошибочную оплату отменяют и вводят новую. Начисление с действующими оплатами сначала требует их отмены. Повтор отмены сохраняет исходную причину и время. Финансовые данные вводятся явными полями, без дат или сумм по умолчанию в БД.

Все суммы — целые копейки, в PostgreSQL `bigint`, на HTTP — целые числа. Предел отдельной суммы 10¹² копеек; сложение и сравнение выполняются через `bigint`, выдача проверяет безопасный диапазон JavaScript. Строки начисления необязательны; если заданы, их точная сумма обязана совпасть с итогом. Перерасчёт — отдельная строка `adjustment` с положительной или отрицательной суммой. Итог неотрицателен. Срок по умолчанию — день `paymentRule` в следующем после расчётного месяце, с ограничением последним числом короткого месяца. Без правила нужен явный срок.

Квитанция и чек — обычные зашифрованные файлы объекта R0.5, связанные через `record_links` с ролью `receipt`. API принимает только живой видимый файл того же объекта. Его самостоятельная корзина скрывает файл из ответа, восстановление возвращает ссылку. Никакого нового хранения файлов нет.

## Срок оплаты

Срок начисления использует `source_kind=payment`, FK `charge_id` и тот же объект как границу доступа. Наступление счёта на следующий после расчётного месяца подавляется при наличии действующего начисления за этот период, даже если явный срок начисления отличается от дня счёта. Другие месяцы и исторические ручные отметки счёта сохраняются. Отмена начисления возвращает напоминание счёта.

Сумма действующих оплат без корзины сравнивается с итогом; производный `is_paid` пересчитывается триггером. Самостоятельная правка признака запрещена. Нулевой итог сразу закрыт. Радар, очередь и отправка проверяют закрытие по одной семантике; отмена оплаты снова открывает срок без потери UUID наступления. Worker видит только служебные поля закрытия и периода; суммы, строки, плательщик и названия ему не выданы. Просроченное начисление, введённое сегодня, всё равно появляется в радаре.

«Отметить оплату» создаёт оплату на остаток текущей датой дома, от текущего участника, способом `card`. Объект и начисление блокируются, поэтому параллельный повтор не создаёт дубль. Для изменения способа следует использовать явное добавление оплаты. Обратная отметка отвечает `CANCEL_PAYMENT_WITH_REASON`: отмена денежной записи требует причины. Старое наступление счёта также направляет к начислению за его расчётный месяц. Если таких начислений несколько, возвращается `SELECT_CHARGE`.

## Поиск, экспорт и обновление

Начисления и оплаты находятся через лицевой счёт и начисление; отдельных результатов общего поиска до экранов финансов нет. Суммы и реквизиты в индекс не добавляются. ZIP версии 1 дополнен `utility_charges.json`, `utility_payments.json` и историей, включая отменённые записи и корзину. Квитанции входят существующим экспортом файлов и связей. `is_paid` — производный, в ZIP не входит; `charge_id` и подписи обычных сроков входят.

Миграции 0036–0037 после 0035 создают новые таблицы, дополняют ссылки сроков и расширяют функции жизненного цикла. Старые записи, история, UUID наступлений, ручные отметки и настройки не переписываются. Проверка обновления выполняется на отдельной заполненной базе с 0035. Новых зависимостей нет. Клиент, выпуск и рабочая база в задачу не входят.
