# ADR-0047. Копии на Яндекс Диск через WebDAV вместо REST API

- **Статус:** принято, 28 октября 2026; дополняет [ADR-0021](0021-operations-backups.md) (второе место копий) и [ADR-0014](0014-backups-restic.md)
- **Связано:** PRD DATA-3, раздел 13 (журналы); задача D29; [rclone #10067](https://github.com/rclone/rclone/issues/10067)

## Контекст

С 11 октября 2026 REST API Яндекс Диска отвечает `410 Gone` на любой путь для rclone-бэкенда `yandex`; запрос `about` работает, вход действителен. Облачная копия не делается с 13 октября, v0.5.8-pilot.1 выпущен с пропуском облака по команде владельца. В журнале было только `restic failed at cat`: причина не видна ни владельцу, ни агенту, а restic по умолчанию повторяет запросы к хранилищу до 15 минут.

## Решение

- **Бэкенд rclone `webdav`:** `url = https://webdav.yandex.ru`, `vendor = other`, логин Яндекса и **пароль приложения** Яндекс ID с типом «Файлы / WebDAV». Подключение по умолчанию называется `yadisk-webdav`, адрес хранилища — `rclone:yadisk-webdav:HomeCRM-backups`. Папка та же, что у REST API, поэтому прежние снимки снова доступны: restic хранит в ней обычные файлы, способ доступа к ним не важен.
- **`connect-yandex-disk.ps1 -WebDav`** спрашивает логин и пароль приложения в консоли владельца (пароль — скрытым вводом), шифрует пароль `rclone obscure -` через стандартный ввод и сам дописывает секцию в `secrets\rclone\rclone.conf`. Бриф предлагал `rclone config create … --obscure`; от него отказались, потому что пароль оказался бы в аргументах процесса. Затем скрипт создаёт и читает папку (`rclone mkdir`, `rclone lsf`), пишет адрес в `secrets\backup.env`, проверяет путь restic → rclone → WebDAV (`cli.ts cloud-check`) и пересоздаёт запущенное расписание копий на том же образе, чтобы оно взяло новый адрес. При неудаче `rclone.conf` и `backup.env` возвращаются прежними. Прежнее подключение `yadisk` (REST API) удаляется только после успеха: его токен открывает весь Диск, а работать он перестал.
- **`--yandex-hard-delete` передаётся только бэкенду `yandex`.** Тип подключения `restic.ts` берёт из строки `type` нужной секции `rclone.conf`; остальные строки (логин, пароль, токен) не читаются дальше этой функции.
- **Причина сбоя облака без вывода программ.** По stderr restic и rclone выбирается одна из своих фраз: `HTTP 401: login or app password rejected`, `HTTP 403`, `HTTP 410: Yandex Disk REST API is gone, use WebDAV`, `HTTP 507: cloud storage is full`, `HTTP 429`, `network error: cloud is unreachable`. Сам вывод в журнал и статус не попадает (PRD, раздел 13). Пример: `restic failed at cat (exit code 1): HTTP 401: login or app password rejected`. `backup-status.ps1` переводит причину в понятный совет по-русски.
- **Свой тайм-аут служебных команд облака** (`cat`, `snapshots`, `init` — `BACKUP_CLOUD_COMMAND_TIMEOUT_SECONDS`, 2 минуты; копия и восстановление — 15 минут) уже был; теперь сообщение называет команду, срок и причину: `cloud timeout at cat after 120 s: HTTP 401: …`. Без него restic ждал бы 15 минут повторов.
- **Тест цикла** (`deploy/test/backup-cycle.ps1`, по умолчанию `-Cloud webdav`): `rclone serve webdav` в отдельном контейнере вместо Яндекса. Сначала копии идут через «прежнее» подключение, затем `connect-yandex-disk.ps1 -WebDav` переключает их на WebDAV по той же папке. Проверяется: прежние снимки видны, восстановление из облака, проверка восстановления, неверный пароль (причина HTTP 401 в журнале, статусе и `backup-status.ps1`, команда прерывается своим тайм-аутом). Настоящего Яндекса и настоящих паролей в тесте нет.

## Последствия

- Владельцу нужен пароль приложения: его создают в Яндекс ID один раз (runbook, раздел 9). Пароль приложения, как и прежний токен, открывает весь Диск; отозвать его можно в Яндекс ID, не меняя основной пароль.
- WebDAV Яндекса медленнее REST API на больших объёмах. Для семейной базы и файлов это приемлемо; если копия перестанет укладываться в 15 минут, срок задаётся `BACKUP_CLOUD_BACKUP_TIMEOUT_SECONDS` в `secrets\backup.env`.
- Ключа `--yandex-hard-delete` у WebDAV нет. Удалённые restic файлы могут попадать в корзину Яндекс Диска и занимать место; владелец раз в несколько месяцев смотрит корзину (runbook, раздел 9).
- Учётные данные WebDAV в `rclone.conf` лежат в виде `rclone obscure` — это не шифрование, а защита от случайного взгляда. Защищает файл то же, что и раньше: папка `secrets`, монтирование только для чтения.

## Как вернуться к REST API

Если Яндекс починит REST API, владелец запускает `pwsh deploy/scripts/connect-yandex-disk.ps1` без `-WebDav`: вход в браузере создаёт подключение `yadisk`, адрес хранилища становится `rclone:yadisk:HomeCRM-backups` (та же папка, снимки сохраняются), для него снова передаётся `--yandex-hard-delete`. Подключение `yadisk-webdav` можно оставить или удалить (`rclone config delete yadisk-webdav --config E:\HomeCRM-data\secrets\rclone\rclone.conf`), пароль приложения — отозвать в Яндекс ID.

## Отклонённые варианты

- **Ждать исправления REST API.** Облачной копии нет с 13 октября; DATA-3 требует двух мест.
- **Другая версия rclone.** Ошибка на стороне Яндекса: 410 отвечает сервер, а не клиент.
- **Другое облако** (S3, Google Диск) — см. ADR-0021: владелец выбрал Яндекс Диск, а WebDAV не требует нового аккаунта и переноса снимков.
- **`rclone config create … pass=… --obscure`** — пароль в аргументах процесса; заменено записью секции из скрипта.
