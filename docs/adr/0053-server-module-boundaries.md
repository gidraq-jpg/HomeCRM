# ADR-0053: Границы модулей сервера и проверка архитектуры

Статус: принято (D53b, 16 ноября 2026)

## Контекст

Сервер вырос до двух десятков модулей в `apps/server/src`. Разбор кода 16 ноября 2026 показал:

- модули зависели друг от друга по кругу: `contacts` ↔ `files` ↔ `objects` ↔ `offline` ↔ `utilities`
  (через `objects/support.ts` и `idempotency.ts`) и `deadlines` ↔ `notifications`;
- файлы маршрутов импортировали друг друга ради вспомогательных функций (`getObject`, `getTask`,
  `readRadar`, `AuthModule`);
- сервер и браузерные сценарии обращались к пакету базы длинными путями `../../../../packages/db/src/...`.

Каждый агент, которому нужна маленькая правка, вынужден был читать соседние модули целиком,
а порядок загрузки файлов зависел от случайностей.

## Решение

1. **Основание `records/`.** Общее для всех модулей с записями лежит в `apps/server/src/records`:
   `support.ts` (маршруты записей, ошибки, размещение), `idempotency.ts`, `snapshot.ts`,
   `objects.ts` (чтение объекта с проверкой доступа), `errors.ts`. Основание зависит только от `auth`.
2. **Направление зависимостей.** `auth` и `records` — основание; над ними `files`, `utilities`,
   `contacts`, `notes`, `objects`, `tasks`; над ними `deadlines`; над `deadlines` — `notifications`
   (в том числе фоновые задачи сроков, `notifications/deadline-jobs.ts`); сверху `inbox`, `ai`,
   `export`, `mcp`, `oauth`. Точки сборки — `app.ts`, `main.ts`, `worker.ts`, `dev/` — импортируют всё.
3. **Файлы маршрутов.** `*routes.ts` импортируют только точки сборки. То, что нужно другому модулю,
   лежит в файле без маршрутов: `auth/module.ts`, `tasks/records.ts`, `contacts/records.ts`,
   `deadlines/radar.ts`, `oauth/grants.ts`, `notes/cards.ts`.
4. **Пакеты.** `shared` → `db` → `server`; клиент берёт только `shared`. Чужой пакет импортируется
   по имени (`@homecrm/db/migrate`, `@homecrm/db/bootstrap`, `@homecrm/db/testing/postgres`),
   а не путём в `src`. Исключение — браузерные сценарии `apps/web/e2e`: они поднимают сервер
   в своём процессе, а у сервера нет входов пакета.
5. **Проверка.** `scripts/check-architecture.ts` входит в `pnpm lint` и проверяет пункты 2–4:
   циклы между папками сервера (по импортам, существующим при выполнении; `import type` не считается),
   импорты файлов маршрутов, пути мимо границ пакетов и направление зависимостей пакетов.
   Новых зависимостей нет: разбор импортов — регулярным выражением.

## Обработчики ошибок

Ответы об ошибках не менялись. Единого обработчика на всё приложение нет намеренно:

- модули на `dataRoutes` используют расширенный обработчик из `records/support.ts`;
- заметки и дом — общий `plainErrorHandler` из `records/errors.ts` (раньше две одинаковые копии);
- сроки отвечают `400 INVALID_INPUT` на нарушение ограничений базы, где остальные отвечают
  `409 CONFLICT`; у ИИ, сводок, OAuth и MCP — свои тексты и коды для клиента.

Свести эти ответы к одному виду — изменение поведения API и клиента; оно требует отдельного решения.

## Последствия

- Перенос файла между модулями или новый импорт «вверх» ловится локально и в CI с понятным текстом.
- Новому модулю нужно выбрать место в порядке из пункта 2; если он нужен модулю ниже —
  общая часть выносится в основание.
- Граф считается по папкам первого уровня: внутри модуля порядок файлов не проверяется.
