# ADR-0040. Действия наступления и сводки

- **Статус:** принято для R1c.5–6, 11 октября 2026.
- **Связано:** DEAD-2…6, NOTIF-2…7, SPACE-7, ADR-0028/0029/0039.

## Решение

Действие хранится отдельно от производного наступления: ссылка на правило, календарная дата и ключ календаря (каноническое JSONB правила без настроек предупреждений). Пояс не входит в ключ: смена пояса сохраняет календарный экземпляр. Правка календаря создаёт другой ключ; прежняя история сохраняется, но не применяется к новому календарю. Очистка источника каскадно удаляет действия через правило. Корзина временно скрывает их, восстановление возвращает. Причины не индексируются; экспорт следует текущему доступу к правилу, а не прежнему снимку размещения.

RLS действий проверяет текущий источник через RLS правила. Запись дополнительно использует право изменения самого источника, включая назначенные ребёнку дела и собственный профиль. Общие поля доступа фиксируются серверным триггером; сохранённый снимок не расширяет текущую видимость. Содержательный вклад другого участника блокирует приватизацию источника по существующему правилу. История состояния хранится вместе с действием и не доступна worker. Версия и неизменяемая квитанция api_operations защищают гонки и потерянный ответ.

Отложить скрывает конкретный календарный экземпляр до UTC-момента, введённого в поясе источника; срок не меняется. Неактуальность требует причины. Возврат не открывает выполненный или закрытый источником пункт. Очередь и диспетчер проверяют состояние непосредственно перед постановкой и отправкой. Worker читает только служебные колонки состояния, без причин и истории.

Сводка хранит получателя, дом, пояс, вид, границы календарного периода и состояние доставки; пользовательские названия и тексты не сохраняются. Чтение содержимого выполняется обычным соединением приложения под RLS получателя и текущей ответственностью. Отдельная RLS сводки допускает только получателя; администратор не получает чужие сводки. Экспорт личного включает метаданные своих сводок; они не участвуют в поиске, удаляются вместе с аккаунтом. Потеря членства скрывает общую сводку.

Утро — 08:00 каждого местного дня, неделя — воскресенье 19:00. Границы считаются календарно, включая DST. Один вид и местный период создают одну логическую сводку независимо от устройств. После простоя создаётся только последний актуальный период. Сводки используют существующий диспетчер, подписки, бюджет, тихие часы и повтор; бюджет сводки не создаёт рекурсивную сводку. Старые summary-события связываются атомарно, по логическому событию, только после повторной проверки актуальности. При чтении содержимого права проверяются заново.

Push содержит только общий текст и маршрут к защищённой сводке. Уже переданный внешней службе пакет отозвать нельзя. Проверка настоящих Android/PWA и сети остаётся владельцу перед выпуском.

## Детали реализации

Миграции 0061/0062 создают ENABLE/FORCE RLS обеих сущностей. App читает причины/историю
только через текущее правило и RLS родителя. Изменяемые колонки действия ограничены
состоянием, причиной, моментом откладывания и версией; идентичность, автор и общие поля
ставит триггер. Блокировка источника предшествует ручному правилу; управляемое правило
читается без UPDATE, иначе запрещалась бы отметка назначенного ребёнку дела. Закрытие
и смена доступа сериализуются с мутацией источника. Чужой вклад учитывает существующий
`has_other_contributions`.

Ключ — MD5 канонического JSONB правила без `warnings`, `endWarnings`, `warningTime`;
это идентификатор календаря, не криптографическая защита. UTC откладывания после смены
пояса сохраняется как выбранный момент. Обычный срок закрывается `complete`; у `after`
дата события становится датой подтверждения в поясе источника. Финансовые и документные
подтверждения выполняются существующими API источников.

Worker получает только служебные колонки действий, включая момент подтверждения, и
источников для проверки открытости/выполнения. Причины, история и названия недоступны.
Дополнительная SELECT-политика платежей допускает служебные поля только платежей
видимого worker начисления. Полный эталон грантов проверяет отсутствие лишних колонок.

Миграция добавляет четыре отдельных вида только при включённом прежнем `deadline`;
пустой список отключает обе новые сводки. Quiet-hours/budget/hideText сохраняются.
PATCH без defaults сохраняет пропущенные поля. Расписание фиксировано, без новой
настройки часов; границы DST вычисляет общий календарный помощник.

Период `done` проверяет актуальные подтверждения, открытые блоки пересчитываются из
общего `readRadar`. Дело, документ и начисление в блоке не дублируются. Историческое
открытое содержимое поэтому может меняться. Название дома читает только API приложения.
Смена пояса отменяет pending push со старым поясом.

Уникальная сводка и включение старых событий создаются одной транзакцией под advisory
lock. Уже включённые события сохраняют связь при сетевом отказе/нулевом бюджете;
в приложении они доступны по текущим правам. Пустой период сохраняется без push.
Новые события после планового момента входят в следующий период; повтор запуска
не рассылает период второй раз.

ZIP следует текущему размещению родителя и включает историю. Корзина скрывает причины
через родителя, восстановление возвращает доступ, окончательная очистка удаляет их
каскадом. Свои сводки экспортируются лично и удаляются с аккаунтом/домом; отдельной
корзины метаданных нет.

## Отклонённые варианты

FK действия на UUID наступления теряет состояние при пересчёте. Снимок названий в сводке возвращает ставший недоступным текст. Вторая очередь назначения/выполнения дублирует существующие события.

## Устойчивое подтверждение документа — NOTIF-5

Миграция 0063 добавляет `documents.invalidated_at`. Триггер базы фиксирует его при
переходе в `invalid` (включая продление) и при создании уже недействительного документа.
При повторном назначении, правке, переносе, корзине и восстановлении момент остаётся
прежним. Приложение не получает UPDATE этой колонки; при вставке подставленное значение
заменяется моментом базы. API `done.at` и `summaryHasContent` используют эту же колонку.
Worker получает SELECT только служебного `invalidated_at`; прежний SELECT `updated_at`
отозван. Названия и история по-прежнему недоступны worker, RLS источника сохранён.

Для прежнего `invalid` точный момент восстанавливается только по явному переходу
`valid → invalid` в `documents_history` (включая личные документы) либо созданию с `status=invalid`. Записи
без истории и записи без такого события сохраняют неизвестный момент (`NULL`).
`updated_at` и `created_at` связанной новой версии не доказывают момент перехода:
новую версию разрешено создать уже после признания старой недействительной.
Такие старые документы и цепочки версий сохранены, но не входят в недельный `done`
до появления достоверного события; повторное назначение или восстановление его не создаёт.
Миграция не меняет прежние строки, `updated_at`, историю, вклад участников, сроки и поиск.
Временные политики backfill и отключение триггеров ограничены транзакцией миграции.
ZIP включает `invalidated_at` (в том числе `null`) под текущими правами к документу.

Узкая регрессия до правки: 3/3 отказа на настоящих API `assignee`, `trash/restore`, `move`;
подтверждение переносилось A → B, `summaryHasContent` менялась с `{A:true,B:false}` на
`{A:false,B:true}`, планировщик создавал ложный push B. Тест переводит только служебные
часы `updated_at` в неделю B; момент признания недействительным не подменяется.

После исправления те же 3/3 API-сценария проходят: дата и подтверждение остаются в A,
в B подтверждения и push нет. Обновление 0062 → 0063 сохраняет прежние данные/историю/сроки/поиск,
восстанавливает момент общей и личной записи из истории и оставляет неизвестный NULL.
Точные гранты worker и настоящий ZIP с устойчивой датой проверены отдельно.
