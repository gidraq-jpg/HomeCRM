# Клиент дел R1c.4b

Клиент использует API PR #49–50 на основе `ced0256`. Сервер, схемы доступа, миграции и рабочее окружение не менялись. Требования: TASK-1…11 в пределах брифа R1c.4b.

| Адрес | Экран |
|---|---|
| `#/today` | Сегодня, главное, выполненное, окна показаний и срочное |
| `#/today/plan` | План с подгрузкой и блоком без даты |
| `#/today/all` | Все дела, фильтры и страницы по 50 записей |
| `#/today/new` | Создание |
| `#/today/tasks/:id` | Карточка, правка, файлы, связи, история и действия серии |
| `#/open/:id` | Открытие из уведомления, включая отложенный переход после входа |

Выбранный дом передаётся идентификатором `householdId` между вкладками и созданием. Список `/tasks` не принимает этот параметр: клиент фильтрует полученные страницы по дому и сохраняет подгрузку; старые личные дела без привязки к дому остаются доступны. Карточки лент не загружаются отдельными запросами. Служебные блоки и справочники независимы.

Повторы, преемников и просрочку вычисляет сервер. Клиент отправляет `repeatScope`, полный чек-лист с прежними UUID и `expectedUpdatedAt`. При конфликте черновик сохраняется, а текущая версия показывается для сравнения. Скрытый адресат ожидания не пересылается как намеренное удаление. Назначение с `suggestedPlacement` подтверждается отдельно; отказ сохраняет форму. При подтверждении меняется тело и ключ, при транспортном повторе неизменённого действия — прежний ключ.

Окно отмены рассчитывается по `doneAt`, HTTP `Date` и монотонным часам с поправкой на транспорт и секундную точность заголовка. Решение об отмене всегда принимает сервер. Действие «Возобновить» отделено от отмены. Для общего конфликта отмены показаны возможные причины без приписывания серверу отсутствующего кода.

После изменений дел, сроков, начислений, объектов, документов и счётчиков обновляется агрегат «Сегодня». Тексты не сохраняются в URL, localStorage, Cache API или журналах. Ключи запросов содержат участника, дом и фильтры; существующая смена сессии очищает query-кэш.

## Ограничения API для ведущего

Эти пункты не закрыты клиентом и не объявляются выполненными. Воспроизведение есть в `apps/web/e2e/app/tasks.e2e.ts`; тесты проверяют фактический ответ текущего API.

1. **Выбор дома при правке старого дела.** Вымышленный взрослый состоит в двух домах; у его старого личного дела `household_id=NULL`. `PATCH /api/tasks/:id` с `{ "planOn": "2026-10-11" }` возвращает `400 {"code":"HOUSE_REQUIRED"}`. Тот же запрос с `householdId` действующего дома возвращает `400 {"code":"INVALID_INPUT"}`. Строгая PATCH-схема не содержит `householdId`. Клиент сохраняет дату и объясняет ограничение, не посылает неподдерживаемое поле. Нужен согласованный способ привязать старое дело к явно выбранному дому. Сценарий «API: HOUSE_REQUIRED…» использует текущую дату дома и отдельную тестовую базу.
2. **Производный срок документа.** Документ взрослого с датой окончания виден в радаре. `POST /api/deadlines/:deadlineId/assignee` с `{ "assigneeId": "<тот же взрослый>" }` возвращает `404 {"code":"NOT_FOUND"}`, хотя контракт предусматривает `409 EDIT_SOURCE`. В маршруте `SELECT ... FOR UPDATE` происходит до проверки `sourceKind`; политика UPDATE не пропускает производный срок. Клиент ведёт в карточку документа и не пытается изменить производный срок. Сценарий «производный срок…» проверяет 404 и переход к источнику; ветка ответа EDIT_SOURCE для этого источника остаётся непроверенной на настоящем API.
3. **Различение причин отказа в отмене.** Изменённый преемник и истёкшее окно защищены ограничениями базы, но HTTP-обёртка возвращает общий `409 CONFLICT`. Для точных отдельных сообщений нужны стабильные публичные коды. Сейчас UI различает действие отмены и показывает возможные причины, обновляет данные; отказ успехом не считается.
4. **Перенос общего дела в личное.** Ответ карточки не содержит `hasOtherContributions`. Общая модель `canMove` по умолчанию считает чужой вклад возможным. Клиент не подставляет ложное `false` и не предлагает этот перенос; перенос своего личного дела в общее и смена аудитории доступны по модели. Нужен подтверждённый признак/способ проверки возможности переноса, чтобы закрыть этот вариант интерфейса.
5. **Быстрая строка второго дома.** `/me` содержит один `timeZone`; агрегат выбранного дома содержит `today`, но не его пояс. Для дополнительного дома быстрая строка не применяет чужой пояс: UI предлагает полную форму с явной датой. Нужен пояс выбранного дома в публичном контракте. Основной дом работает через существующий пояс и общий `parseQuickline`.

## Проверка

Целевые сценарии работают с настоящим сервером и PostgreSQL: отдельная случайная база на сценарий, вымышленная семья, свободные порты, временный ключ файлов. Для окна отмены тест меняет возраст сохранённого события в своей базе вместо ожидания по часам браузера. Проверяется содержимое кэшированных ответов и консоль, включая смену участника и скрытые связи.

Linux-окружение: `apps/web/e2e/tasks-ui/compose.yaml`, проект `homecrm-test-task-4-tasks-ui`, PostgreSQL 18, официальный Playwright 1.63.0, Node 24 и pnpm 12.9.1. Для нового окружения используется существующий `apps/web/e2e/Dockerfile`.

```sh
docker compose -f apps/web/e2e/tasks-ui/compose.yaml up -d --build
docker compose -f apps/web/e2e/tasks-ui/compose.yaml exec -T playwright sh -c 'tar -C /source --exclude=node_modules --exclude=.git --exclude=test-results --exclude=docs/screenshots -cf - . | tar -C /workspace -xf -; cd /workspace/apps/web && node e2e/run.ts app app/tasks.e2e.ts --project=w360 --project=w412 --workers=2'
```

При изменении зависимостей в уже созданном контейнере требуется штатный `pnpm install --frozen-lockfile`. Команды не обращаются к проекту `homecrm` и рабочим данным.

Скриншоты снимаются только в Linux, вместе с axe, проверкой целей от 44 px и отсутствия горизонтальной прокрутки. [360 px](screenshots/R1c.4b/w360/) · [412 px](screenshots/R1c.4b/w412/). Перед снимком формы сохраняются только вымышленные данные. Полный прогон всех экранов продукта не входит в эту задачу.

Тестовый push доставляется через протокол отладки Chromium в сервис-воркер, затем событие нажатия открывает дело после входа. Это проверка браузерного транспорта и маршрута. Доставка через службы push на настоящие Android, поведение PWA и проверка владельцем перед выпуском остаются отдельными проверками.
