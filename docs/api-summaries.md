# Сводки: контракт R1c.6

## Расписание и настройки

Утро — каждый день в **08:00 дома**, неделя — **воскресенье 19:00 дома**.
Расписание фиксировано. `GET/PATCH /api/notifications/settings` дополнен
`morningEnabled`, `weeklyEnabled` (для новых настроек — `true`). Пропущенные поля PATCH
не меняют существующие тихие часы, бюджет, скрытие текста и выключенные виды.

В `enabledKinds` отдельно представлены `document`, `task_reminder`, `task_assignment`,
`task_done`; прежние виды сохранены. Миграция добавляет эти четыре вида только тем,
у кого включён прежний `deadline`, поскольку раньше он охватывал эти события.
Если прежний список пуст, обе сводки выключаются. Иначе их значения по умолчанию — true.
Существующие quiet-hours/budget/hideText сохраняются; это проверяется обновлением базы
с миграции 0060.

Планировщик работает и без push-транспорта: метаданные доступны в приложении. Включение
вида сводки управляет созданием новых периодов и push; уже созданная сводка остаётся
доступной получателю. Разрешение браузера и нулевой бюджет не запрещают чтение API.

## API и блоки

`GET /api/summaries?householdId=<UUID>` — собственные метаданные, по убыванию конца
периода и UUID. Неизвестные параметры — 400, чужой дом — 404.
`GET /api/summaries/:id` — строго проверенный `SummaryResponse`:

| Поле | Содержание |
|---|---|
| `metadata` | ID, получатель, дом, пояс, вид, местная дата, UTC границы периода/создание |
| `today` | Доступные текущие пункты группы «Сейчас» |
| `upcoming` | «Сейчас» и ближайшие семь календарных дней |
| `stuck` | Открытая просрочка и ожидания с наступившей датой проверки, включая сегодня |
| `done` | Подтверждённые дела, полные оплаты, недействительные прежние документы и выполненные ручные сроки в периоде |
| `deferred` | Актуальные логические события прежнего статуса `summary`, включённые в эту сводку |
| `recalculating` | Общий признак пересчёта сроков |

Утренний экран показывает «Сегодня» и «Срочное»; недельный — «Что сделано», «На подходе»,
«Что зависло». Одна запись в блоке не дублируется: например, план/крайний срок одного дела
дают одну ссылку. Отмена выполнения/оплаты удаляет подтверждение из `done` при следующем
чтении. Продление подтверждено недействительностью прежней версии, а не скрытием срока.
`done.at` документа — устойчивый `documents.invalidated_at`, который база фиксирует
при смене статуса. Повторное назначение, перенос, корзина и восстановление не переносят
подтверждение между периодами; корзина скрывает его, восстановление возвращает в исходный.
Для прежних документов точный момент берётся только из явного события истории.
При отсутствии такого события момент неизвестен (`NULL`): документ/версии сохранены,
но подтверждение не включается в недельную сводку и не создаёт push.
Содержимое открытых блоков всегда текущее, включая исторические сводки; период `done`
остаётся сохранённым календарным интервалом.

Получатель личного — владелец, общего — текущий ответственный; дом определяется
источником. Ни текст, ни количество из другого дома не попадают в блоки. Дни рождения
сохраняют специальные правила доступа/получателя общего движка. RLS допускает только
получателя с действующим членством в доме сводки; чужой ID, в том числе у администратора,
возвращает 404. Названия/причины читаются только текущим RLS приложения. Перенос в личное,
смена исполнителя, уход, корзина и отмены перепроверяются при чтении и доставке.

Клиентские маршруты: `/more/summaries` и `/more/summaries/:id`. Push содержит ID,
`kind:summary` и только общий текст. Скрытие: «В HomeCRM есть новое»; без скрытия —
«Готова утренняя сводка»/«Готова недельная сводка». Сервис-воркер принимает безопасный
UUID-маршрут; до входа сохраняется существующий отложенный переход. После входа
содержимое запрашивается у защищённого API; ключи кэша и дерево форм разделены аккаунтом.

## Планирование и доставка

`summaries` хранит только получателя, дом/пояс, вид, местную дату и UTC границы.
Период недели — между соседними воскресеньями 19:00 в местном календаре; DST даёт
167/169 часов. Уникальность `(account_id, household_id, kind, local_date)` и транзакционная
блокировка сериализуют повторные запуски. Разные устройства используют одно событие.
После простоя формируется только последний момент каждого включённого расписания;
пачки пропущенных ежедневных push нет. Периоды до начала членства не создаются.

В той же транзакции старые актуальные события `summary` связываются с ближайшей
подходящей сводкой через `summary_id`: только того же получателя/дома, включённые
настройками, ещё не включённые ранее. При сбое откатываются и связь, и создание.
Сводочный push не включается в другую сводку. Одна логическая запись считается один раз,
независимо от количества устройств. Источники и настройки повторно проверяются API,
а также непосредственно перед транспортом; утратившее актуальность событие не доставляется.

Используется существующий dispatcher: тихие часы, дневной бюджет, сеть/повтор,
индивидуальные доставки устройств, отзыв подписок 404/410 и журнал неопределённого
результата. Успешное устройство повторно не отправляется. Пустая сводка хранит метаданные
для понятного пустого экрана, но push не создаёт. Бюджет сводки не порождает рекурсию.
Переданный внешнему транспорту пакет уже нельзя отозвать.

Worker читает только служебные поля источников/подтверждений; права на названия,
причины и историю действий отсутствуют. Метаданные своих сводок включены в личный ZIP,
не индексируются и удаляются с аккаунтом/домом. Отдельной пользовательской корзины
метаданных нет; источники следуют своей корзине. См. [ADR-0040](adr/0040-radar-summaries.md).

Напоминание дела использует существующее наступление и предупреждение в `planTime`/
`dueTime`, вид `task_reminder`. Назначение и выполнение используют прежние event keys
и очередь, виды `task_assignment`/`task_done`; вторая очередь не создаётся. Перенос
срока/исполнителя, повтор, отмена и изменение доступа отменяют устаревшее событие.
