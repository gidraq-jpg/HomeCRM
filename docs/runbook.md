# Runbook HomeCRM

Как готовить и обслуживать сервер: заглушка и туннели этапа 0, рабочее окружение, резервные копии, восстановление, внешний сторож. Решения и причины — [ADR-0021](adr/0021-operations-backups.md).

Все команды — из корня репозитория `E:\Projects\HomeCRM` в PowerShell 7. Выпуск в рабочее окружение, изменения на VPS и в DNS выполняются только по вашей команде.

## 1. Подготовка компьютера

Делается один раз. Это системные настройки, их меняете вы сами.

1. **Сон.** «Параметры» → «Система» → «Питание и спящий режим»: сон при питании от сети — «Никогда».
2. **Docker Desktop.** Settings → General → включить «Start Docker Desktop when you sign in to your computer».
3. **Автоматический вход.** Без него после перезагрузки Docker не стартует, пока кто-то не войдёт.
   - Скачайте [Autologon](https://learn.microsoft.com/sysinternals/downloads/autologon) с сайта Microsoft, запустите, введите пароль своей учётной записи, нажмите Enable. Пароль хранится в зашифрованном виде, а не открытым текстом в реестре.
   - Чтобы рабочий стол не оставался открытым, создайте в «Планировщике заданий» задачу:
     - название — «HomeCRM - заблокировать экран после входа» (двоеточие в имени задачи Windows не принимает);
     - триггер — «При входе в систему», ваш пользователь, с задержкой 30 секунд;
     - действие — программа `rundll32.exe`, аргументы `user32.dll,LockWorkStation`.

     Сервисы поднимутся, экран будет заблокирован.
4. **Обновления Windows.** «Параметры» → «Обновление и безопасность» → «Изменить период активности»: например, с 6:00 до 24:00. Тогда перезагрузки после обновлений будут ночью.
5. **После отключения света** (по желанию). В BIOS — включение компьютера при появлении питания, обычно «Restore on AC Power Loss: Power On».

## 2. Папка рабочих данных

```powershell
pwsh deploy/scripts/init-data-dir.ps1
```

Создаёт `E:\HomeCRM-data`:

| Путь | Что там |
|---|---|
| `secrets\vapid.env` | Ключи push. **Сохраните содержимое в менеджере паролей:** без этих ключей все подписки придётся оформлять заново |
| `secrets\tunnel\` | Ключ SSH туннеля; при потере создаётся новый |
| `secrets\app\` | Пароли базы и `server.env` рабочего окружения (раздел 7). Для предпросмотра — `secrets\preview\` |
| `secrets\restic-password` | Пароль хранилищ резервных копий. **Без него копии бесполезны** (раздел 8) |
| `secrets\backup.env` | Настройки копий: время, адрес папки на Яндекс Диске |
| `secrets\rclone\` | Подключение к Яндекс Диску с токеном — доступ ко всему Диску, берегите (раздел 9) |
| `backups\restic\` | Копия 1: хранилище restic на этом компьютере. Другой путь — переменная `HOMECRM_BACKUP_DIR` |
| `backups\status\` | Отметки: когда была последняя копия и проверка восстановления |
| `import\` | Выгрузка из LifeOS (R1d) |

Повторный запуск ничего не перезаписывает.

## 3. Заглушка для замеров

Заглушка и приложение занимают один порт 8300, поэтому одновременно работает что-то одно. Пока рабочее окружение не включено (раздел 7), работает заглушка.

| Действие | Команда |
|---|---|
| Запустить | `docker compose -f deploy/compose.yaml --profile probe up -d --build` |
| Остановить | `docker compose -f deploy/compose.yaml --profile probe down` |
| Журнал | `docker compose -f deploy/compose.yaml logs probe` |
| Страница проверки на этом компьютере | <http://127.0.0.1:8300/probe/> |
| Результаты | <http://127.0.0.1:8309/>, сырые данные — <http://127.0.0.1:8309/results.json> |

`down -v` удаляет и результаты замеров — только если их нужно начать заново.

## 4. Вход через VPS

Вариант А1 — российский VPS, вариант А2 — зарубежный ([ADR-0018](adr/0018-external-entry.md)).

1. **DNS.** У регистратора домена добавьте запись A: `home.<домен>` → IP российского VPS, `home-alt.<домен>` → IP зарубежного.
2. **Настройка VPS.** Скопируйте скрипт и запустите его на VPS от root:

   ```powershell
   scp deploy/edge/setup-edge.sh root@<IP VPS>:/root/
   ssh root@<IP VPS> "bash /root/setup-edge.sh home.<домен> '<публичный ключ туннеля>'"
   ```

   Публичный ключ туннеля печатает `init-data-dir.ps1`; он лежит в `E:\HomeCRM-data\secrets\tunnel\id_ed25519.pub`. Если порты 80 или 443 заняты, например VPN, скрипт остановится и ничего не изменит.
3. **Ответ скрипта** — адрес, порт SSH и ключ сервера — передайте агенту. Он запишет `secrets\tunnel\ru.env` (или `alt.env`) и `secrets\tunnel\known_hosts`.
4. **Запуск туннеля.** Туннель смотрит на то, что работает на порту 8300 в сети compose:

   | Что работает | Команда |
   |---|---|
   | Приложение (раздел 7) | `docker compose -f deploy/compose.yaml --profile tunnel-ru up -d --build` |
   | Заглушка (раздел 3) | `$env:TUNNEL_TARGET='probe:8300'; docker compose -f deploy/compose.yaml --profile probe --profile tunnel-ru up -d --build` |

   Для зарубежного VPS — профиль `tunnel-alt`, для сравнения через Cloudflare — `tunnel-cf`. Адрес Cloudflare появится в журнале: `docker compose -f deploy/compose.yaml logs tunnel-cf`.
5. **Проверка:** `https://home.<домен>/health` отвечает `{"status":"ok",…}`; у приложения в ответе есть и `"database":"ok"`.

Туннели перезапускаются сами после обрыва связи и после перезагрузки компьютера (`restart: unless-stopped`).

## 5. База данных и сервер за туннелем (с R0.1)

**Миграции R0.1 заменили прежние.** Набор 0000–0005 (проверки 0.4 и 0.3) заменён набором 0000–0003: рабочей базы с данными семьи до R0.1 не было. Если на этом компьютере осталась база разработки, созданная старыми миграциями, первая новая миграция остановится с ошибкой «The database was created by pre-R0.1 migrations». Удалите такую базу вместе с её томом и создайте заново. Тестовые базы одноразовые, их пересоздавать не нужно; рабочее окружение (compose-проект `homecrm`) этим не затрагивается.

**Как писать миграции дальше.** Рабочую базу миграции меняют уже с данными, поэтому:

- колонку `NOT NULL` в непустую таблицу добавляют в три шага — колонка без ограничения, заполнение, ограничение; одним `ALTER TABLE … ADD COLUMN … NOT NULL` без значения по умолчанию миграция упадёт на первой же строке;
- у таблицы записей новую колонку после `ADD COLUMN` выдают ролям вызовом `SELECT app.grant_record_table('<таблица>');`;
- перед выпуском миграции проверяют на копии резервной копии, а не только на пустой базе: `restore-check.ps1` и предпросмотр на данных рабочей базы (раздел 7). Перед самой миграцией в рабочем окружении копия делается автоматически (DATA-4).

**Адрес клиента за туннелем.** Лимит попыток входа и журнал входов считаются по адресу клиента (AUTH-8). Сервер берёт его из `X-Forwarded-For`, только если ему это разрешено переменной окружения `TRUST_PROXY`:

| Значение | Когда |
|---|---|
| `false` (по умолчанию) | Сервер доступен напрямую, прокси нет: адрес — тот, с которого пришло соединение |
| `true` | Сервер слушает только `127.0.0.1` или закрытую сеть compose, и к нему ходит один туннель или Caddy ([ADR-0018](adr/0018-external-entry.md)): заголовок ставит Caddy, подделать его снаружи нельзя |
| `loopback, 172.16.0.0/12` | Верить только прокси из списка адресов и подсетей, через запятую |

Без `TRUST_PROXY` за туннелем у всех запросов один адрес: ограничение запросов по адресу стало бы общим на всю семью, а журнал входов не показывал бы, откуда зашли. Для рабочего окружения `new-app-secrets.ps1` записывает `TRUST_PROXY=true`: приложение слушает только `127.0.0.1` этого компьютера и сеть compose, куда ходит один туннель.

## 6. Вход: настройки, первая настройка, секреты (с R0.2)

**Переменные окружения сервера.** Сервер читает их из файла окружения. В рабочем окружении это `E:\HomeCRM-data\secrets\app\server.env`, его создаёт `new-app-secrets.ps1` (раздел 7). Файл лежит вне репозитория и не печатается нигде; при неверных настройках сервер называет только имена переменных.

| Переменная | Что это |
|---|---|
| `DATABASE_URL_APP` | Приложение: роль `homecrm_app`, политики «только своё» |
| `DATABASE_URL_AUTH` | Служба входа: роль `homecrm_auth` (Better Auth, приглашения, сброс пароля) |
| `DATABASE_URL_WORKER` | Обработчик: роль `homecrm_worker`; пока им служит очистка просроченного раз в час |
| `BETTER_AUTH_SECRET` | Не короче 32 символов; шифрует секреты второго фактора и подписывает cookie |
| `BASE_URL` | Адрес приложения, как его видит браузер: `https://…`; cookie всегда с `Secure` |
| `TRUSTED_ORIGINS` | Необязательно: адреса через запятую, откуда ещё принимаются изменяющие запросы (Vite в разработке) |
| `HOME_TIME_ZONE` | Необязательно: часовой пояс дома (IANA), в нём приложение показывает даты; по умолчанию `Asia/Yekaterinburg` |
| `TRUST_PROXY` | См. раздел 5 |
| `STATIC_DIR` | Папка собранного клиента; в образе задана, в разработке не нужна |

**Секрет `BETTER_AUTH_SECRET` входит в лист восстановления (раздел 8).** Без него секреты TOTP в базе не расшифровать: потеря секрета — потеря второго фактора у всех, включая администратора; восстановить доступ можно только кодами восстановления. Сменить секрет нельзя без повторной настройки второго фактора у каждого участника.

**Первая настройка.** Выполняется один раз на пустой базе, после запуска окружения (миграции уже применены):

```powershell
docker compose -f deploy/compose.yaml --profile app --profile ops run --rm ops node deploy/scripts/first-setup.ts
```

Команда спрашивает название дома, имя, логин, почту (необязательно) и пароль — пароль дважды, без эха. Пароль нигде не сохраняется: в базе только хэш Argon2id. Нужна лишь `DATABASE_URL_AUTH`. Повторный запуск отказывается, пока в базе есть хоть одна учётная запись; новых участников добавляют приглашения. Администратор входит и сразу включает второй фактор: пока он не включён, данные и управление домом закрыты (AUTH-3). Коды восстановления он сохраняет при включении.

**Очистка.** Обработчик раз в час убирает просроченные сессии и одноразовые значения, давние счётчики попыток, приглашения старше 30 дней после принятия, отзыва или срока и журнал входов старше 180 дней. Сроки — `RETENTION` в `packages/db/src/schema.ts`.

## 7. Рабочее окружение: включение, выпуск, откат, предпросмотр

### Подготовка Web Push (R0.7)

По команде владельца, до запуска обновлённого worker, выполните `pwsh deploy/scripts/new-app-secrets.ps1`; для предпросмотра повторите с `-Environment preview`. Скрипт сохраняет пару из `secrets/vapid.env` этапа 0, а если её нет — создаёт один раз. В `server.env` добавляется только `VAPID_PUBLIC_KEY`, в `worker.env` — также `VAPID_PRIVATE_KEY` и `VAPID_SUBJECT`. Повторный запуск сохраняет значения; несовпадающие ключи требуют восстановления сохранённой пары, скрипт их не заменяет. Значения не печатаются. Сохраните `vapid.env` вне компьютера: замена пары потребует переподписки всех устройств.

Без VAPID API публичного ключа отвечает 503, worker отказывается запускаться с некорректной конфигурацией. После подготовки применяйте обычную процедуру выпуска ниже; изменение файлов само по себе не перезапускает контейнеры. Журнал доставки доступен только владельцу через `GET /api/notifications/deliveries`: `sent` означает принятие push-службой, `retry` — повтор, `gone` — удалённую подписку, `uncertain` — неизвестный результат после аварии, отложенный в сводку. Действующая реализация не отправляет сами сводки. Контракт API и ограничения — [ADR-0029](adr/0029-notification-dispatcher.md).

Окружение — compose-проект `homecrm`: база PostgreSQL 18 (том `homecrm_db-data`), контейнер `migrate` (роли, копия перед миграцией, миграции), `app` (API и клиент на `127.0.0.1:8300`), `worker` (движок сроков) и `backup` (расписание копий). Наружу не публикуется ничего, кроме `127.0.0.1`; на VPS идёт только туннель.

### Первое включение

Делает ведущий агент по вашей команде или вы сами. Заглушка на это время останавливается.

1. `pwsh deploy/scripts/init-data-dir.ps1` (раздел 2), если ещё не запускали.
2. `pwsh deploy/scripts/new-app-secrets.ps1` — создаёт пароли, `server.env` и отдельный `worker.env`. Адрес приложения по умолчанию `https://home.gidraq.link:8443`; другой — ключом `-BaseUrl`.
3. **Сразу сохраните вне компьютера** пароль restic и `BETTER_AUTH_SECRET` — раздел 8. Без этого окружение включать нельзя.
4. Подключите Яндекс Диск — раздел 9. **Без него семье доступ не открывать:** DATA-3 требует копию в двух местах.
5. Остановите заглушку: `docker compose -f deploy/compose.yaml --profile probe down`. Туннель при этом остаётся без приложения за ним — семья пока ничего не видит, и так должно быть до шага 11.
6. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version v0.1.0`. Скрипт собирает образ, запускает базу, миграции, приложение и расписание копий, затем проверяет `/health` (должны быть `status: ok` и `database: ok`).
7. Выполните первую настройку (раздел 6).
8. Сделайте первую копию сразу: `pwsh deploy/scripts/backup-now.ps1`.
9. **Проверьте восстановление из обоих хранилищ:** `pwsh deploy/scripts/restore-check.ps1`. Скрипт разворачивает копию с компьютера и копию с Яндекс Диска в отдельном проекте и сверяет данные; в конце должно быть «ок» по обоим.
10. `pwsh deploy/scripts/backup-status.ps1 -Snapshots` должен закончиться строкой «Всё в порядке» (код 0). Пока проверка восстановления не проведена или не прошла, скрипт возвращает ошибку: окружение не готово. Затем один раз создайте задачу ежемесячной проверки: `pwsh deploy/scripts/register-ops-tasks.ps1` (раздел 9).
11. **Только теперь откройте доступ семье:** запустите туннель на приложение (раздел 4, шаг 4).

До первого включения `backup-now.ps1`, `restore-check.ps1` и `backup-status.ps1` ждут появления базы не больше 90 секунд, затем завершаются с сообщением «База ещё не создана — сначала первое включение (runbook, раздел 7)». Они не создают базу и не запускают миграции. После первой удачной копии проверка восстановления и просмотр копий доступны и при утрате исходной базы. Для отдельного окружения у проверки восстановления есть `-SourceProject` (исходный проект), у остальных команд — `-Project`.

### Обработчик сроков (R0.8)

`worker` работает отдельно от API: раскладывает наступления сроков на 90 дней вперёд раз в сутки и при изменении правил; раз в пять минут проверяет предупреждения и ставит их в очередь. Отправка уведомлений появится в R0.7. Сервис входит в профиль `app`, отдельного порта нет.

Окружение worker — `secrets\app\worker.env`, для предпросмотра — `secrets\preview\worker.env`: только `DATABASE_URL_WORKER` и `HOME_TIME_ZONE`. Перед первым выпуском с worker повторите `pwsh deploy/scripts/new-app-secrets.ps1`; для существующего предпросмотра — также с `-Environment preview`. Скрипт добавит отсутствующий файл из действующего `server.env`, сохранив все существующие секреты. При последующем изменении подключения worker или начального пояса дома обновляйте эти два значения и в `worker.env`.

Журнал: `docker compose -f deploy/compose.yaml --profile app logs --tail 100 worker`; для предпросмотра добавьте `-p homecrm-preview --env-file deploy/preview.env`. При сбое журнал содержит класс (`errorClass`) и код (`errorCode`, если есть); сообщения исключений, стек, SQL и параметры не печатаются.

На время восстановления `restore.ps1` останавливает `app`, `worker` и `backup` и прерывается, если остановка не удалась. После успешного восстановления запустите окружение через `release.ps1` выбранной версии (раздел 10): профиль `app` поднимет и worker, а для рабочего проекта запустится также backup. При ошибке восстановления сервисы остаются остановленными; запуск выбранного образа выполняется отдельно, чтобы сохранить возможность отката.

### Обновление (выпуск)

Только по вашей команде. Метку версии `vX.Y.Z` ставит ведущий агент.

```powershell
pwsh deploy/scripts/release.ps1 -Version v0.2.0
```

Порядок: сборка образа → отдельный контейнер `migrate`: если есть новые миграции, **сначала копия в оба хранилища, потом миграция** → ожидание кода 0 → перезапуск приложения и worker → проверка версии и `/health`. До успеха `migrate` старые app и worker не пересоздаются. При его ошибке скрипт пишет «Выпуск остановлен: migrate завершился с ошибкой», показывает последние безопасные JSON-строки журнала и подсказку отката; «Готово» не выводится. После успешного выпуска проверьте вход на телефоне.

Если облако не отвечает, каждая облачная команда ограничена по времени: `backup`, восстановление, `forget --prune` и `check` — 900 секунд, служебные (`cat`, `init`, `snapshots`) — 120 секунд. Для восстановления большого снимка с Яндекс Диска предел можно поднять. Тайм-аут завершает restic вместе с дочерним rclone и записывает `cloud timeout` без вывода программы. Пределы меняются в `secrets/backup.env`: `BACKUP_CLOUD_BACKUP_TIMEOUT_SECONDS` и `BACKUP_CLOUD_COMMAND_TIMEOUT_SECONDS` (целые секунды, 1…86400). Сбой обязательной копии останавливает миграцию, даже если локальная копия готова (ADR-0021). Сбой очистки старых копий после успешного backup остаётся предупреждением.

Для срочного выпуска без интернета владелец может явно пропустить облако **только для копии перед миграцией**:

```powershell
try {
  $env:BACKUP_PRE_MIGRATION_CLOUD = 'skip'
  pwsh deploy/scripts/release.ps1 -Version <новая-метка>
} finally {
  Remove-Item Env:BACKUP_PRE_MIGRATION_CLOUD -ErrorAction SilentlyContinue
}
```

В этом режиме облако вообще не вызывается, в `backup.json` сохраняется `skipped: configuration`, а `backup-status.ps1` показывает «пропущено по настройке». Локальная копия обязательна; её сбой останавливает выпуск. Пропуск не считается успешной облачной копией. Ежедневные копии продолжают обращаться к обоим хранилищам; после восстановления сети выполните `backup-now.ps1` и проверьте `backup-status.ps1`.

Проверка механизма выпуска без рабочих данных: `pwsh deploy/scripts/test-release.ps1 -ImageVersion <локальная-метка-образа>`. Скрипт создаёт вымышленные секреты в `test-results`, запускает отдельный проект `homecrm-test-release` на порту 8377, проверяет успешный старт и отказ миграции с сохранением прежнего app, затем удаляет только свои контейнеры, тома и временные данные. Параллельный прогон этого проекта запрещён; `-Port` позволяет выбрать другой свободный порт.

### Откат

- **Миграций не было** (или они совместимы со старым образом): запустите прежнюю версию без пересборки — `pwsh deploy/scripts/release.ps1 -Version v0.1.0 -NoBuild`. Образы прежних версий хранятся на компьютере под своими метками.
- **Миграция несовместима со старым образом:** сначала восстановите копию, сделанную перед ней (раздел 10, «Вернуть состояние до выпуска»), потом запустите прежний образ.

### Предпросмотр

Проверка выпуска до переключения: отдельный проект `homecrm-preview` со своей базой на `127.0.0.1:8301`. Рабочее окружение не затрагивается. Копий предпросмотр не делает (`BACKUP_ENABLED=0`), чтобы не смешивать свои тестовые данные с копиями рабочей базы.

```powershell
pwsh deploy/scripts/new-app-secrets.ps1 -Environment preview
pwsh deploy/scripts/release.ps1 -Version v0.2.0 -Project homecrm-preview -EnvFile deploy/preview.env -Port 8301
```

Чтобы проверить миграции на настоящих данных, перед запуском восстановите в предпросмотр последнюю копию: `pwsh deploy/scripts/restore.ps1 -Project homecrm-preview -EnvFile deploy/preview.env`. Новая версия при запуске применит свои миграции к этой копии. Чтобы вход со вторым фактором в таком предпросмотре работал, скопируйте строку `BETTER_AUTH_SECRET` из `secrets\app\server.env` в `secrets\preview\server.env`. Убрать предпросмотр: `docker compose -p homecrm-preview --env-file deploy/preview.env -f deploy/compose.yaml --profile app down -v`.

### Ключ файлов (R0.5b)

`new-app-secrets.ps1` создаёт 32 случайных байта в шестнадцатеричном виде: `secrets/app/file-master-key-1` (для предпросмотра — `secrets/preview/file-master-key-1`). Существующий ключ никогда не перезаписывается. При обновлении существующего окружения повторно запустите этот скрипт перед выпуском: остальные секреты останутся прежними. Само выполнение и выпуск — только по команде владельца.

Compose монтирует ключ приложению как `/run/secrets/file-master-key`; настройки сервера — `FILE_MASTER_KEY_FILE`, `FILE_MASTER_KEY_VERSION=1`, `FILES_DIR=/data/files`. При отсутствии или неверном формате ключа сервер останавливается до открытия базы, без печати значения. В разработке также нужен собственный файл ключа и путь к нему; тестовые ключи не используются сервером автоматически.

Сохраните ключ и его номер **вне компьютера**, вместе с паролем restic. Потеря ключа делает файлы и превью из копий нечитаемыми; пароль restic его не заменяет. Главный ключ не лежит на томе файлов и не входит в restic: восстанавливается владельцем из листа восстановления. Перед восстановлением верните прежний `file-master-key-1`; не оставляйте вновь сгенерированный ключ.

Блоки на томе зашифрованы; имена, типы, размеры и конверты ключей находятся в базе. Копия снимает базу и staging тома под общей с очисткой блокировкой. `manifest.version=2` хранит блоки рядом с дампом, `files/`; восстановление продолжает принимать прежние снимки версии 1 с `/data/files`. Проверка восстановления сверяет количество блоков; проверка расшифровки требует сохранённый главный ключ. Смена главного ключа ещё не реализована: при добавлении нового номера нужно сохранить доступ к прежнему, миграция конвертов — отдельная задача.

## 8. Лист восстановления: что хранить вне компьютера

Если компьютер сломан или украден, из всего, что на нём было, вам понадобятся четыре вещи. Сохраните их **вне этого компьютера**: в менеджере паролей и, лучше, ещё и на бумажном листе дома.

| Что | Где взять | Что будет без него |
|---|---|---|
| **Пароль restic** | файл `E:\HomeCRM-data\secrets\restic-password` | Копии на компьютере и на Яндекс Диске зашифрованы и **не открываются вообще**: они бесполезны |
| **Главный ключ файлов и его номер** | `E:\HomeCRM-data\secrets\app\file-master-key-1`, номер `1` | Фото, PDF и превью из копий не расшифровать |
| **`BETTER_AUTH_SECRET`** | строка в файле `E:\HomeCRM-data\secrets\app\server.env` | Данные восстановятся, но секреты второго фактора не расшифровать: все, включая администратора, теряют второй фактор и входят только по кодам восстановления |
| **Доступ к аккаунту Яндекса**, где лежат копии | ваш аккаунт Яндекса (логин и пароль) | Копии из облака не достать; останется только локальная копия |

Как сохранить: откройте файл блокнотом (`notepad E:\HomeCRM-data\secrets\restic-password`), скопируйте значение в менеджер паролей. Скрипты и агент эти значения не показывают, и показывать не должны. Ключи push (`secrets\vapid.env`, раздел 2) сохраняются так же: без них push-подписки оформляются заново.

Проверьте лист: найдите в менеджере паролей запись и убедитесь, что значение совпадает с файлом. Пароль restic после создания не меняется; если он когда-либо утёк, скажите ведущему агенту — потребуется перешифровать хранилища.

## 9. Резервные копии

**Что и куда.** Каждую ночь в 3:30 по времени дома создаётся копия базы и файлов приложения, зашифрованная паролем restic, в **двух местах**: на этом компьютере (`E:\HomeCRM-data\backups\restic`) и на **Яндекс Диске** (папка `HomeCRM-backups`). Хранится 7 ежедневных, 4 недельных, 6 месячных копий. Дополнительно копия делается перед каждой миграцией. Если компьютер ночью был выключен, копия делается сразу после включения (через минуту после запуска Docker). Раз в неделю проверяется целостность хранилищ, раз в месяц — восстановление (ниже).

### Подключить Яндекс Диск по WebDAV (основной способ с 28 октября 2026)

С 11 октября 2026 Яндекс отвечает `410 Gone` на прежний способ доступа (REST API, вход в браузере), и облачная копия не делалась. Теперь копии идут по **WebDAV** с **паролем приложения** Яндекс ID ([ADR-0047](adr/0047-yandex-webdav.md)). Папка та же — `HomeCRM-backups`, поэтому прежние снимки снова видны.

Бесплатный объём Яндекс Диска — 5 ГБ; для базы дома этого хватает надолго. Когда появятся фото и документы (R0.5), следите за объёмом (`backup-status.ps1 -Snapshots`), при нехватке — платный тариф Яндекс 360.

**Что важно знать до начала.**

- Пароль приложения, как и прежний токен, даёт доступ **ко всему вашему Яндекс Диску**, а не только к папке `HomeCRM-backups`. Поэтому лучше держать копии в **отдельном аккаунте Яндекса** без личных файлов; но можно и в основном.
- Копии зашифрованы паролем restic, который лежит только у вас дома (раздел 8): даже получив доступ к Диску, прочитать их без пароля нельзя. Но **удалить** их можно, поэтому пароль приложения надо беречь. Отозвать его можно в Яндекс ID, не меняя основной пароль.
- Пароль приложения вы вводите только в консоль скрипта: ввод не отображается, на экран и в журналы пароль не выводится. Он сохраняется в `E:\HomeCRM-data\secrets\rclone\rclone.conf` в виде, который rclone прячет от случайного взгляда (это не шифрование). Не отправляйте этот файл никому, в том числе агенту. Контейнеры получают его только для чтения.

**Шаги.**

1. Установите программу rclone, если её ещё нет: `winget install Rclone.Rclone`, затем закройте и снова откройте PowerShell.
2. Убедитесь, что секреты созданы (раздел 7, шаг 2) и образ собран (`pwsh deploy/scripts/release.ps1 …` или `docker compose -f deploy/compose.yaml --profile app build`).
3. Создайте пароль приложения: откройте [id.yandex.ru/security/app-passwords](https://id.yandex.ru/security/app-passwords) в том аккаунте Яндекса, где лежит папка `HomeCRM-backups` → «Создать пароль приложения» → тип **«Файлы / WebDAV»** → любое название, например `HomeCRM`. Яндекс покажет пароль **один раз**: не закрывайте страницу до шага 5.
4. Запустите: `pwsh deploy/scripts/connect-yandex-disk.ps1 -WebDav`.
5. Скрипт спросит логин Яндекса (например, `ivanov` или `ivanov@yandex.ru`) и пароль приложения — вставьте его (`Ctrl+V` или правой кнопкой мыши), символы не отображаются, нажмите Enter.
6. Скрипт откроет папку по WebDAV и напишет, есть ли в ней хранилище копий («прежние снимки будут видны»), запишет адрес в `secrets\backup.env`, проверит весь путь restic → Яндекс Диск и перезапустит расписание копий. Прежнее подключение `yadisk` удаляется только после удачной проверки. В конце должно быть «Яндекс Диск подключён».
7. Скажите ведущему агенту, что подключение готово: он сделает копию (`pwsh deploy/scripts/backup-now.ps1`), проверит, что старые снимки видны (`pwsh deploy/scripts/backup-status.ps1 -Snapshots`), и проверит восстановление (`pwsh deploy/scripts/restore-check.ps1`).

Если скрипт пишет «Яндекс не принял логин или пароль приложения» — проверьте логин и тип пароля («Файлы / WebDAV»), создайте новый пароль приложения и запустите скрипт ещё раз. Ничего не сломано: при ошибке подключение и адрес хранилища остаются прежними.

Если позже `backup-status.ps1` покажет у Яндекс Диска «Причина: Яндекс не принял логин или пароль приложения» (пароль отозван или удалён) — повторите шаги 3–5.

**Корзина Яндекс Диска.** По WebDAV старые копии удаляются без ключа «мимо корзины», поэтому удалённые restic файлы могут попадать в корзину и занимать место. Раз в несколько месяцев откройте [disk.yandex.ru](https://disk.yandex.ru) → «Корзина» и очистите её, если там много файлов с непонятными именами из `HomeCRM-backups`.

**Как вернуться к прежнему способу (REST API).** Если Яндекс починит REST API, запустите `pwsh deploy/scripts/connect-yandex-disk.ps1` без `-WebDav` и выполните шаги ниже: подключение `yadisk` создаётся заново, папка и снимки те же. Пароль приложения после этого можно отозвать в Яндекс ID.

### Подключить Яндекс Диск через REST API (прежний способ, вход в браузере)

Сейчас не работает (Яндекс отвечает 410). Оставлен на случай, если Яндекс починит API.

- Пароль Яндекса в консоль не вводится: вы входите в браузере. Токен входа сохраняется в файл `E:\HomeCRM-data\secrets\rclone\rclone.conf` — не отправляйте его никому, в том числе агенту. На экран токен не выводится: вместо значения в строках будет `***`.

**Шаги.** Своих ключей и консоли разработчика не нужно, всё делает скрипт.

1. Установите программу rclone: `winget install Rclone.Rclone`, затем закройте и снова откройте PowerShell.
2. Убедитесь, что секреты созданы (раздел 7, шаг 2) и образ собран (`pwsh deploy/scripts/release.ps1 …` или `docker compose -f deploy/compose.yaml --profile app build`).
3. Если у вас ещё нет аккаунта для копий — создайте его на [passport.yandex.ru](https://passport.yandex.ru) и один раз откройте [disk.yandex.ru](https://disk.yandex.ru), чтобы Диск создался.
4. Запустите: `pwsh deploy/scripts/connect-yandex-disk.ps1`.
5. Откроется браузер. Войдите в тот аккаунт Яндекса, на Диске которого будут лежать копии, и нажмите «Разрешить» для приложения rclone. Если браузер не открылся сам, rclone напечатает ссылку — откройте её вручную. Когда в браузере появится «Success!», вернитесь в консоль.
6. Скрипт создаст на Диске папку `HomeCRM-backups`, запишет адрес в `secrets\backup.env` и проверит весь путь: создаст в папке зашифрованное хранилище. В конце должно быть «Яндекс Диск подключён».
7. Сделайте первую копию: `pwsh deploy/scripts/backup-now.ps1`.

Если на шаге 5 что-то пошло не так, причина напечатана строками rclone выше (значения секретов в них заменены на `***`); запустите скрипт ещё раз. Если порт 53682 занят, закройте другие окна rclone и повторите.

Если доступ позже пропадёт (токен истёк, вы отозвали доступ в настройках Яндекс ID, сменили пароль) — `backup-status.ps1` покажет ошибку у Яндекс Диска. Войдите заново: `pwsh deploy/scripts/connect-yandex-disk.ps1 -Reconnect` (откроется тот же вход), затем `pwsh deploy/scripts/backup-now.ps1`. Если в причине написано `HTTP 410` — REST API снова не работает, подключите WebDAV (выше).

### Как проверить, что копия дошла

```powershell
pwsh deploy/scripts/backup-status.ps1 -Snapshots
```

Скрипт печатает по-русски: когда была последняя копия, удалась ли она в каждом месте, когда проверялось восстановление (если не проверялось или проверка не прошла — это ошибка), и **список снимков, который он читает прямо из каждого хранилища** (в том числе из Яндекс Диска). Строка «Всё в порядке» — код выхода 0; любая проблема (копия старше 26 часов, ошибка Яндекс Диска, проверка восстановления старше 35 дней) — предупреждение и код 1. При ошибке Яндекс Диска ниже строкой «Причина:» написано, что делать: неверный пароль приложения (HTTP 401), не работает REST API (HTTP 410), кончилось место (HTTP 507), нет сети или Яндекс не ответил вовремя. В журнале контейнера `backup` та же причина — коротким текстом вроде `restic failed at cat (exit code 1): HTTP 401: login or app password rejected` или `cloud timeout at cat after 120 s`; вывод rclone и restic туда не попадает.

Увидеть копии глазами можно в браузере: [disk.yandex.ru](https://disk.yandex.ru) → «Файлы» → папка `HomeCRM-backups`. Внутри будут папки `data`, `index`, `keys`, `snapshots` и файл `config` с непонятными именами и содержимым: **так и должно быть**, это зашифрованное хранилище. Папку не открывайте, не переименовывайте и ничего из неё не удаляйте — это сломает копии.

### Проверка восстановления

Раз в месяц (задачу создаёт `pwsh deploy/scripts/register-ops-tasks.ps1`; она запускается каждый день в 5:30 и сама пропускает запуск, если последняя удачная проверка моложе 30 дней) скрипт `restore-check.ps1`:

1. поднимает чистую базу в отдельном проекте `homecrm-restore-check` (рабочее окружение не затрагивается);
2. разворачивает в неё последнюю копию — по очереди с компьютера и с Яндекс Диска;
3. сверяет число строк по таблицам и число файлов с тем, что записано в копии;
4. применяет миграции текущей версии — так проверяется, что новая версия справится с настоящими данными;
5. удаляет проект и записывает результат; `backup-status.ps1` его показывает.

Запустить вручную: `pwsh deploy/scripts/restore-check.ps1`. Если проверка не прошла, скажите ведущему агенту: копии есть, но восстановить из них пока нельзя. Отметка о проверке обязательна: пока её нет или она старше 35 дней, `backup-status.ps1` сообщает об ошибке. Причина сбоя в журнале и отметке — только этап и код выхода (например, `pg_restore failed at restore (exit code 1)`): тексты записей и сообщения программ туда намеренно не попадают (PRD, раздел 13), подробности смотрятся на месте, на компьютере, с участием ведущего агента.

## 10. Восстановление

Восстановление идёт только в **пустую** базу: поверх живых данных скрипт не работает.

### Вернуть состояние до выпуска или после порчи базы

1. Остановите приложение: `docker compose -f deploy/compose.yaml --profile app --profile backup down` (тома остаются).
2. Удалите том базы: `docker volume rm homecrm_db-data`. Это единственное разрушающее действие; делайте его, только если сначала убедились, что нужная копия есть (`backup-status.ps1 -Snapshots`).
3. `pwsh deploy/scripts/restore.ps1` — восстановит последнюю копию с компьютера; `-From cloud` — с Яндекс Диска; `-Snapshot <номер>` — конкретный снимок (номера — в списке снимков; копии перед миграцией помечены `pre-migration`).
4. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version <метка> -NoBuild`.

### Потерян или сломан компьютер

Нужны лист восстановления (раздел 8) и новый компьютер с Windows и Docker Desktop. Ключ SSH туннеля и ключи push лежат только на старом компьютере: если их не сохранили, туннель настраивается заново (раздел 4, шаг 2), а push-подписки оформляются заново.

1. Подготовьте компьютер (раздел 1), склонируйте репозиторий в `E:\Projects\HomeCRM`, `pnpm install`.
2. `pwsh deploy/scripts/init-data-dir.ps1`, затем `pwsh deploy/scripts/new-app-secrets.ps1` (новые пароли базы подойдут: в копии паролей нет).
3. **Подставьте старые секреты:** в `secrets\restic-password` — пароль restic из листа восстановления (одна строка, без лишних пробелов); в `secrets\app\server.env` — строку `BETTER_AUTH_SECRET=` со старым значением.
4. Подключите Яндекс Диск (раздел 9, «Подключить Яндекс Диск по WebDAV»; тот же аккаунт и та же папка `HomeCRM-backups` — скрипт её не пересоздаёт, а использует).
5. Соберите образ: `docker compose -f deploy/compose.yaml --profile app build`. Затем `pwsh deploy/scripts/restore.ps1 -From cloud`: скрипт сам поднимет пустую базу, развернёт последнюю копию с Яндекс Диска и сверит число строк.
6. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version v0.1.0` (подставьте последнюю метку), затем туннель.
7. Войдите и проверьте данные. Если копия не открывается с «wrong password» — пароль restic введён неверно; без верного пароля восстановление невозможно.

Целевые сроки (план): потеря данных не больше суток (RPO), восстановление за 4 часа (RTO).

## 11. Внешний сторож на VPS

Сценарий для VPS, который раз в минуту запрашивает `https://home.gidraq.link:8443/health` и сообщает, если приложение не отвечает или не может обратиться к базе. Лучше ставить на VPS, **который не служит входом**: тогда сторож заметит и падение самого входа. На VPS ничего не ставится без вашей команды; ниже — инструкция для неё. Файлы лежат в `deploy/watchdog`.

1. Скопируйте на VPS (от root):

   ```powershell
   scp deploy/watchdog/homecrm-watch.sh root@<IP VPS>:/usr/local/bin/homecrm-watch.sh
   scp deploy/watchdog/homecrm-watch.service deploy/watchdog/homecrm-watch.timer root@<IP VPS>:/etc/systemd/system/
   scp deploy/watchdog/homecrm-watch.env.example root@<IP VPS>:/etc/homecrm-watch.env
   ```

2. На VPS: `chmod 755 /usr/local/bin/homecrm-watch.sh && chmod 600 /etc/homecrm-watch.env`, при необходимости поправьте `WATCH_URL` в `/etc/homecrm-watch.env`. Нужен `curl` (`apt install curl`).
3. Включите: `systemctl daemon-reload && systemctl enable --now homecrm-watch.timer`.
4. Проверка: `systemctl start homecrm-watch.service; journalctl -u homecrm-watch -n 5`. При исправном приложении записей об ошибках нет. Журнал: `/var/log/homecrm-watch/watch.log`.

Правила: 5 неудачных проверок подряд (около 5 минут) — запись «notify: unavailable» в журнал и оповещение; когда приложение снова отвечает — «notify: recovered» с временем начала простоя. Оповещение приходит, если приложение не ответило 200 со `"status":"ok"` и `"database":"ok"` (в том числе при недоступной базе).

**Канал оповещений.** Сейчас — журнал VPS. Заготовка под Telegram (R2) включается строками `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `/etc/homecrm-watch.env`; токен читается только из этого файла и не печатается. Из России Telegram API почти недоступен: канал включают на зарубежном VPS.

## 12. Проверки ночью и перед выпуском

Команды выполняются из своего worktree. Одновременно на машине идёт только один тяжёлый прогон: `pnpm check`, замеры скорости или e2e. Перед push дождитесь завершения чужого прогона; штатную ловушку обходить нельзя.

Ловушка сравнивает отправляемые коммиты с удалённой веткой, для новой — с общей базой с `origin/main`. Если изменены только `*.md` (включая `AGENTS.md`, `CLAUDE.md`, `CHANGELOG.md`) или `docs/**`, кроме `docs/screenshots/**`, выполняются только `pnpm check:encoding` и проверка формата изменённых существующих файлов. Для Markdown: LF, перевод строки в конце файла и отсутствие пробелов в конце строк; для поддерживаемых форматов в `docs/` — Biome. У переименований проверяются оба пути; удалённые документы не читаются. Код, снимки, смешанный или пустой набор, неизвестная база требуют полного `pnpm check` и тестов выбора проверок. Полный прогон можно запустить вручную в любой момент:

```powershell
pnpm check
pnpm test:perf
pnpm test:e2e:full
```

`pnpm check` проверяет кодировку, линтер, типы и все обычные тесты Vitest. Файлы `*.perf.test.ts` выделены в `pnpm test:perf`: последовательно, одним worker, с прежним пределом p95 300 мс. В CI это отдельный обязательный шаг задания «pnpm check», после остальных тестов. Ночью и перед каждым выпуском нужны обе команды; замер не запускают одновременно с e2e или проверками другого исполнителя.

В CI задание `changes` использует ту же функцию выбора по путям и всегда проверяет кодировку. На PR сравниваются base/head коммиты, на push в `main` — before/after; неизвестная база и ручной запуск означают полный прогон. Для документов тяжёлые задания не запускаются, а итоговые «pnpm check» и «Вход · 360 и 412 px · axe» завершаются зелёным с пояснением после проверки формата. Для кода браузерные сценарии делятся на три части `--shard=1/3`, `2/3`, `3/3` с лимитом 30 минут каждая. У каждой свой runner, одноразовая PostgreSQL и свободные порты сценариев; `fail-fast: false` даёт завершиться всем частям. Итоговое задание с прежним именем зелёное только при успехе всех трёх, ошибка или отмена любой части блокирует зелёный итог. Артефакты — `auth-screens-360-412-shard-1`, `-2`, `-3`. Состав тестов, тайм-ауты сценариев, повторы, матрица доступа и шаг замеров скорости не меняются.

В CI задан `HOMECRM_E2E_GROUP_STUDIO=1`: файл `studio2.e2e.ts` целиком выполняется в первой части после основного набора, сначала проект `w360`, затем `w412`. Его коллаж читает снимки `w360`, поэтому разделять эти проекты по runner нельзя. Остальные тесты штатно делит `--shard`. Для сгруппированных запусков отдельные каталоги ошибок сохраняют артефакты основного набора; снимки остаются в общем каталоге первой части. Тесты не меняются и не дублируются.

Контроль разбиения D31 через `playwright test --list --reporter=json`, 26 октября 2026: исходный набор — 753 проверки. Первое равномерное разбиение 251 + 251 + 251 совпало по составу, но выявило зависимость коллажа Studio 2 от снимков другого проекта. С учётом группы Studio 2 части содержат 259 + 247 + 247 проверок; объединение идентификаторов совпадает с исходным набором, дублей нет. Успешное выполнение подтверждает отдельный прогон CI.

Проверка D31 на том же PR с временной базой на уже проверенном коммите: push только документации прошёл за 3,67 с вместо полного push за 13 мин 12 с (1885 успешных тестов, 4 прежних пропуска). [Прогон CI только документов](https://github.com/gidraq-jpg/HomeCRM/actions/runs/40327587166) прошёл за 29 с: оба прежних итоговых задания зелёные, полные проверки и браузерные части не запускались. После этого база PR возвращена на `main`, временная ветка удалена; итоговый прогон проверяет весь код D31.

`pnpm test:e2e:full` собирает Linux-образ Playwright и запускает отдельный compose-проект `homecrm-test-full` с одноразовой PostgreSQL. В нём последовательно идут все сценарии приложения (360/412 px и существующие desktop-сценарии на 1280 px), полная матрица форм UI-7 (`e2e/fullscreen-forms/full-matrix.ts`, 100/200%, клавиатура, создание и правка на 360/412 px), затем все сценарии прототипа на обеих его ширинах. axe и проверки доступа, конфликтов и офлайна сохраняются. При ошибке команда возвращает ненулевой код; красный ночной прогон останавливает выпуск.

У тестовой PostgreSQL постоянно задано `max_locks_per_transaction=512`: в локальном Compose и e2e через команду сервера, в CI через `POSTGRES_INITDB_ARGS`. Для внешней тестовой PostgreSQL, переданной через `HOMECRM_TEST_PG_ADMIN_URL`, такую настройку задают при создании кластера; рабочую базу для тестов не используют.

Полный прогон не публикует постоянных портов приложения, серверы сценариев получают свободные порты. После завершения (в том числе ошибки) команда удаляет только свой compose-проект и его одноразовые тома. После принудительного закрытия терминала очистка вручную:


Снимки CI и полного прогона пишутся в `apps/web/test-results/screens/`, ошибки — в `apps/web/test-results/artifacts/` (подпапки `app`, `forms`, `prototype`), эти файлы не коммитятся. Эталоны `docs/screenshots/**` автоматически не меняются: отобранные Linux-снимки для PR переносятся туда отдельно. В CI каталог `apps/web/test-results` прикладывается как артефакт. Тайм-ауты и повторные попытки тестов не увеличиваются.

Три исправленных нестабильных файла можно проверить пять раз подряд в том же контейнере, без полного прогона:

Исходные `service-*` берутся из `apps/web/test-results/screens/UI-6/`, туда же сохраняются коллажи. Для новых снимков сначала выполните сценарий `studio2-service.e2e.ts`; старые утверждённые снимки остаются в документации.


## ИИ: речь и разбор черновиков (AI-1…8, D24)

По умолчанию оба поставщика выключены, `spaces.ai_enabled=false`. Ручной ввод от ИИ не зависит.
Администратор включает ИИ в «Ещё → Настройки дома» после проверки качества и пояснения передачи данных.
`GET /api/ai/status?spaceId=<UUID дома>` требует сессию участника; ответ содержит enabled, speech, extraction, remaining.
Изменение настройки: `PATCH /api/ai/settings {spaceId, enabled}`, только администратор своего дома.
`POST /api/ai/extract {kind, text, spaceId, consent: true}` возвращает проверенный черновик, записей не создаёт.
Без отметки согласия сервер отклоняет запрос до получения контекста и обращения к поставщику.
Виды `task`, `shopping`, `note` сохраняют форму ответа; `auto` возвращает массив до 10 черновиков с полем `kind`.
Внешняя модель возвращает `whenText` дословно; дату и время вычисляет сервер существующим разбором быстрой строки в поясе дома.
Неизвестный срок или id вне присланного списка остаётся пустым и неуверенным. Количество — строка, например «2 кг».
`POST /api/ai/transcribe?spaceId=…` принимает multipart `file`: webm/ogg/m4a/wav, до 10 МБ и 120 секунд.
Длительность проверяется в памяти; файл без достоверной длительности отклоняется. Звук не пишется на диск приложения.
Сама служба речи LifeOS использует свои временные файлы: это её существующий контракт, HomeCRM их не обслуживает.

### Отдельный Hermes HomeCRM

Решение владельца 23 октября 2026: минимальный сервис `deploy/hermes-ai/server.py` на официальном Python API Hermes,
вместо штатного gateway/API-сервера, сохраняющего историю. Только `POST /v1/chat/completions` и `GET /health`;
loopback 127.0.0.1:8643, без CORS, 15 МБ, один разбор одновременно, ключ сравнивается `hmac.compare_digest`.
Сервис принимает текст и JPEG data-URI; произвольные сетевые image_url запрещены. Сжатие фото до 1600 px делает адаптер.
Инструменты, контекстные файлы и память выключены параметрами AIAgent; сессии и траектории не сохраняются;
на каждый запрос создаётся новый AIAgent. Навыки auto_load пусты; cron/gateway не запускаются. Временных файлов с содержимым сервис не создаёт.
Hermes сам обслуживает `openai-codex` и ChatGPT OAuth. Наш сервис не читает auth.json или токены.

Закреплена официальная версия **v2026.6.5**, commit `3c231eb3979ab9c57d5cd6d02f1d577a3b718b43`.
Владелец готовит отдельный официальный checkout и его Python-окружение в `E:\HomeCRM-data\hermes-runtime`
по [руководству Hermes](https://github.com/NousResearch/hermes-agent/blob/v2026.6.5/website/docs/guides/python-library.md).
Скрипт ожидает `.venv/Scripts/python.exe`, при запуске сверяет commit и не использует личный Hermes.
Установка окружения Hermes не выполняется автоматически с правами приложения.

После слияния, по команде владельца (исполнитель на этих путях не запускает):

```powershell
./deploy/scripts/hermes-ai.ps1 -Install
./deploy/scripts/hermes-ai.ps1 -Login
# Выполнить показанную команду входа в отдельном HERMES_HOME, затем:
./deploy/scripts/hermes-ai.ps1 -Run
./deploy/scripts/hermes-ai.ps1 -Status
```

`-Install` создаёт закрытые ACL каталоги, конфиг и отдельный ключ `secrets/ai/api-server-key` без печати значения,
регистрирует задачу «HomeCRM Hermes» при входе пользователя; существующий конфиг не перезаписывает.
`-Login` только печатает команду, вход делает владелец; `-Status` проверяет health и наличие файла входа,
но не утверждает действительность OAuth. Срок действия проверяется фактическим разбором после входа.
Для временной проверки: `-Install -NoTask -HermesHome <временный каталог> -KeyFile <временный файл> -Port <временный порт>`;
те же параметры передать `-Login` и `-Status`. Порт 8642 и личный `~/.hermes` запрещены.
Для `-Run` нужен настоящий закреплённый runtime; тест обёртки без OAuth: `python deploy/hermes-ai/test_server.py`.
Проверяются HTTP и запуск процесса; в тесте AIAgent подменён: OAuth и обращение к реальной модели он не подтверждает.

### Подключение и сбои

Переменные Compose у app и worker: `AI_STT_PROVIDER=local-stt`, `AI_STT_URL=http://host.docker.internal:9000`,
`AI_EXTRACT_PROVIDER=openai-compatible`, `AI_EXTRACT_URL=http://host.docker.internal:8643/v1`,
`AI_EXTRACT_MODEL=hermes-agent`, `AI_EXTRACT_KEY_FILE=/run/ai-secrets/api-server-key`, `AI_DAILY_LIMIT=100`.
`AI_HTTPS_PROXY` — необязательный HTTP(S)-прокси внешнего разбора, к локальной речи не применяется.
В рабочем окружении эти значения лежат в `deploy/.env` (не коммитится, секретов нет — только адреса и путь к файлу ключа): Compose читает его сам при любом запуске без `--env-file`. Без файла ИИ выключен (`disabled`).
Ключ читается из файла во время запроса, в журнал и ошибку не попадает. Запасной вариант — URL `https://api.openai.com/v1`,
имя модели и отдельный файл ключа API; оплата по токенам. Каталог ai подключён read-only, в нём только ключ сервиса.

Операции синхронные: без pg-boss и записи содержимого в БД/очередь; речь 60 с, разбор 90 с на попытку,
один сетевой повтор; один повтор неверной схемы и отдельное отключение json_schema при HTTP 400.
Hermes исполняет каждый разбор в отдельном процессе с остановкой через 90 с; модель по умолчанию gpt-6-luna,
переопределяется параметром скрипта `-HermesModel` (виртуальное имя API остаётся hermes-agent).
Подписка ChatGPT принимает только модели из списка Codex своего аккаунта (24 октября на Plus: gpt-6-luna, gpt-6-sol,
gpt-6.1-sol, gpt-5.6-*); gpt-5.4 и gpt-5.5 отвечают HTTP 400 model_not_found.
OpenAI отвечает 403 на адреса из России: вход (`-Login` подсказывает команду `hermes auth add openai-codex --type oauth`)
и работа экземпляра идут через прокси. `-Run` берёт `-HttpsProxy` или системный прокси Windows, если он включён;
без прокси разбор вернёт 503 AI_UNAVAILABLE.
Максимум две операции POST на процесс приложения; Hermes — один разбор. Не держим транзакцию БД во время сети.
Дневной предел на дом расходуется атомарно до вызова модели (в том числе при её отказе), по часовому поясу дома;
локальная речь лимит внешней модели не расходует. `ai_daily_usage` — служебные счётчики без содержимого,
поиска и корзины; в пользовательский экспорт не включаются. Приватные документы и неизвестные виды черновика отклоняются до HTTP.
В текущем HTTP API изображений нет: проверка признака passport/medical в адаптере — барьер для будущих сценариев.
Журналы содержат только операцию, поставщика, размер, длительность и код ошибки.

Проверка 23 октября из отдельного Docker-контейнера: host.docker.internal:9000 health=200,
transcribe синтетического WAV=200. На 8643 сервис пока не запущен — доступность Hermes после запуска предстоит проверить.
Если в другом Docker Desktop loopback хоста недоступен, ничего не открывать на 0.0.0.0 автоматически:
проверить настройки сети Docker Desktop и согласовать отдельный ограниченный мост/туннель.
При отказе речи проверить GET /health:9000, включён ли компьютер; перезапускать LifeOS этой задачей не разрешено.
При ошибке разбора проверить -Status, вход владельца и дневной предел; оставлять возможность ручного ввода.

Оценка: `pnpm ai:eval` по умолчанию использует `fake` и проверяет контракт на 3 простых текстовых образцах и 3 WAV (`mode: contract`). Это не оценка качества модели.
При `AI_EXTRACT_PROVIDER=openai-compatible` проверяется качество на 28 вымышленных фразах из `apps/server/src/ai/eval/cases.ts` с фиксированным «сегодня», участниками и объектами (`mode: quality`).
Отчёт содержит точность по полям, отдельно точность извлечения без речи, длины инструкций, коды сбоев, номера образцов и полей с расхождениями; содержимого нет. Порог успешного завершения — 85% полей извлечения и отсутствие сбоев поставщика.

### Черновики в интерфейсе (D25)

Кнопка «Разобрать» появляется рядом с диктовкой в быстрой строке дел и покупок при `enabled=true` из `/api/ai/status`. Доступность поставщика не скрывает кнопку: при сбое остаются пояснение и ручной ввод.
При включённом ИИ диктовка покупок дописывает фразу в строку: текст можно поправить и явно отправить на разбор после согласия. При выключенном ИИ остаются прежние надиктованные покупки без внешней модели.
Перед первой отправкой показывается согласие: фраза, дата и короткие списки доступных имён/объектов уходят через Hermes внешней модели. Файлы и другие записи не отправляются; ограничения AI-4 остаются.
Согласие хранится в localStorage этого браузера отдельно по участнику и дому, с версией текста (`homecrm:ai-consent:v1:…`). Миграция профиля не требуется; на новом устройстве или после очистки настроек согласие спрашивается снова. Если браузер запрещает localStorage — действует только в открытой странице. Фразы и черновики в localStorage не сохраняются. При смене внешнего поставщика обновить пояснение и версию согласия.
Контекст ограничен сегодняшней датой с днём недели в поясе дома, участниками и максимум 50 объектами, доступными автору. Объекты упорядочены по числу видимых активных связей, затем по дате изменения и id; дополнительных сведений о записях нет.
Карточки позволяют исправить поля и видимость, сохранить по одной/все или убрать. Пустые и неуверенные поля помечены «проверьте»; время без даты требует правки. Сохранение идёт через обычные API с проверками доступа. Подтверждённые карточки удаляются сразу, даже если следующая не сохранилась; ключи повторов дел и покупок устойчивы к сетевому сбою.
Покупки проверяются на дубли тем же сравнением, что и обычная строка: отдельно по видимости списка, среди некупленного, включая следующие страницы. Повтор из списка или текущего пакета остаётся карточкой «Уже в списке», без добавления и без потери правок.
Сбой, выключенный компьютер и дневной предел не очищают исходную фразу. В журналах — только операция, поставщик, длительность, размер и код результата; проверяется в `ai/routes.test.ts`.
CI и e2e используют только `fake`; внешний Hermes в тестах не запускается. Целевой Linux-прогон: отдельный compose-проект `homecrm-test-d25`, `ai-drafts.e2e.ts`, проекты `w360`/`w412` (с axe и проверкой 44 px).

### PDF во «Входящих» (D33, AI-9)

Текстовые PDF и сканы разбираются вместе с фотографиями в одной записи.
Берутся первые пять страниц, до 20 000 символов на PDF; сканы — JPEG около
150 dpi, длинная сторона до 2000 px. Для длинного файла в готовом черновике
появляется «Разобраны первые 5 страниц из N», для предела текста — отдельное
пояснение. Остаток проверяется вручную. Исходный PDF остаётся вложением;
содержимое не попадает в поиск. Предел модуля — 25 МиБ, существующий захват
«Входящих» по INBOX-1 ограничен 10 МиБ на всю запись.

При отказе:

1. `AI_PDF_ENCRYPTED`: открыть обычную форму вручную либо загрузить копию без пароля.
   Пароль приложение не запрашивает и не хранит.
2. `AI_PDF_BROKEN`: проверить, что файл открывается локальным просмотрщиком,
   заново сохранить PDF или загрузить страницы как фото. Не отправлять настоящий
   документ в сторонние сервисы диагностики и не добавлять его в issue/журналы.
3. `AI_PDF_TIMEOUT`: декодер остановлен через 20 с. Сократить PDF до нужных страниц
   или заполнить вручную. Проверить загрузку CPU/памяти и код результата в журнале.
   Не поднимать пределы без отдельного изменения и проверки недоверенных файлов.
4. При массовых `AI_PDF_BROKEN` после обновления проверить версии Node 24,
   `pdfjs-dist` 5.4.624 и canvas 0.1.100, наличие нативного модуля своей платформы;
   воспроизвести на вымышленном `receipt-scan.pdf`. stdout/stderr декодера закрыты:
   произвольные исключения PDF.js не включать в журнал HTTP-сервера.

Декодер работает в отдельном процессе: 192 МиБ V8 heap, без наследования секретов,
с ограниченным чтением файлов и запретом записи/дочерних процессов.
Это не жёсткий предел всей RSS нативных библиотек. Логи PDF содержат только
`code`, `pages`, `durationMs`; при ошибке до чтения страниц `pages=0`.
Барьер личности проверяет текст и все изображения перед извлечением полей.
Дневной предел расходуется один раз на запись, включая ошибку PDF.

Проверки из корня worktree:

```powershell
node apps/server/src/ai/eval/generate-pdfs.ts
pnpm ai:eval --kind=pdf
pnpm exec vitest run --project=server apps/server/src/ai/pdf.test.ts apps/server/src/inbox/routes.test.ts apps/server/src/inbox/parse.test.ts
```

Генератор нужен только при изменении вымышленных образцов; обычный прогон использует
сохранённые PDF. Fake: 8 образцов, 27/27 контрактных проверок, не оценка качества.
Hermes HomeCRM (27 октября 2026): 8 образцов, 26/27 значений, квитанции 17/18
(94,4%), суммы 3/3 точно, документы личности 2/2 `identity`, ошибки PDF 2/2;
без сбоев, 209 971 мс. Одно расхождение — `accountId` квитанции.
Настоящие документы семьи в этом прогоне не использовались.
