# Runbook HomeCRM

Как готовить и обслуживать сервер. Сейчас — этап 0: заглушка для замеров и туннели. Разделы про выпуск, резервные копии и восстановление появятся в R0.11.

Все команды — из корня репозитория `E:\Projects\HomeCRM` в PowerShell 7.

## 1. Подготовка компьютера

Делается один раз. Это системные настройки, их меняете вы сами.

1. **Сон.** «Параметры» → «Система» → «Питание и спящий режим»: сон при питании от сети — «Никогда».
2. **Docker Desktop.** Settings → General → включить «Start Docker Desktop when you sign in to your computer».
3. **Автоматический вход.** Без него после перезагрузки Docker не стартует, пока кто-то не войдёт.
   - Скачайте [Autologon](https://learn.microsoft.com/sysinternals/downloads/autologon) с сайта Microsoft, запустите, введите пароль своей учётной записи, нажмите Enable. Пароль хранится в зашифрованном виде, а не открытым текстом в реестре.
   - Чтобы рабочий стол не оставался открытым, создайте в «Планировщике заданий» задачу:
     - название — «HomeCRM: заблокировать экран после входа»;
     - триггер — «При входе в систему», ваш пользователь, с задержкой 30 секунд;
     - действие — программа `rundll32.exe`, аргументы `user32.dll,LockWorkStation`.

     Сервисы поднимутся, экран будет заблокирован.
4. **Обновления Windows.** «Параметры» → «Обновление и безопасность» → «Изменить период активности»: например, с 6:00 до 24:00. Тогда перезагрузки после обновлений будут ночью.
5. **После отключения света** (по желанию). В BIOS — включение компьютера при появлении питания, обычно «Restore on AC Power Loss: Power On».

## 2. Папка рабочих данных

```powershell
pwsh deploy/scripts/init-data-dir.ps1
```

Создаёт `E:\HomeCRM-data`:

| Путь | Что там |
|---|---|
| `secrets\vapid.env` | Ключи push. **Сохраните содержимое в менеджере паролей:** без этих ключей все подписки придётся оформлять заново |
| `secrets\tunnel\` | Ключ SSH туннеля; при потере создаётся новый |
| `backups\` | Локальное хранилище резервных копий (R0) |
| `import\` | Выгрузка из LifeOS (R1d) |

Повторный запуск ничего не перезаписывает.

## 3. Заглушка для замеров

| Действие | Команда |
|---|---|
| Запустить | `docker compose -f deploy/compose.yaml --profile probe up -d --build` |
| Остановить | `docker compose -f deploy/compose.yaml --profile probe down` |
| Журнал | `docker compose -f deploy/compose.yaml logs probe` |
| Страница проверки на этом компьютере | <http://127.0.0.1:8300/probe/> |
| Результаты | <http://127.0.0.1:8309/>, сырые данные — <http://127.0.0.1:8309/results.json> |

`down -v` удаляет и результаты замеров — только если их нужно начать заново.

## 4. Вход через VPS

Вариант А1 — российский VPS, вариант А2 — зарубежный ([ADR-0018](adr/0018-external-entry.md)).

1. **DNS.** У регистратора домена добавьте запись A: `home.<домен>` → IP российского VPS, `home-alt.<домен>` → IP зарубежного.
2. **Настройка VPS.** Скопируйте скрипт и запустите его на VPS от root:

   ```powershell
   scp deploy/edge/setup-edge.sh root@<IP VPS>:/root/
   ssh root@<IP VPS> "bash /root/setup-edge.sh home.<домен> '<публичный ключ туннеля>'"
   ```

   Публичный ключ туннеля печатает `init-data-dir.ps1`; он лежит в `E:\HomeCRM-data\secrets\tunnel\id_ed25519.pub`. Если порты 80 или 443 заняты, например VPN, скрипт остановится и ничего не изменит.
3. **Ответ скрипта** — адрес, порт SSH и ключ сервера — передайте агенту. Он запишет `secrets\tunnel\ru.env` (или `alt.env`) и `secrets\tunnel\known_hosts`.
4. **Запуск туннеля:**

   ```powershell
   docker compose -f deploy/compose.yaml --profile probe --profile tunnel-ru up -d --build
   ```

   Для зарубежного VPS — профиль `tunnel-alt`, для сравнения через Cloudflare — `tunnel-cf`. Адрес Cloudflare появится в журнале: `docker compose -f deploy/compose.yaml logs tunnel-cf`.
5. **Проверка:** `https://home.<домен>/health` отвечает `{"status":"ok",…}`.

Туннели перезапускаются сами после обрыва связи и после перезагрузки компьютера (`restart: unless-stopped`).

## 5. База данных и сервер за туннелем (с R0.1)

**Миграции R0.1 заменили прежние.** Набор 0000–0005 (проверки 0.4 и 0.3) заменён набором 0000–0003: рабочей базы с данными семьи до R0.1 не было. Если на этом компьютере осталась база разработки, созданная старыми миграциями, первая новая миграция остановится с ошибкой «The database was created by pre-R0.1 migrations». Удалите такую базу вместе с её томом и создайте заново. Тестовые базы одноразовые, их пересоздавать не нужно; рабочее окружение (compose-проект `homecrm`) этим не затрагивается.

**Как писать миграции дальше.** Рабочую базу миграции меняют уже с данными, поэтому:

- колонку `NOT NULL` в непустую таблицу добавляют в три шага — колонка без ограничения, заполнение, ограничение; одним `ALTER TABLE … ADD COLUMN … NOT NULL` без значения по умолчанию миграция упадёт на первой же строке;
- у таблицы записей новую колонку после `ADD COLUMN` выдают ролям вызовом `SELECT app.grant_record_table('<таблица>');`;
- перед выпуском миграции проверяют на копии резервной копии, а не только на пустой базе (R0.11).

**Адрес клиента за туннелем.** Лимит попыток входа и журнал входов считаются по адресу клиента (AUTH-8). Сервер берёт его из `X-Forwarded-For`, только если ему это разрешено переменной окружения `TRUST_PROXY`:

| Значение | Когда |
|---|---|
| `false` (по умолчанию) | Сервер доступен напрямую, прокси нет: адрес — тот, с которого пришло соединение |
| `true` | Сервер слушает только `127.0.0.1` или закрытую сеть compose, и к нему ходит один туннель или Caddy ([ADR-0018](adr/0018-external-entry.md)): заголовок ставит Caddy, подделать его снаружи нельзя |
| `loopback, 172.16.0.0/12` | Верить только прокси из списка адресов и подсетей, через запятую |

Без `TRUST_PROXY` за туннелем у всех запросов один адрес: ограничение запросов по адресу стало бы общим на всю семью, а журнал входов не показывал бы, откуда зашли. Значение задаётся вместе с остальным окружением приложения в R0.11.
