# Runbook HomeCRM

Как готовить и обслуживать сервер: заглушка и туннели этапа 0, рабочее окружение, резервные копии, восстановление, внешний сторож. Решения и причины — [ADR-0020](adr/0020-operations-backups.md).

Все команды — из корня репозитория `E:\Projects\HomeCRM` в PowerShell 7. Выпуск в рабочее окружение, изменения на VPS и в DNS выполняются только по вашей команде.

## 1. Подготовка компьютера

Делается один раз. Это системные настройки, их меняете вы сами.

1. **Сон.** «Параметры» → «Система» → «Питание и спящий режим»: сон при питании от сети — «Никогда».
2. **Docker Desktop.** Settings → General → включить «Start Docker Desktop when you sign in to your computer».
3. **Автоматический вход.** Без него после перезагрузки Docker не стартует, пока кто-то не войдёт.
   - Скачайте [Autologon](https://learn.microsoft.com/sysinternals/downloads/autologon) с сайта Microsoft, запустите, введите пароль своей учётной записи, нажмите Enable. Пароль хранится в зашифрованном виде, а не открытым текстом в реестре.
   - Чтобы рабочий стол не оставался открытым, создайте в «Планировщике заданий» задачу:
     - название — «HomeCRM: заблокировать экран после входа»;
     - триггер — «При входе в систему», ваш пользователь, с задержкой 30 секунд;
     - действие — программа `rundll32.exe`, аргументы `user32.dll,LockWorkStation`.

     Сервисы поднимутся, экран будет заблокирован.
4. **Обновления Windows.** «Параметры» → «Обновление и безопасность» → «Изменить период активности»: например, с 6:00 до 24:00. Тогда перезагрузки после обновлений будут ночью.
5. **После отключения света** (по желанию). В BIOS — включение компьютера при появлении питания, обычно «Restore on AC Power Loss: Power On».

## 2. Папка рабочих данных

```powershell
pwsh deploy/scripts/init-data-dir.ps1
```

Создаёт `E:\HomeCRM-data`:

| Путь | Что там |
|---|---|
| `secrets\vapid.env` | Ключи push. **Сохраните содержимое в менеджере паролей:** без этих ключей все подписки придётся оформлять заново |
| `secrets\tunnel\` | Ключ SSH туннеля; при потере создаётся новый |
| `secrets\app\` | Пароли базы и `server.env` рабочего окружения (раздел 7). Для предпросмотра — `secrets\preview\` |
| `secrets\restic-password` | Пароль хранилищ резервных копий. **Без него копии бесполезны** (раздел 8) |
| `secrets\backup.env` | Настройки копий: время, адрес папки на Google Диске |
| `secrets\rclone\` | Подключение к Google Диску с токеном (раздел 9) |
| `backups\restic\` | Копия 1: хранилище restic на этом компьютере. Другой путь — переменная `HOMECRM_BACKUP_DIR` |
| `backups\status\` | Отметки: когда была последняя копия и проверка восстановления |
| `import\` | Выгрузка из LifeOS (R1d) |

Повторный запуск ничего не перезаписывает.

## 3. Заглушка для замеров

Заглушка и приложение занимают один порт 8300, поэтому одновременно работает что-то одно. Пока рабочее окружение не включено (раздел 7), работает заглушка.

| Действие | Команда |
|---|---|
| Запустить | `docker compose -f deploy/compose.yaml --profile probe up -d --build` |
| Остановить | `docker compose -f deploy/compose.yaml --profile probe down` |
| Журнал | `docker compose -f deploy/compose.yaml logs probe` |
| Страница проверки на этом компьютере | <http://127.0.0.1:8300/probe/> |
| Результаты | <http://127.0.0.1:8309/>, сырые данные — <http://127.0.0.1:8309/results.json> |

`down -v` удаляет и результаты замеров — только если их нужно начать заново.

## 4. Вход через VPS

Вариант А1 — российский VPS, вариант А2 — зарубежный ([ADR-0018](adr/0018-external-entry.md)).

1. **DNS.** У регистратора домена добавьте запись A: `home.<домен>` → IP российского VPS, `home-alt.<домен>` → IP зарубежного.
2. **Настройка VPS.** Скопируйте скрипт и запустите его на VPS от root:

   ```powershell
   scp deploy/edge/setup-edge.sh root@<IP VPS>:/root/
   ssh root@<IP VPS> "bash /root/setup-edge.sh home.<домен> '<публичный ключ туннеля>'"
   ```

   Публичный ключ туннеля печатает `init-data-dir.ps1`; он лежит в `E:\HomeCRM-data\secrets\tunnel\id_ed25519.pub`. Если порты 80 или 443 заняты, например VPN, скрипт остановится и ничего не изменит.
3. **Ответ скрипта** — адрес, порт SSH и ключ сервера — передайте агенту. Он запишет `secrets\tunnel\ru.env` (или `alt.env`) и `secrets\tunnel\known_hosts`.
4. **Запуск туннеля.** Туннель смотрит на то, что работает на порту 8300 в сети compose:

   | Что работает | Команда |
   |---|---|
   | Приложение (раздел 7) | `docker compose -f deploy/compose.yaml --profile tunnel-ru up -d --build` |
   | Заглушка (раздел 3) | `$env:TUNNEL_TARGET='probe:8300'; docker compose -f deploy/compose.yaml --profile probe --profile tunnel-ru up -d --build` |

   Для зарубежного VPS — профиль `tunnel-alt`, для сравнения через Cloudflare — `tunnel-cf`. Адрес Cloudflare появится в журнале: `docker compose -f deploy/compose.yaml logs tunnel-cf`.
5. **Проверка:** `https://home.<домен>/health` отвечает `{"status":"ok",…}`; у приложения в ответе есть и `"database":"ok"`.

Туннели перезапускаются сами после обрыва связи и после перезагрузки компьютера (`restart: unless-stopped`).

## 5. База данных и сервер за туннелем (с R0.1)

**Миграции R0.1 заменили прежние.** Набор 0000–0005 (проверки 0.4 и 0.3) заменён набором 0000–0003: рабочей базы с данными семьи до R0.1 не было. Если на этом компьютере осталась база разработки, созданная старыми миграциями, первая новая миграция остановится с ошибкой «The database was created by pre-R0.1 migrations». Удалите такую базу вместе с её томом и создайте заново. Тестовые базы одноразовые, их пересоздавать не нужно; рабочее окружение (compose-проект `homecrm`) этим не затрагивается.

**Как писать миграции дальше.** Рабочую базу миграции меняют уже с данными, поэтому:

- колонку `NOT NULL` в непустую таблицу добавляют в три шага — колонка без ограничения, заполнение, ограничение; одним `ALTER TABLE … ADD COLUMN … NOT NULL` без значения по умолчанию миграция упадёт на первой же строке;
- у таблицы записей новую колонку после `ADD COLUMN` выдают ролям вызовом `SELECT app.grant_record_table('<таблица>');`;
- перед выпуском миграции проверяют на копии резервной копии, а не только на пустой базе: `restore-check.ps1` и предпросмотр на данных рабочей базы (раздел 7). Перед самой миграцией в рабочем окружении копия делается автоматически (DATA-4).

**Адрес клиента за туннелем.** Лимит попыток входа и журнал входов считаются по адресу клиента (AUTH-8). Сервер берёт его из `X-Forwarded-For`, только если ему это разрешено переменной окружения `TRUST_PROXY`:

| Значение | Когда |
|---|---|
| `false` (по умолчанию) | Сервер доступен напрямую, прокси нет: адрес — тот, с которого пришло соединение |
| `true` | Сервер слушает только `127.0.0.1` или закрытую сеть compose, и к нему ходит один туннель или Caddy ([ADR-0018](adr/0018-external-entry.md)): заголовок ставит Caddy, подделать его снаружи нельзя |
| `loopback, 172.16.0.0/12` | Верить только прокси из списка адресов и подсетей, через запятую |

Без `TRUST_PROXY` за туннелем у всех запросов один адрес: ограничение запросов по адресу стало бы общим на всю семью, а журнал входов не показывал бы, откуда зашли. Для рабочего окружения `new-app-secrets.ps1` записывает `TRUST_PROXY=true`: приложение слушает только `127.0.0.1` этого компьютера и сеть compose, куда ходит один туннель.

## 6. Вход: настройки, первая настройка, секреты (с R0.2)

**Переменные окружения сервера.** Сервер читает их из файла окружения. В рабочем окружении это `E:\HomeCRM-data\secrets\app\server.env`, его создаёт `new-app-secrets.ps1` (раздел 7). Файл лежит вне репозитория и не печатается нигде; при неверных настройках сервер называет только имена переменных.

| Переменная | Что это |
|---|---|
| `DATABASE_URL_APP` | Приложение: роль `homecrm_app`, политики «только своё» |
| `DATABASE_URL_AUTH` | Служба входа: роль `homecrm_auth` (Better Auth, приглашения, сброс пароля) |
| `DATABASE_URL_WORKER` | Обработчик: роль `homecrm_worker`; пока им служит очистка просроченного раз в час |
| `BETTER_AUTH_SECRET` | Не короче 32 символов; шифрует секреты второго фактора и подписывает cookie |
| `BASE_URL` | Адрес приложения, как его видит браузер: `https://…`; cookie всегда с `Secure` |
| `TRUSTED_ORIGINS` | Необязательно: адреса через запятую, откуда ещё принимаются изменяющие запросы (Vite в разработке) |
| `HOME_TIME_ZONE` | Необязательно: часовой пояс дома (IANA), в нём приложение показывает даты; по умолчанию `Asia/Yekaterinburg` |
| `TRUST_PROXY` | См. раздел 5 |
| `STATIC_DIR` | Папка собранного клиента; в образе задана, в разработке не нужна |

**Секрет `BETTER_AUTH_SECRET` входит в лист восстановления (раздел 8).** Без него секреты TOTP в базе не расшифровать: потеря секрета — потеря второго фактора у всех, включая администратора; восстановить доступ можно только кодами восстановления. Сменить секрет нельзя без повторной настройки второго фактора у каждого участника.

**Первая настройка.** Выполняется один раз на пустой базе, после запуска окружения (миграции уже применены):

```powershell
docker compose -f deploy/compose.yaml --profile app --profile ops run --rm ops node deploy/scripts/first-setup.ts
```

Команда спрашивает название дома, имя, логин, почту (необязательно) и пароль — пароль дважды, без эха. Пароль нигде не сохраняется: в базе только хэш Argon2id. Нужна лишь `DATABASE_URL_AUTH`. Повторный запуск отказывается, пока в базе есть хоть одна учётная запись; новых участников добавляют приглашения. Администратор входит и сразу включает второй фактор: пока он не включён, данные и управление домом закрыты (AUTH-3). Коды восстановления он сохраняет при включении.

**Очистка.** Обработчик раз в час убирает просроченные сессии и одноразовые значения, давние счётчики попыток, приглашения старше 30 дней после принятия, отзыва или срока и журнал входов старше 180 дней. Сроки — `RETENTION` в `packages/db/src/schema.ts`.

## 7. Рабочее окружение: включение, выпуск, откат, предпросмотр

Окружение — compose-проект `homecrm`: база PostgreSQL 18 (том `homecrm_db-data`), контейнер `migrate` (роли, копия перед миграцией, миграции), `app` (API и клиент на `127.0.0.1:8300`) и `backup` (расписание копий). Наружу не публикуется ничего, кроме `127.0.0.1`; на VPS идёт только туннель.

### Первое включение

Делает ведущий агент по вашей команде или вы сами. Заглушка на это время останавливается.

1. `pwsh deploy/scripts/init-data-dir.ps1` (раздел 2), если ещё не запускали.
2. `pwsh deploy/scripts/new-app-secrets.ps1` — создаёт пароли и `server.env`. Адрес приложения по умолчанию `https://home.gidraq.link:8443`; другой — ключом `-BaseUrl`.
3. **Сразу сохраните вне компьютера** пароль restic и `BETTER_AUTH_SECRET` — раздел 8. Без этого окружение включать нельзя.
4. Подключите Google Диск — раздел 9. Можно и позже, но тогда копия до этого будет только на компьютере.
5. Остановите заглушку: `docker compose -f deploy/compose.yaml --profile probe down`.
6. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version v0.1.0`. Скрипт собирает образ, запускает базу, миграции, приложение и расписание копий, затем проверяет `/health` (должны быть `status: ok` и `database: ok`).
7. Запустите туннель на приложение (раздел 4, шаг 4), если он был остановлен.
8. Выполните первую настройку (раздел 6).
9. Сделайте первую копию сразу и проверьте её: `pwsh deploy/scripts/backup-now.ps1`, затем `pwsh deploy/scripts/backup-status.ps1 -Snapshots`.
10. Один раз создайте задачу проверки восстановления: `pwsh deploy/scripts/register-ops-tasks.ps1` (раздел 9).

### Обновление (выпуск)

Только по вашей команде. Метку версии `vX.Y.Z` ставит ведущий агент.

```powershell
pwsh deploy/scripts/release.ps1 -Version v0.2.0
```

Порядок: сборка образа → контейнер `migrate`: если есть новые миграции, **сначала копия в оба хранилища, потом миграция** (без удачной копии миграция не идёт и окружение не обновляется) → перезапуск приложения → проверка `/health`. После этого проверьте вход на телефоне. Если нет интернета и копия на Google Диск не уходит, а выпуск срочный, можно перед запуском задать `$env:BACKUP_PRE_MIGRATION_CLOUD='skip'`: тогда достаточно локальной копии.

### Откат

- **Миграций не было** (или они совместимы со старым образом): запустите прежнюю версию без пересборки — `pwsh deploy/scripts/release.ps1 -Version v0.1.0 -NoBuild`. Образы прежних версий хранятся на компьютере под своими метками.
- **Миграция несовместима со старым образом:** сначала восстановите копию, сделанную перед ней (раздел 10, «Вернуть состояние до выпуска»), потом запустите прежний образ.

### Предпросмотр

Проверка выпуска до переключения: отдельный проект `homecrm-preview` со своей базой на `127.0.0.1:8301`. Рабочее окружение не затрагивается. Копий предпросмотр не делает (`BACKUP_ENABLED=0`), чтобы не смешивать свои тестовые данные с копиями рабочей базы.

```powershell
pwsh deploy/scripts/new-app-secrets.ps1 -Environment preview
pwsh deploy/scripts/release.ps1 -Version v0.2.0 -Project homecrm-preview -EnvFile deploy/preview.env -Port 8301
```

Чтобы проверить миграции на настоящих данных, перед запуском восстановите в предпросмотр последнюю копию: `pwsh deploy/scripts/restore.ps1 -Project homecrm-preview -EnvFile deploy/preview.env`. Новая версия при запуске применит свои миграции к этой копии. Чтобы вход со вторым фактором в таком предпросмотре работал, скопируйте строку `BETTER_AUTH_SECRET` из `secrets\app\server.env` в `secrets\preview\server.env`. Убрать предпросмотр: `docker compose -p homecrm-preview --env-file deploy/preview.env -f deploy/compose.yaml --profile app down -v`.

## 8. Лист восстановления: что хранить вне компьютера

Если компьютер сломан или украден, из всего, что на нём было, вам понадобятся три вещи. Сохраните их **вне этого компьютера**: в менеджере паролей и, лучше, ещё и на бумажном листе дома.

| Что | Где взять | Что будет без него |
|---|---|---|
| **Пароль restic** | файл `E:\HomeCRM-data\secrets\restic-password` | Копии на компьютере и на Google Диске зашифрованы и **не открываются вообще**: они бесполезны |
| **`BETTER_AUTH_SECRET`** | строка в файле `E:\HomeCRM-data\secrets\app\server.env` | Данные восстановятся, но секреты второго фактора не расшифровать: все, включая администратора, теряют второй фактор и входят только по кодам восстановления |
| **Доступ к Google-аккаунту**, где лежат копии | ваш аккаунт Google | Копии из облака не достать; останется только локальная копия |

Как сохранить: откройте файл блокнотом (`notepad E:\HomeCRM-data\secrets\restic-password`), скопируйте значение в менеджер паролей. Скрипты и агент эти значения не показывают, и показывать не должны. Ключи push (`secrets\vapid.env`, раздел 2) сохраняются так же: без них push-подписки оформляются заново.

Проверьте лист: найдите в менеджере паролей запись и убедитесь, что значение совпадает с файлом. Пароль restic после создания не меняется; если он когда-либо утёк, скажите ведущему агенту — потребуется перешифровать хранилища.

## 9. Резервные копии

**Что и куда.** Каждую ночь в 3:30 по времени дома создаётся копия базы и файлов приложения, зашифрованная паролем restic, в **двух местах**: на этом компьютере (`E:\HomeCRM-data\backups\restic`) и на **Google Диске** (папка `HomeCRM-backups`). Хранится 7 ежедневных, 4 недельных, 6 месячных копий. Дополнительно копия делается перед каждой миграцией. Если компьютер ночью был выключен, копия делается сразу после включения (через минуту после запуска Docker). Раз в неделю проверяется целостность хранилищ, раз в месяц — восстановление (ниже).

### Подключить Google Диск (один раз)

Бесплатный объём Google Диска — 15 ГБ на аккаунт; для базы дома этого хватает на годы. Когда появятся фото и документы (R0.5), следите за объёмом (`backup-status.ps1 -Snapshots`), при нехватке — платный тариф Google One.

Приложение получает доступ **только к файлам, которые оно само создало** (область `drive.file`): остальной ваш Диск ему не виден. Ключ доступа не вводится в консоль: вы входите в Google в браузере, а токен сохраняется в файл `E:\HomeCRM-data\secrets\rclone\rclone.conf`.

1. Установите программу rclone: `winget install Rclone.Rclone`, затем закройте и снова откройте PowerShell.
2. Убедитесь, что секреты созданы (раздел 7, шаг 2) и образ собран (`pwsh deploy/scripts/release.ps1 …` или `docker compose -f deploy/compose.yaml --profile app build`).
3. Запустите: `pwsh deploy/scripts/connect-google-drive.ps1`.
4. Откроется браузер. Войдите в тот аккаунт Google, где должны лежать копии, и нажмите «Разрешить». Если Google пишет, что приложение не проверено, нажмите «Дополнительно» → «Перейти на страницу…» (это общий вход rclone, а не отдельное приложение).
5. Вернитесь в консоль. Скрипт создаст на Диске папку `HomeCRM-backups`, запишет адрес в `secrets\backup.env` и проверит весь путь: создаст в папке зашифрованное хранилище. В конце должно быть «Google Диск подключён».
6. Сделайте первую копию: `pwsh deploy/scripts/backup-now.ps1`.

Если доступ позже пропадёт (вы сменили пароль Google, отозвали доступ) — `backup-status.ps1` покажет ошибку у Google Диска. Подключите заново: `rclone config reconnect gdrive: --config E:\HomeCRM-data\secrets\rclone\rclone.conf` (откроется тот же вход), затем `backup-now.ps1`.

### Как проверить, что копия дошла

```powershell
pwsh deploy/scripts/backup-status.ps1 -Snapshots
```

Скрипт печатает по-русски: когда была последняя копия, удалась ли она в каждом месте, когда проверялось восстановление, и **список снимков, который он читает прямо из каждого хранилища** (в том числе из Google Диска). Строка «Всё в порядке» — код выхода 0; любая проблема (копия старше 26 часов, ошибка Google Диска, проверка восстановления старше 35 дней) — предупреждение и код 1.

Увидеть копии глазами можно в браузере: Google Диск → «Мой диск» → папка `HomeCRM-backups`. Внутри будут папки `data`, `index`, `keys`, `snapshots` и файл `config` с непонятными именами и содержимым: **так и должно быть**, это зашифрованное хранилище. Папку не открывайте, не переименовывайте и ничего из неё не удаляйте — это сломает копии.

### Проверка восстановления

Раз в месяц (задачу создаёт `pwsh deploy/scripts/register-ops-tasks.ps1`; она запускается каждый день в 5:30 и сама пропускает запуск, если последняя удачная проверка моложе 30 дней) скрипт `restore-check.ps1`:

1. поднимает чистую базу в отдельном проекте `homecrm-restore-check` (рабочее окружение не затрагивается);
2. разворачивает в неё последнюю копию — по очереди с компьютера и с Google Диска;
3. сверяет число строк по таблицам и число файлов с тем, что записано в копии;
4. применяет миграции текущей версии — так проверяется, что новая версия справится с настоящими данными;
5. удаляет проект и записывает результат; `backup-status.ps1` его показывает.

Запустить вручную: `pwsh deploy/scripts/restore-check.ps1`. Если проверка не прошла, скажите ведущему агенту: копии есть, но восстановить из них пока нельзя.

## 10. Восстановление

Восстановление идёт только в **пустую** базу: поверх живых данных скрипт не работает.

### Вернуть состояние до выпуска или после порчи базы

1. Остановите приложение: `docker compose -f deploy/compose.yaml --profile app --profile backup down` (тома остаются).
2. Удалите том базы: `docker volume rm homecrm_db-data`. Это единственное разрушающее действие; делайте его, только если сначала убедились, что нужная копия есть (`backup-status.ps1 -Snapshots`).
3. `pwsh deploy/scripts/restore.ps1` — восстановит последнюю копию с компьютера; `-From cloud` — с Google Диска; `-Snapshot <номер>` — конкретный снимок (номера — в списке снимков; копии перед миграцией помечены `pre-migration`).
4. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version <метка> -NoBuild`.

### Потерян или сломан компьютер

Нужны лист восстановления (раздел 8) и новый компьютер с Windows и Docker Desktop. Ключ SSH туннеля и ключи push лежат только на старом компьютере: если их не сохранили, туннель настраивается заново (раздел 4, шаг 2), а push-подписки оформляются заново.

1. Подготовьте компьютер (раздел 1), склонируйте репозиторий в `E:\Projects\HomeCRM`, `pnpm install`.
2. `pwsh deploy/scripts/init-data-dir.ps1`, затем `pwsh deploy/scripts/new-app-secrets.ps1` (новые пароли базы подойдут: в копии паролей нет).
3. **Подставьте старые секреты:** в `secrets\restic-password` — пароль restic из листа восстановления (одна строка, без лишних пробелов); в `secrets\app\server.env` — строку `BETTER_AUTH_SECRET=` со старым значением.
4. Подключите Google Диск (раздел 9, «Подключить Google Диск»; вход в тот же аккаунт и та же папка `HomeCRM-backups` — скрипт её не пересоздаёт, а использует).
5. Соберите образ: `docker compose -f deploy/compose.yaml --profile app build`. Затем `pwsh deploy/scripts/restore.ps1 -From cloud`: скрипт сам поднимет пустую базу, развернёт последнюю копию с Google Диска и сверит число строк.
6. Запустите окружение: `pwsh deploy/scripts/release.ps1 -Version v0.1.0` (подставьте последнюю метку), затем туннель.
7. Войдите и проверьте данные. Если копия не открывается с «wrong password» — пароль restic введён неверно; без верного пароля восстановление невозможно.

Целевые сроки (план): потеря данных не больше суток (RPO), восстановление за 4 часа (RTO).

## 11. Внешний сторож на VPS

Сценарий для VPS, который раз в минуту запрашивает `https://home.gidraq.link:8443/health` и сообщает, если приложение не отвечает или не может обратиться к базе. Лучше ставить на VPS, **который не служит входом**: тогда сторож заметит и падение самого входа. На VPS ничего не ставится без вашей команды; ниже — инструкция для неё. Файлы лежат в `deploy/watchdog`.

1. Скопируйте на VPS (от root):

   ```powershell
   scp deploy/watchdog/homecrm-watch.sh root@<IP VPS>:/usr/local/bin/homecrm-watch.sh
   scp deploy/watchdog/homecrm-watch.service deploy/watchdog/homecrm-watch.timer root@<IP VPS>:/etc/systemd/system/
   scp deploy/watchdog/homecrm-watch.env.example root@<IP VPS>:/etc/homecrm-watch.env
   ```

2. На VPS: `chmod 755 /usr/local/bin/homecrm-watch.sh && chmod 600 /etc/homecrm-watch.env`, при необходимости поправьте `WATCH_URL` в `/etc/homecrm-watch.env`. Нужен `curl` (`apt install curl`).
3. Включите: `systemctl daemon-reload && systemctl enable --now homecrm-watch.timer`.
4. Проверка: `systemctl start homecrm-watch.service; journalctl -u homecrm-watch -n 5`. При исправном приложении записей об ошибках нет. Журнал: `/var/log/homecrm-watch/watch.log`.

Правила: 5 неудачных проверок подряд (около 5 минут) — запись «notify: unavailable» в журнал и оповещение; когда приложение снова отвечает — «notify: recovered» с временем начала простоя. Оповещение приходит, если приложение не ответило 200 со `"status":"ok"` и `"database":"ok"` (в том числе при недоступной базе).

**Канал оповещений.** Сейчас — журнал VPS. Заготовка под Telegram (R2) включается строками `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `/etc/homecrm-watch.env`; токен читается только из этого файла и не печатается. Из России Telegram API почти недоступен: канал включают на зарубежном VPS.
