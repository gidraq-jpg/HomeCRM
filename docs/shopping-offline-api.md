# Отчёт R1c.7–8a

Сделано: SHOP-1…3 API личного/общего списка, количество и data, связи, история, поиск, ZIP,
отметка куплено, системная корзина после семи суток и восстановление без немедленной уборки.
Офлайн-allowlist реализована на прежних маршрутах дел/заметок/чек-листов/показаний с фото,
включая атомарное «Сохранить всё»; правила доступа и семисекундная отмена сохранены.

Точный контракт: [api-shopping](api-shopping.md), [api-offline](api-offline.md),
решение/права/совместимость: [ADR-0041](adr/0041-shopping-offline-receipts.md).
Новых зависимостей, клиентских экранов/IndexedDB, второй очереди событий и bulk-движка нет.
Миграция 0064 только добавляет data/receipt и необходимые политики/функции/индексацию после 0063.

Целевые проверки: новые server suites 22/22, последний DB-каталог/гранты/schema/vintage upgrade
95/95; до них прежние затронутые API, каскады и обновления. Типы, линтер и кодировка чистые
(предыдущие предупреждения линтера в неизменённых файлах не исправлялись).
Проверены настоящий COMMIT с потерянным ответом, параллельный replay, иной payload/key/owner,
current RLS/уход/корзина/аудитория/назначение, цепочки UUID и точной commit-version,
snapshot race и конфликт двух ревизий в одной миллисекунде, checklist parent version,
read-only accountId-envelope радара/покупок/последних карточек без editable-версий,
шифрованное фото→показание, batch атомарность/база/предупреждение, один преемник/push, 7 секунд,
SHOP уборка/отмена/restore, настоящий ZIP и opt-in поиск с сохранным legacy enum/лимитом.
Обновление реальной базы 0063→0064 сохраняет прежние строки/историю/файлы/blob registry и
канонические task_create/patch/status хэши: старые живые ключи replay без ложного 409.

Проверки отправки идут штатным pre-push `pnpm check` и CI конкретного HEAD;
их окончательные результаты находятся в описании запроса на слияние и CI.
Тестовое окружение: свой tmpfs PostgreSQL18, случайный loopback-порт, случайные базы,
max_locks_per_transaction=512, VITEST_MAX_WORKERS=2. Рабочие данные/окружение не используются.

Граница: клиент 8b обязан сверять accountId/owner/key/operation и поколение сессии, хранить
базовые версии только согласованного snapshot и не считать 409 подтверждением. Старый cache
без точной версии требует обновления/явного решения. На телефонах, offline cache и реальной
сети эта серверная задача не заявляет проверок. Выпуска/слияния исполнитель не делает.
