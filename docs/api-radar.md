# Радар: контракт R1c.5–6

Сессия обязательна. Названия, связи, варианты фильтров, количества и возможности
читаются обычной ролью приложения под RLS текущего участника. «Весь дом» расширяет
ответ только среди уже доступных источников. `access.ts` остаётся эталоном прав.

## Чтение

`GET /api/deadlines?from=YYYY-MM-DD&to=YYYY-MM-DD`

Дополнительные параметры:

| Параметр | Значение по умолчанию | Смысл |
|---|---|---|
| `householdId` | все действующие членства | Дом источника, включая привязанный дом личного срока |
| `objectId` | все | Прямой объект, объект-владелец документа или видимая связь объекта с документом, делом, заметкой |
| `personId` | все | Участник-ответственный, именинник, владелец документа или адресат ожидания |
| `scope` | `all` | `all`, `personal`, `household` |
| `view` | `all` | `mine` — текущий ответственный; `all` — все доступные |
| `state` | `active` | `active`, `snoozed`, `dismissed`, `all` |

Все фильтры соединяются через И. Неизвестный параметр, некорректная дата/UUID или
`from > to` — 400. Недоступный дом, объект или человек — 404. Справочники объекта
и человека строятся из доступных кандидатов ответа до применения дополнительных
фильтров; они не раскрывают скрытые связи. В вариантах `people` роль подписана:
«Ответственный», «Именинник», «Владелец документа», «Адресат ожидания». Один ID может
иметь несколько ролей. `options.houses` содержит только действующие членства.

Ответ строго проверяется `RadarResponse` из `packages/shared/src/radar.ts`:
`{items, options:{houses,objects,people}, groups, recalculating}`. `groups` считает
уже отфильтрованный результат. Порядок — `startsAt`, затем UUID наступления.
Страничного обрезания нет; количество SQL-запросов не зависит от числа карточек.
Старые вызовы из «Сегодня» и дел без новых параметров совместимы.

Поля пункта сохраняют прежний контекст источника и включают:

- `calendarKey`: непрозрачный ключ календаря; клиент отправляет его без пересчёта;
- `canWrite`: право изменить источник; чтение само по себе этого права не даёт;
- `actionState`: версия, состояние, UTC откладывания, причина, автор и время отметки;
- `objects`, `people`: только видимые соответствия фильтрам;
- `missingReadingsCount`: активные приборы без живого переданного показания в окне;
- `totalCents`, `paidCents`, `remainingCents`: целые копейки для начисления;
- `timeZone`: пояс самого источника, используемый группировкой и формами.

Пять основных групп: `overdue`, `now`, `7days`, `30days`, `90days`. Для документа
или дня рождения с уже начавшимся дальним предупреждением сохраняется `later`.
Серверный горизонт — 90 дней, для документа/дня рождения — 365. Открытая старая
просрочка не отсекается нижней границей `from`; просроченные дни рождения исключены.
Фактические оплата, передача показаний, выполнение дела и недействительность документа
проверяются по текущему источнику, а не по вспомогательной отметке.

## Действия

Карточка всегда доступна отдельной ссылкой. `primaryAction=null` у читающего без права
изменения. Коммунальные действия описаны в [действующем контракте](utility-deadlines-api.md).
Документ возвращает `renew_document`; «Продлить» открывает
`/documents/:id?action=renew` и существующую форму новой версии. Дело открывает своё
дело; остальные источники сохраняют явный идемпотентный `/api/tasks/from-radar`.

`POST /api/deadlines/occurrences/:id/action`, строгий JSON:

```json
{
  "action": "dismiss",
  "calendarKey": "0123456789abcdef0123456789abcdef",
  "expectedVersion": 0,
  "idempotencyKey": "00000000-0000-4000-8000-000000000001",
  "reason": "Вымышленная причина"
}
```

| `action` | Дополнительные поля | Результат |
|---|---|---|
| `snooze` | будущие `date`, `time` (`HH:mm`) дома источника | `snoozed` до сохранённого UTC-момента; исходный срок не сдвигается |
| `dismiss` | непустая `reason`, до 2000 знаков | `dismissed`, отдельно от выполнения/удаления |
| `restore` | нет | `active`, без открытия закрытого источника |
| `complete` | нет | `completed` только у обычного ручного срока; производный закрывается в источнике |

Ответ — `RadarActionState`. У нового экземпляра версия 0; успешная запись повышает
её на один. Автор/момент проставляются сервером. Общая отметка видна тем же читателям,
а меняется по существующему праву источника: ребёнок может менять назначенное ему
дело, собственный профиль меняет его владелец. Назначение обычного срока ребёнку
не выдаёт права редактировать его родительскую запись.

Повтор того же ключа операции не создаёт вторую отметку; квитанция возвращает текущее
доступное состояние сохранённого действия. Другой запрос с тем же ключом, устаревшая
версия, изменённый календарь/закрытый источник — 409. Недоступный ID — 404; видимый
без права изменения — 403. Клиент при 409 сохраняет форму и показывает актуальную
версию; ошибка обновления сохраняет введённое. Смена аккаунта очищает состояние формы.
Смена дома сбрасывает несовместимые фильтры.

У `after` с отсутствующим событием дату события задают существующей правкой правила
`PATCH /api/deadlines/:id`. Выполнение такого ручного срока записывает дату фактического
подтверждения в местном календаре как `eventDate`; последующее наступление вычисляет
общий движок. Оплата и продление не заменяются `complete` или `dismiss`.

## Хранение и жизненный цикл

См. [ADR-0040](adr/0040-radar-summaries.md). Ключ действия: правило, ключ календаря,
календарная дата. Он переживает повторный/полный пересчёт, смену UUID наступления,
смену пояса и корзину/восстановление. Правка календаря оставляет историю, но не переносит
отметку на другое наступление; следующее наступление серии имеет свою дату.
Режимы экрана показывают отложенные и неактуальные пункты, причину/автора/время и возврат.

Причины и история не индексируются и не читаются worker. ZIP экспортирует
`radar_actions.json` только по текущему RLS и выбранной области родителя, включая
историю и корзину. Поля размещения в выгрузке берутся из текущего правила. Окончательная
очистка источника удаляет правило и его действия каскадом.
