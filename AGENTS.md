# Правила для ИИ-агентов в HomeCRM

HomeCRM — семейное веб-приложение (PWA): дом и коммуналка, документы, контакты, дела, заметки. У каждого участника своё личное пространство, у семьи — общее пространство дома.

Перед работой прочитайте:

- [PRD](docs/02-prd.md) — что строим. Требования пронумерованы: AUTH-1, SPACE-3, UTIL-5…
- [План разработки](docs/03-dev-plan.md) — архитектура, этапы, ход работ.
- [ADR](docs/adr/README.md) — принятые технические решения и их причины.

Владелец продукта пишет по-русски. Документы, комментарии в коде и тексты интерфейса — на русском. Сообщения в журналах сервера — на английском: так их без искажений показывает любая консоль.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm install` | Ставит зависимости и подключает ловушку git перед `git push` |
| `pnpm dev` | Сервер (`127.0.0.1:8310`) и клиент (`127.0.0.1:5173`) в режиме наблюдения; другие порты — через `PORT` и `WEB_PORT` |
| `pnpm check` | Всё, что проверяет ловушка перед отправкой: кодировка, формат и линтер, типы, тесты. Тестам базы нужен запущенный Docker: они поднимают свой PostgreSQL |
| `pnpm test:changed` | Только тесты, затронутые изменениями относительно `main` |
| `pnpm format` | Исправляет формат и порядок импортов |
| `pnpm test`, `pnpm test:watch` | Все тесты Vitest |

Окружение: Node 24, pnpm 12 (версия закреплена в `package.json`), GitHub CLI `gh` — для запросов на слияние и результатов проверок. У владельца — Windows 10 и PowerShell 7, в CI — Linux.

## Карта репозитория

| Путь | Что там |
|---|---|
| `apps/web` | Клиент: React 19 + Vite, PWA |
| `apps/server` | Сервер: Fastify; API и, позже, обработчик фоновых задач |
| `packages/shared` | Общее для клиента и сервера: правила доступа, схемы, типы |
| `packages/db` | База: схема Drizzle, миграции, роли, политики RLS, матрица доступа |
| `tools/access-probe` | Временная заглушка для замеров этапа 0 |
| `deploy` | Compose, туннель, настройка VPS, скрипты эксплуатации |
| `docs` | Исследование, PRD, план, ADR, бэклог, замеры этапа 0, runbook |
| `docs/tasks` | Брифы задач от ведущего агента |

## Как идёт работа

Каждое правило закрывает ошибку, которая уже случалась — в LifeOS или у других команд агентов. Обоснование — в [ADR-0019](docs/adr/0019-agent-workflow.md).

### Роли

| Роль | Что делает |
|---|---|
| Владелец | Решает по продукту, даёт команду на выпуск, проверяет выпуски на телефонах |
| Ведущий агент | Пишет брифы задач по плану, запускает исполнителей и ревьюеров, сливает в `main`, ставит метки версий по команде владельца. Код не пишет — только брифы, таблицу хода работ в плане и бэклог |
| Исполнитель | Делает одну задачу: сам коммитит, открывает запрос на слияние, пишет отчёт и завершается |
| Ревьюер | Делает одно ревью изменения и завершается |

### Одна задача — один свежий агент

- На каждую задачу запускается новый агент с брифом; после отчёта он завершается. Длинный контекст перечитывается каждым ходом — это главная статья расходов.
- Всё, что понадобится следующему агенту, записывается в репозиторий: PRD, таблица хода работ в плане, ADR, runbook, описание запроса на слияние. В переписке не должно остаться ничего, без чего нельзя продолжить.
- Бриф задачи:

  ```text
  Задача: R0.4 Заметки — первый сквозной модуль
  Требования: NOTE-1…3, SPACE-7
  Готово, когда: <проверяемые условия>
  Область: <пакеты и папки>; не трогать: <что>
  Ветка: feat/note-1-notes
  ```

### Изоляция

- Каждый исполнитель работает в своём `git worktree` и своей ветке. В основной папке `E:\Projects\HomeCRM` исполнители не работают.
- Тесты не занимают постоянных портов: сервер — через `inject` или на свободном порту. Тестовая база — своя на каждый прогон, со случайным именем.
- Сервер разработки в worktree запускается на своих портах: например, `PORT=8320` и `WEB_PORT=5183`.
- Рабочее окружение — compose-проект `homecrm`, его тома и база, порты 8300, 8301 и 8309 — и чужие worktree исполнители не трогают.
- Параллельно — не больше двух исполнителей, в непересекающихся областях. Миграции базы и правила доступа (`packages/shared/src/access.ts`) меняет один исполнитель за раз.

### Ветки, коммиты, слияние

- Требования меняются сначала в PRD, потом в коде.
- Имя ветки: `<тип>/<требование>-<кратко>`, например `feat/util-5-meter-validation`.
- Сообщение коммита начинается с номера требования PRD (`UTIL-5: проверка показаний`) или задачи плана (`0.2: заглушка для замеров`).
- Исполнитель сам коммитит и открывает запрос на слияние. Сливает в `main` и ставит метку версии только ведущий — при зелёных проверках и пройденном ревью.
- Запрещено: `git push --no-verify`, `git push --force` в `main`, слияние с красными проверками. Бесплатный тариф GitHub технически этого не запрещает — правило держится на вас.
- Задача готова, когда выполнены условия раздела 3.2 плана.

### Ревью

- Одно ревью на изменение. Исправляются только блокеры; остальные замечания ревьюер перечисляет в отчёте, а ведущий переносит их в [бэклог](docs/backlog.md).
- Блокер — это:
  - поведение расходится с PRD или критерием приёмки;
  - чужое личное или записи «Взрослые» могут попасть не тому; новая сущность без политики RLS и строк матрицы доступа;
  - риск потери или порчи данных: опасная миграция, удаление мимо корзины, деньги не в копейках, сроки не в часовом поясе дома;
  - уязвимость или секрет в коде и журналах;
  - красные проверки;
  - серьёзные и критичные замечания axe, поломка вёрстки на 360 px.
- После исправления блокеров ведущий проверяет только их. Повторного ревью нет.

### Тесты

- **Во время работы — только затронутое:** `pnpm test:changed`; Playwright — по изменённым экранам, на 360 и 412 px с axe. Так быстрее, и не приходится читать длинные журналы прогонов.
- **Перед отправкой** ловушка git запускает `pnpm check`.
- **На каждом запросе на слияние в CI** — модульные и интеграционные тесты и матрица доступа. Это независимая проверка: она решает, можно ли сливать, и главная гарантия того, что личное остаётся личным.
- **Полный визуальный прогон** — все сценарии на всех ширинах — идёт ночью на компьютере владельца и перед каждым выпуском. Красный ночной прогон останавливает выпуск.
- **Тесты на компьютере владельца можно запускать**, но отдельно от рабочего окружения: свой compose-проект `homecrm-test-<ветка>`, своя база, свои порты. Полный прогон — не больше одного одновременно.
- **Скриншоты для сравнения** снимаются только в контейнере Playwright на Linux, как в CI: Windows рисует шрифты иначе, и эталоны расходились бы.

### Отчёт

До 15 строк — в ответе ведущему и в описании запроса на слияние:

```text
Сделано: <что, номера требований>
Файлы: <главные>
Проверки: pnpm check — ок; тесты 48/48; матрица доступа 312/312; e2e — 3 экрана × 2 ширины
Риски: <что может пойти не так>
Нужно от владельца: <решения или проверки; «ничего», если ничего>
```

## Обязательные правила

### Безопасность и данные

1. Никогда не выводите, не записывайте в журналы и не коммитьте секреты: пароли, токены, ключи, значения `.env`, содержимое `E:\HomeCRM-data\secrets`. Если секрет нужен программе, он читается из файла окружения во время работы.
2. Работайте только внутри репозитория. Папка `E:\HomeCRM-data` с рабочими данными — только через скрипты из `deploy/scripts`.
3. В тестах, фикстурах и на скриншотах — только вымышленная семья. Настоящие данные семьи в репозиторий не попадают.
4. В журналах нет названий, номеров и текстов записей (PRD, раздел 13).
5. Выпуск в рабочее окружение, изменения на VPS и в DNS — только по прямой команде владельца.

### Личное остаётся личным

- Правила доступа — в `packages/shared/src/access.ts`. Политики RLS в базе и проверки на сервере обязаны давать тот же ответ; матрица доступа в CI сравнивает их с этим модулем.
- Администратор не видит чужое личное. Никаких служебных обходов проверки доступа в коде приложения.
- Новая сущность с пользовательскими данными добавляется только вместе с:
  - полями доступа: пространство, аудитория, автор, ответственный, отметка удаления;
  - политикой RLS;
  - строками в матрице доступа;
  - решением о поиске;
  - экспортом;
  - поведением корзины.

### Код

- TypeScript в строгом режиме. Сервер запускает `.ts` прямо в Node, поэтому синтаксис только стираемый: без `enum`, `namespace` и свойств-параметров конструктора. Вместо `enum` — массив `as const` и объединение типов.
- Относительные импорты пишутся с расширением: `./app.ts`, `./App.tsx`.
- Данные на границах — HTTP, переменные окружения, импорт, очереди — проверяются схемами zod.
- Деньги — целые копейки. Моменты времени — UTC (`timestamptz`). Даты без времени — отдельный тип. Сроки считаются в часовом поясе дома.
- Ошибки не проглатываются: либо обработка, либо проброс с контекстом.
- Новая зависимость — только с обоснованием в описании изменения; заметное решение — с ADR в `docs/adr/`.

### Тексты и кодировка

- Все файлы — UTF-8 без BOM, переводы строк LF.
- После правки русских текстов запустите `pnpm check:encoding`. Он ловит следы поломки кодировки: `????`, `�`, `Рџ`, `Ð`. <!-- encoding-check: ignore-line -->
- Пишите из PowerShell 7: он сохраняет UTF-8 по умолчанию. Windows PowerShell 5.1 не используйте.
- Тексты интерфейса — по PRD, раздел 13: правильные формы множественного числа, даты вида «5 окт.», суммы в рублях.

### Интерфейс

- Изменённые экраны проверяются в Playwright на ширине 360 и 412 px вместе с axe; скриншоты прикладываются к запросу на слияние.
- WCAG 2.2 AA, цели нажатия от 44 px, без горизонтальной прокрутки на 360 px.
